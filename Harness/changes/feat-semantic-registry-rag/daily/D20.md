### 2.2 四条硬约束（脚本 docstring 里也写死）

1. **不重算 embedding** —— 直接搬 v1 现有向量。一旦重算，影子比对里会混入向量漂移，
   差异不可解释。
2. **只增不删** —— 只往**新建的 v2 集合**写，v1 一行不动；同一 `(type, ontology_id)`
   走「先删后插」覆盖，删除范围只限本次覆盖到的那一行。
3. **幂等** —— 先删后插 ⇒ 重复跑不留重复行。
4. **写目标闸门** —— 目标库是 `default`（生产本体集合所在，Milvus 无自动备份 ⇒ 误写不可逆）
   且未显式 `--allow-prod` ⇒ 直接 `SystemExit`。

### 3.1 判据：为什么**不能**拿 v1 的召回当基准（关键发现）

v1 集合的 HNSW 是**近似检索**，而**同一段文本在 v1 里被写进了多个 `ontology_id`**
（实测 property 集合有 **698 组向量逐字节相同**）⇒ 图遍历陷在重复簇里，
**基线的近似误差比过滤本身的影响还大**：

```
query 3706（property，精确真值先按范围筛再取 top5）
  精确真值：  3706(0.0), 3704(0.396), 3705(0.438), 3707(0.457), 3703(0.502)
  v1 ANN（不过滤）：3704(0.396), 3707(0.457), 3709(0.537), 3708(0.631), 898(0.786)
                  ↑ 连 d=0.0 的「自己」都漏了
  v2 过滤检索： 3706(0.0), 3704(0.396), 3705(0.438), 3707(0.457), 3703(0.502)
                  ↑ 与真值**完全一致**
```

⇒ 所以「差异可解释」的基准必须是**精确真值**：用 numpy 在 v1 向量上暴力算 L2
（先按范围筛、再取 topK），要求 **v2 的过滤检索 == 真值**。
这同时给出一个反直觉但有用的结论：**带过滤的检索比不过滤的检索更准**
（候选集收窄 ⇒ ANN 退化为对收窄集合的精确扫描）。

## 四、过程中三次失败的根因（记录以免重犯）

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| 1 | 泄漏 20 条 / 范围内被误滤 2 条 | **维度真值表按 `ontology_id` 全局建索引** —— 但 `ontology_id` 是**按类型编号**的（class 121 ≠ property 121）⇒ 拿别的类型的维度判本类型的行 | 维度表改成按 `(type, ontology_id)` 建索引 ⇒ 泄漏归零 |
| 2 | 泄漏 0 / 范围内被误滤 1 / 不可解释新增 4 | **拿 v1 的 ANN 结果当基准**（见 §3.1） | 判据换成精确真值；「不可解释新增」这一指标随之作废（它测的是基线误差，不是过滤） |
| 3 | 幂等看着像坏了（37 → 74 行） | `num_entities`/`row_count` 是**物理行数**（含已删除未 compact 的墓碑行）⇒ 实测 v2 property 物理 14,920 行 vs **可见** 3,730 行 | 计数改成「按 `ontology_id` 去重的可见行数」；**报告里不能引用物理行数** |

> 第 3 条还有一个配套坑：**先删后插的顺序**必须是
> `delete → flush → release → load → insert → flush → release → load`。
> delete 之后必须先 release+load 让墓碑生效再插新行，否则新行可能落进
> 「已应用删除位图的 segment」而**跟着一起消失**（比重复更糟）。
