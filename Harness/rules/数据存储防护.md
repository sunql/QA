# 数据存储防护

## 强制要求（CRITICAL，不可违反）

- **Docker volume 是不可重建的资产**：所有 `qa-system_*` volume 内的数据（35万 entity_mapping、LLM API key、本体图谱、向量索引、种子业务数据）只能从备份恢复，无备份即永久丢失。
- **销毁命令必须经 hook 二次确认**：项目已配置 Claude Code PreToolUse hook（见下文）。任何 `docker compose down -v`、`docker volume rm` 等命令会被红框警告并要求显式 `QA_SYSTEM_VOLUME_GUARD_BYPASS=1` 才放行。
- **备份是唯一恢复手段**：数据库结构修改、数据迁移、容器操作前必须确认 `backups/pg/` 有最近 14 天内的快照；缺失必须立即补跑 `scripts/backup_pg.sh`。
- **执行任何 docker 命令前确认 `pwd`**：hook 是 project-scoped，**仅在本项目目录生效**；cd 到其他项目后再跑销毁命令不会被保护（本项目数据不受影响，但其他项目同理需各自防护）。
- **绝不手工改 prod 数据库 schema 而不备份**：详见 `数据库环境使用规范.md`。

## Docker Volume 命名约定

| Compose 名（`docker-compose.yml` 内） | 完整 docker 名 | 用途 | 不可重建原因 |
|---|---|---|---|
| `pg_data` | `qa-system_pg_data` | qa_metadata（PostgreSQL 42表） | 35万 entity_mapping + 全部业务数据 |
| `neo4j_data` | `qa-system_neo4j_data` | 本体图谱（67 个 prod 类） | ontology_class/property 节点与关系 |
| `milvus_etcd` | `qa-system_milvus_etcd` | Milvus 元数据 | 向量索引元信息 |
| `milvus_minio` | `qa-system_milvus_minio` | Milvus 存储 | 对象存储 chunk |
| `milvus_data` | `qa-system_milvus_data` | Milvus 向量 | 文档向量 |
| `mysql_data` | `qa-system_mysql_data` | WMS demo 库 | Oracle WMS 同步数据 |
| `objects_data` | `qa-system_objects_data` | **知识源文件原件**，MinIO 后端。丢弃后 `document_catalog.storage_url` 全部失效，证据链断头 —— 不可重建（源文件只在用户手里） |

**不要修改 volume 名**。保持 `qa-system_*` 前缀：
- 显式关联本项目（`docker volume ls` 一眼识别）
- 避免 `docker volume prune` 误删（只会清掉孤立 volume）

## 销毁性命令黑名单

| 危险命令 | 后果 | 安全替代 |
|---|---|---|
| `docker compose down -v` | 删除所有 named volumes（全部 6 个） | `docker compose down`（无 `-v`） |
| `docker-compose down -v` | 同上（v1 写法） | `docker-compose down` |
| `docker compose down --volumes` | 同上 | `docker compose down` |
| `docker compose down --rmi all` | 删镜像 + volume（卷不删，但会清空缓存） | `docker compose down` |
| `docker volume rm <name>` | 删除指定 volume | 先 `docker volume ls` 确认 |
| `docker volume prune` | 删除所有未挂载 volume | 先 `docker volume ls` 检查 |
| `docker system prune -a` | 删除未用镜像 + 容器 + volume | `docker system prune`（无 `-a`） |
| `docker system prune --volumes` | 同 `docker volume prune` | 不带 `--volumes` |
| `docker rm -v <container>` | 删除容器时清其匿名 volume | `docker rm <container>`（无 `-v`） |

**注意**：`docker compose down`（无 `-v`）、`docker compose stop`、`docker compose restart` 都不会删数据，可放心使用。

## 备份策略

| 维度 | 值 |
|---|---|
| 备份脚本 | `scripts/backup_pg.sh` |
| 默认保留窗口 | 14 天（`--keep 14`） |
| 备份时间 | 每日 8:00 + 20:00（cron 两条） |
| Cron marker | `# qa-system-pg-backup` |
| 输出路径 | `backups/pg/qa_metadata_YYYY-MM-DD_HHMM.dump` |
| 备份格式 | `pg_dump -Fc` custom（压缩二进制，支持 `pg_restore --table` 选择性恢复） |
| 安装/卸载 | `./scripts/install_pg_backup_cron.sh` / `--uninstall` |
| 备份日志 | `backups/pg/backup.log` |
| 备份内容覆盖 | 42 表全部业务数据 + 全部 entity_mapping + 全部 ontology_class |

**仅备份 PostgreSQL（qa_metadata）**。Neo4j / Milvus / MySQL 当前没有自动备份脚本——其数据理论上可重建（ontology_class 可重新 seed），但重建耗时较长，恢复优先级低于 PG。

## 事故复盘（2026-09-10）

**事件**：prod `qa_metadata` 42 张表在 2026-09-10 23:36 被静默清空。

**根因调查**：
- `pg_stat_user_tables` 显示大量表 `n_tup_ins > 0` 但 `n_live_tup = 0`、`n_tup_del = 0` —— 非 SQL DELETE
- `pg_control` 最后修改时间 `2026-09-10 23:36:52`（最后一次 checkpoint）
- 唯一可能路径：`docker compose down -v` 或 `docker volume rm qa-system_pg_data` 在无人察觉下执行

**恢复 SOP**（约 30 分钟）：
1. `ls backups/pg/` 找最近的 .dump（本次：`qa_metadata_2026-09-09_1259.dump`）
2. `docker exec -u postgres qa-postgres dropdb qa_metadata` + `createdb qa_metadata`（或 `DROP SCHEMA public CASCADE; CREATE SCHEMA public;`）
3. `cat backups/pg/qa_metadata_2026-09-09_1259.dump | docker exec -i qa-postgres pg_restore -U qa_user -d qa_metadata --no-owner`
4. `docker exec qa-backend bash -lc 'cd /app && alembic upgrade head'` 补 0048-0051 迁移
5. 按顺序跑种子脚本：`seed_ontology` → `seed_features` → `seed_kpi_catalog` → `seed_kpi_semantic_index` → `seed_business_objects` → `seed_menu_config`
6. **手动配置 llm_config API key**（备份不含密钥）；**重跑 sync_entity_mapping_from_thbi**（35万 entity_mapping 不在备份）；**重新上传 document_catalog**

**完整记录**：memory `qa-system-pg-wipe-incident.md`。

## Claude Code Volume Guard 钩子

项目已配置 PreToolUse hook（`.claude/hooks/protect_volumes.sh`），触发红色警告并 `exit 2` 阻断：

- `docker compose down -v` / `--volumes` / `--rmi all`
- `docker-compose down -v` / `--volumes`
- `docker volume rm <任意>` / `docker volume remove <任意>`
- `docker system prune -a` / `--all` / `--volumes`
- `docker rm -v <container>` / `--volumes`

**绕过方式**（仅紧急情况，需在终端显式设置环境变量）：

```bash
export QA_SYSTEM_VOLUME_GUARD_BYPASS=1
# 然后再跑销毁命令 —— hook 仍打印 WARNING 但 exit 0 放行
```

**作用域**：hook 是 **project-scope**（`.claude/settings.json` matcher=`project`），仅在本项目目录内执行命令时触发。其他项目目录执行 `docker compose down -v` 不受影响。

**测试 hook**：

```bash
# 危险 → 阻断（exit 2 + 红框）
echo '{"tool":"Bash","params":{"command":"docker compose down -v"}}' | ./.claude/hooks/protect_volumes.sh
echo $?  # 期望: 2

# 安全 → 放行（exit 0）
echo '{"tool":"Bash","params":{"command":"docker compose down"}}' | ./.claude/hooks/protect_volumes.sh
echo $?  # 期望: 0
```

## 反模式（review 时拦截）

- ❌ 「反正有备份，删一下没事」—— 备份窗口 14 天，事故发现延迟可能超过
- ❌ 「hook 太烦了，直接 setenv QA_SYSTEM_VOLUME_GUARD_BYPASS=1 永久绕过」—— 旁路仅限紧急场景，永久绕过等于撤销 Layer 1 防护
- ❌ 「crontab -l 看不到 cron 就以为是空的」—— 用户级 cron 是 `crontab -l`，不是 `/etc/crontab`
- ❌ 「在 prod `qa_metadata` 上跑 DDL 前先备份」 —— 不备份就改数据是事故温床
- ❌ 「手动 `docker volume rm` 一个无关 volume 没事」 —— 写错 volume 名就完蛋，先 `docker volume ls` 确认全名
- ❌ 「其他项目的 hook 没配就不管」 —— 每个项目都应配自己的 PreToolUse hook
