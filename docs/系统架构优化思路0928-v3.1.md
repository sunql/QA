## 一、为什么不是"Text-to-SQL"

（保留 v3 §1 内容，本节与架构可行性无关，是定位陈述）

我们做的不是一个 NL2SQL 系统，而是一个完整的 **AI 智能问数 + 多轮数据分析 + 自动报告生成** 平台。

真正难的地方，不在「把自然语言转成 SQL」，而在：

> **让 AI 理解企业业务语义 → 正确选择数据 → 正确生成查询 → 验证结果 → 多轮推理分析 → 选择合适的表达方式 → 形成可信、可追溯的分析报告。**

系统的本质定义：

> **Natural Language → Enterprise Semantic Model → Analytical Plan → Query Plan → SQL → Evidence → Insight → Report**

```
        → Metric / Dimension → Semantic → Data Mapping → SQL/API
```

### 4.12 Evidence：**降级**——从 8 种 → 3 种 MVP

**v3 原案**：8 种类型（Document / Database Query / API Result / Metric Result / Transaction / Business Event / System Record / Human Confirmation）。

**v3.1 校准**：每种类型 1-2 周工程（独立 schema + 版本管理 + 可追溯机制），8 种全做 = 2-3 个月。**MVP 阶段只做 3 种**：

| MVP 类型 | 存储 | 版本管理 | 工程量 |
|---|---|---|---|
| **Document** | Object Storage + PG 元数据 | Git-like（不可变 + diff）| 2 周 |
| **SQL Query** | PG（query + params_hash + result_hash）| 追加写 | 1 周 |
| **Metric Result** | PG（metric_code + period + value + calc_time）| 追加写 | 0.5 周 |

**延后类型**（📦 v3.x）：

- API Result：等外部系统对接需求触发
- Transaction / Business Event：等业务事件总线建设后
- System Record / Human Confirmation：等审计系统全面升级

**激活条件**：
```yaml
v3.x_unlock_evidence_type:
  trigger: 有明确业务需求 + 已完成 MVP 3 种
  effort_per_type: "1-2 周"
  total_cap: 8   # 不会超过 8 种
```

| 现状 | 🟡 部分（wiki_link）；独立 Evidence 表 ⚪；MVP 3 种待建 |
|---|---|

### 4.13 Authority：**降级**——从完整模型 → 字段 + 治理流程建议

**v3 原案问题**：

- 假设"财务部定义财务指标、CRM 管理部门定义客户..."，但：
  - 同一指标多 Owner（"客户活跃度"既属 CRM 也属销售）
  - 跨部门指标普遍存在（毛利率 = 财务 × 业务）
  - Authority 是**治理流程的产物**，不是技术能"建"出来的——没有治理委员会，模型形同虚设

**v3.1 校准**：

1. **技术层只做 Authority 字段**（枚举值见 §4.11 YAML 示例），承认"权威归属"是**软约束**
2. **冲突消解不算法化**：当两个 Claim 冲突时，**系统不自动判定**——提示用户"X 部门 vs Y 部门说法不同，请选择"
3. **治理建议**（独立文档 `docs/governance-authority.md`）：如何建立治理委员会、如何定义指标 Owner、如何处理跨部门冲突——**这是组织问题，不是技术问题**

```python
# v3.1 Authority 处理伪代码
def resolve_conflict(claims: list[Claim]) -> Resolution:
    """v3.1: 不算法化判定，提示用户选择"""
    if len({c.authority for c in claims}) > 1:
        return Resolution(
            status='NEEDS_HUMAN_DECISION',
            options=claims,
            message='多个权威来源说法不同，请选择采纳'
        )
    return Resolution(status='OK', claim=claims[0])
```

| 现状 | ⚪ Authority 字段；治理流程文档 |
|---|---|

### 4.14 Knowledge Compiler：**降级**——从 8 种产物 → 3 种核心 + 运维约束

**v3.1 三种核心产物**：

| 产物 | 存储 | 触发 | 更新策略 |
|---|---|---|---|
| **Semantic Graph** | Neo4j | 业务对象 / Relation 变更 | 增量 |
| **Vector Index** | Milvus | Term / Wiki Page 变更 | 增量 + 批量刷新 |
| **SQL Metadata** | PG | Metric / Rule 变更 | 增量 |

**v3.1 强制运维约束**（v3 原案缺失的关键）：

1. **图、向量、关系三元同步**：Semantic Graph（Neo4j）+ Vector Index（Milvus）+ Relational（PG）保持**最终一致**（允许 ≤ 5 秒延迟）
2. **编译产物可追溯**：每个产物都能反向追溯到源定义（source_object_id + source_version）
3. **增量编译**：支持单对象增量更新，避免全量重建
4. **缓存与失效**：Semantic Graph 改了 → Vector Index 必须 invalidate（不强制 rebuild）
5. **版本管理**：业务定义变更产生新版本（v1 → v2），编译产物保留旧版本只读
6. **编译失败回滚**：使用事务/快照机制，编译失败回滚到上一版本（不允许半成品状态）

**延后产物**（📦 v3.x）：Query Template / API Definition / Agent Tool / Prompt Context / Validation Rule / Policy——这些由其他模块维护（agent_tool_config_registry / metric_promotion_service 已部分覆盖），不强制走 Knowledge Compiler 统一编译。

| 现状 | ⚪ 编译逻辑分散（ontology_service / agent_tool_config_registry / metric_promotion）；统一 Compiler ⚪ |
|---|---|

## 五、L6 · AI Data Analyst（**重大降级**）

### 5.0 Agent 设计原则（v3.1 新增）

> **v3.1 原则**：每个 Agent 必须有明确的成本/价值权衡；能合并的不拆分；能用模板/LLM 后处理的就不做独立 Agent。

**v3.1 Agent 总成本上限**：

| 任务类型 | LLM 调用上限 | Token 上限 | 月度成本上限（100 用户） |
|---|---|---|---|
| 单步查询 | 1 次 | ≤ 4k | < 500 元 |
| 多步分析 | 3 次 | ≤ 12k | < 1500 元 |
| 自动报告 | 5 次 | ≤ 20k | < 2500 元 |

超限必须经**人审介入**（不能纯 LLM 跑完）。

```
用户："今年销售额是多少？"     → Metric=SA, Year=2026
下一轮："去年呢？"              → Metric 继承, Year=2025
下一轮："华东呢？"              → 继承, Region=华东
```

### 5.2 Semantic Agent（**增强**：合并 Intent 职责）

**v3.1 调整**：v3 的 Intent Agent 与 Semantic Agent 职责高度重叠（都是"理解用户问题"），合并为一个。

**职责**：

```
意图识别（合并自 Intent Agent）
   ↓
语义映射（自然语言 → 企业语义对象）
```

**输出示例**：

```json
{
  "intent": "Query | Comparison | Trend | Ranking | RootCause | Report",
  "semantic": {

    "metric": "Sales Amount",

    "filters": [{ "field": "region", "op": "=", "value": "华东" }],
    "comparison": "YoY"
  }

```

**这里不应直接生成 SQL。**

| 现状 | 🟡 semantic_recall + IntentType 枚举；合并 Agent ⚪ |
|---|---|

### 5.3 Analysis Planner：**降级**——从 10+ 步 → ≤ 5 步

**v3.1 限制**：

- **≤ 5 步**硬上限，超出由 Planner-Mini 拒绝并提示"问题过于复杂，请拆解"
- 每步输出必须是 **Semantic Query**（不是自由文本）
- **Planner 输出必须可缓存**（相同输入产生相同计划），便于降级为模板

**v3.1 强制分级**：

| 问题复杂度 | 步数上限 | 实现 |
|---|---|---|
| 单步查询 | 1 | 跳过 Planner |
| 简单对比 / 排名 | 2-3 | 模板化（TOP-N 模板） |
| 中等分析（趋势 + 拆解） | 4-5 | LLM 生成 + 模板校验 |
| 复杂归因 | > 5 | **拒绝，走人审** |

**拒绝示例**：

```
用户："完整分析今年华东销售下降的所有原因"
Planner-Mini:
  识别步骤：1) 销售同比 2) 区域拆解 3) 客户拆解 4) 产品拆解 5) 价格拆解 6) 订单量 7) 客户流失 8) ...
  步数 = 12，超出上限
  → 提示：请聚焦某一维度（如"先分析客户层面原因"）
```

| 现状 | 🟡 multi_step_plan + chained_step_plan；≤5 步限制 ⚪ |
|---|---|

### 5.4 Query Agent（保留 + 合并 Result）

**v3.1 调整**：v3 的 Result Agent（结果统计）合并进 Query Agent——SQL 执行后立即做基础统计（Distribution / Outlier / Trend），不需要独立 Agent。

**职责**：

```
Semantic Query
   ↓
Schema Retrieval（按 metric/dimension 选表）
   ↓

   ↓

   ↓

   ↓

   ↓
```

### 5.6 Hypothesis Agent：**降级**——从独立 Agent → 可选 LLM 后处理钩子

**v3.1 调整**：Hypothesis Agent 不作为主链路 Agent，而是**可选后处理**。

**触发条件**（v3.1 限定）：

```yaml
hypothesis_hook:
  trigger:
    - Intent == RootCause
    - 或用户显式说"分析原因"
  cost: +1 LLM call（约 4-8k tokens）
  output: 
    type: list[Hypothesis]
    max_count: 3  # 不超过 3 个假设
  risk_acknowledgment: |
    LLM 生成的假设是"看起来合理"的相关性，不是因果。
    每个假设必须用后续 Evidence Query 验证。
```

**v3.1 假设生成规则**（强制约束）：

1. **必须包含已知 driver**：从 Schema 自动发现可能 driver（如 order_count / avg_price / customer_count）
2. **每个假设必须可验证**：附带验证 SQL
3. **不做因果判断**：仅生成"可能解释"，不输出"因为 X 所以 Y"
4. **假设数量 ≤ 3**：避免 LLM 发散

| 现状 | ⚪ 当前根因归因较粗；Hypothesis Hook ⚪ |

## 十二、可信性：**Confidence 模型降级**

### 12.1 三层证据链（保留）

```
1. 数据层证据：SQL Query + Result Hash
2. 业务层证据：Business Rule + Definition
3. 知识层证据：Document + Authority + Version
```

### 12.2 Confidence：**改写**——从 4 维连乘 → 离散 4 级

**v3 原案**（伪精确）：

```python
Confidence = 数据完整度 × 业务规则匹配度 × 来源权威度 × 历史准确率
```

**v3.1 校准**：

```python
# v3.1: 离散 4 级 + 触发条件
def calculate_confidence(claim: Claim) -> Confidence:
    if not has_evidence(claim):
        return REFUSE                      # 无证据，拒绝判定
    if data_is_stale(claim):
        return REFUSE                      # 数据未更新
    if conflicting_authorities(claim):
        return REFUSE                      # 多源冲突（参考 §4.13）
    
    score = 0
    if has_complete_evidence(claim):    score += 1
    if rules_matched(claim):            score += 1
    if has_history(claim, min=10):      score += 1   # 冷启动豁免
    if historical_accuracy(claim) > 0.9: score += 1
    
    return {3: HIGH, 2: MEDIUM, 1: LOW, 0: REFUSE}[score]
```

**4 级定义**：

| 等级 | 含义 | 用户提示 |
|---|---|---|
| **HIGH** | 证据完整 + 规则匹配 + 历史准确 | "高置信度，可作为决策依据" |
| **MEDIUM** | 满足前 2 项 | "中等置信度，建议复核" |
| **LOW** | 仅满足证据存在 | "低置信度，仅供参考" |
| **REFUSE** | 任一前置条件缺失 | "无法判定，原因：..." |

**关键改进**：

- **避免假精确**：不再输出"置信度 87%"这种 LLM 算不出的数
- **可解释**：每级都有明确触发条件
- **冷启动友好**：新 Claim 不因"历史准确率 = 0"而一律归零

| **3c 自动报告** | 仅限数据成熟 + 模板化场景 | ≤ 5 次 | **可选人审** |

**v3.1 Phase 3 硬约束**：

1. **查询 ≤ 10 个**（超出拒绝）
2. **强制人审环节**（v3.1 不允许"全自动报告"）
3. **结论必须有 Evidence 引用**（无 Evidence 的结论 = 不输出）
4. **结论分类输出**：
   ```
   [事实] 基于查询结果的客观陈述
   [推断] 基于业务规则的合理推断
   [假设] 需要进一步验证的可能原因
   ```
5. **每份报告 ≤ 2 页**（超长 = 用户不会读）

### 26.3 不会升级的能力（**组织问题，不是技术问题**）

这些是**组织能力问题**，技术上无法靠架构解决：

| 能力 | 不升级的理由 |
|---|---|
| **真正的 Authority 治理** | 需要治理委员会、Owner 制度、冲突仲裁流程——企业治理变革 |
| **业务对象完整性** | 需要业务部门持续投入梳理对象、属性、关系——知识工程 |
| **指标口径统一** | 需要财务/业务/IT 三方共识——业务治理 |
| **数据质量 SLA** | 需要数据 Owner 承诺与考核——组织制度 |
| **业务事件总线** | 需要各业务系统改造——架构级投入 |

**v3.1 立场**：技术架构不能假装能解决组织问题。明确划线，让架构做架构的事，让组织做组织的事。

### 26.4 文档维护约定

**v3.1 维护原则**：

1. **任何能力降级必须更新本文档**——不能默默砍掉 §22 中的能力而文档不更新
2. **任何 v3.x 激活必须先评估 ROI**——按 §26.2 表格的触发条件
3. **每季度回顾**：检查 §22 现状表格，更新 ✅ → 🟡 → ⚪ 状态
4. **不写"未来会做 X"**——只写"满足条件 Y 后会激活 X"，避免重蹈 v3 的"理想化承诺"
