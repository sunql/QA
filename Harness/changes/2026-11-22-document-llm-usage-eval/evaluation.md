  「辅助生成数据库问答语句」「对结果判断」

## 一、现状事实（代码实测，非推测）

### 1.1 三条链路对文档的接触面

| 链路 | 入口 | 现在用不用文档 |
|---|---|---|
| 采购知识检索 | `POST /procurement/knowledge/documents/search` → `searchProcurementDocuments` | ✅ 用（RAG + 密级闸 + catalog 核验）；**证据已带回 `relatedEntities`** |
| 采购 Copilot | `POST /procurement/copilot/messages` → 编排 run → 工具 | ◐ **能查**（`procurement_policy_search` / `contract_document_search` 已绑定），但**没有"用文档评估结果"的指令** |
| AIChatService（NL2SQL） | `POST /api/v1/chat/*` → ChatService | ❌ **完全不碰文档**（纯 本体+数据库 问答） |

### 1.2 AIChat 的四个可注入点（都已定位到行）

```
问题
 ├─[① 意图/路由] intent_service → 决定走 SQL / 多步 / 指标 / 研究
 ├─[② 计划] planQuery（选类）
 ├─[③ 生成 SQL] chat_service.py:1706  generateSql(question, classes, ..., context=, fewShot=, ...)
 └─[④ 生成答案] chat_stream_output.py:144  _buildAnswerPrompt(question, sql, data, history=)
       ↑ 提示词由 chat_service.py:2401 组装（安全前置 + 问题 + SQL + 数据摘要 + 空结果提示 + 历史）
```

**④ 是「用文档评估结果」的天然落点**：那里已经有 `summary_dict`（全量统计 + 样本），
只要多注入一段「文档依据」，模型就能做到「数据说 X、制度说 Y、二者是否一致」。

**③ 是「辅助生成 SQL」的落点**：`generateSql` 已有 `context` / `fewShot` / `driftWarning`
等可选上下文参数，加一个「文档口径片段」与既有模式一致。

## 二、两个**数据质量阻塞项**（不修就会把垃圾喂给模型）

### 阻塞一：旧向量里可能是乱码

实测各文档解析质量（中文占比）：

```
DOC-7DF4B953ADD1   82.0%  OK        DOC-WIKI-DD51544F3ED0  58.4%  OK
DOC-22B82B2C5FAF   73.6%  OK        DOC-WIKI-3E0C1374E234  44.5%  OK
DOC-1A6D70F78F58   77.0%  OK        DOC-WIKI-F9F24A0FA8B5  26.8%  OK
DOC-203B7FEB25B4   解析失败 ⚠️       DOC-D54BCAD4E30F       11.6%  ⚠️
```

`DOC-203B7FEB25B4`（采购与供应商控制程序.pdf）**现在解析直接失败**，但它在
`document_embeddings` 里仍有 **84 个旧 chunk**，检索会命中且内容是乱码
（实测片段：`RR REINS 34APaP 多 Res`）。

⇒ **若直接把这些 chunk 注入 prompt，等于定向污染模型**。
必须先做「入库文本质量体检 + 重建」，并对低质量文档打 `text_quality` 标记、
在注入时**排除**。

### 阻塞二：关联数据可能脏

实测存在 `entityKey = "KPI_PAYMENT_ON_TIME 付款及时率"`（编码+名称混写）与
「把 A 文档关联到错误指标」这类记录 ⇒ `relatedEntities` 注入提示词前，
必须**只信结构化校验通过的**（类名/指标名严格匹配 ontology 表），否则模型会把
错误关联当事实。

## 三、三类场景的设计

### 3.1 采购知识检索（已具备，补两点）

现状已可用。建议补：
1. **实体过滤自动化**：现在 `entityKeys` 只能调用方手填，无人使用；
   当查询里解析出供应商/物料时自动带上 `TYPE:KEY`，把"这份文档是否相关"判断
   交给关联而不是纯向量相似度。
2. **质量闸**：检索结果按 `text_quality` 过滤（见阻塞一）。

### 3.2 采购 Copilot（指令层 + 一个可选工具）

Copilot 已经能调文档工具，缺的是**用它做判断**。两块改动，都不碰执行引擎：

| 改动 | 内容 |
|---|---|
| **profile 指令**（`seed_procurement_agent_profiles.py`） | 增加铁律：结论要给"数据值 + 文档依据 + 两者是否一致"；文档与数据冲突时**以数据为准**并显式指出冲突；文档仅作口径/规则来源，**不得改写数值** |
| **可选工具 `policy_compliance_check`** | 输入 `{claim, documentTypes?}` → 返回命中文档片段 + 关联对象，供 Agent 在"结果是否合规"一问里调用（复用 `searchProcurementDocuments`，零新检索逻辑） |

**代价**：每次多一次文档检索（embedding + Milvus，约 100–300ms）+ 500–1500 prompt tokens。
**开关**：`COPILOT_DOC_EVAL=1`（默认关，验收后再开）。

### 3.3 AIChatService（四个用途 → 两个钩子 + 一个路由）

用户提的四个用途，归并为三处改动：

| 用户诉求 | 落点 | 做法 |
|---|---|---|
| 辅助生成 SQL（理解口径/术语） | **钩子 H1**：`generateSql(..., documentContext=)` | 生成 SQL 前用问题检索 topK=2 文档片段，**只取"口径/字段含义/术语定义"摘要**（≤600 字），作为参考数据注入；不注入整篇 |
| 用文档评估结果 / 对结果判断 | **钩子 H2**：`_buildAnswerPrompt(..., documentContext=)` | 答案阶段注入同样片段，要求模型输出"数据结论 + 文档依据 + 一致性判断" |
| 文档内容理解（纯制度问答） | **路由 H3**：意图层分流 | 问题不含数值/排名诉求、但命中制度类文档 ⇒ 直接走文档问答（复用知识检索），**不生成 SQL**；避免"用 SQL 查一条制度"这种无意义路径 |

**统一护栏（写进 prompt 与代码，不靠模型自觉）**：
1. **数据优先**：文档不得覆盖查询结果数值；冲突时并列呈现并标注「文档说 X / 数据为 Y」；
2. **ACL**：检索必带 `user` 走密级闸（与知识检索同一套 `buildClearanceFilter`）；
3. **预算**：每轮注入 ≤1500 tokens，超了按相关度截断；
4. **可关闭**：三个钩子共用 `CHAT_DOC_CONTEXT=0/1`，默认关；
5. **可观测**：注入的文档 id + 命中分数进 answer 审计行（便于回答"为什么这么说"）。

## 四、成本与风险

| 项 | 估算 | 说明 |
|---|---|---|
| 延迟 | +100–300ms/轮 | embedding（本地 Qwen 约 30–80ms）+ Milvus 检索 |
| Token | +500–1500/轮 | 两阶段（SQL + 答案）各注入一次；答案阶段占比更高 |
| 质量风险 | **中** | 文档过期/冲突会诱导模型做错判断 ⇒ 靠「数据优先 + 冲突并列」护栏 |
| 数据风险 | **高（当前）** | 乱码 chunk（阻塞一）与脏关联（阻塞二）会直接污染 |

**⇒ 先修数据质量，再上钩子。** 顺序反了会得到"模型引用了一段乱码"这种最难排查的结果。

## 五、建议的分阶段计划

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0（前置，必须）** | 入库文本质量体检脚本（中文占比 + 解析成功率）+ 低质量文档重建/标记；关联数据清洗（校验类名/指标名严格匹配） | 体检报告：所有可检索文档 `text_quality=OK`；关联 100% 通过结构化校验 |
| **P1** | AIChat 钩子 **H2**（答案阶段注入文档口径）——收益最大、风险最低（只影响措辞与解释，不改 SQL） | 试点 10 问：答案带文档依据；数值与 SQL 结果 100% 一致；关闭开关后行为不变 |
| **P2** | AIChat 钩子 **H1**（SQL 生成注入口径） | 口径类问题 SQL 正确率不降；prompt token 增量 ≤15% |
| **P3** | Copilot profile 指令 + `policy_compliance_check` 工具 | 试点问题能给出「数据 + 文档 + 一致性」三段式 |
| **P4** | 路由 **H3**（纯制度问题走文档问答） | 这类问题不再生成 SQL；响应时间下降 |
| **P5** | 知识检索实体过滤自动化 + 质量闸 | 检索精度提升可量化（人工标注 20 问） |

## 六、结论

1. **可行**，且三条链路里 **AIChat 的 H2 是性价比最高的一步**（收益大、风险小）。
2. **但当前数据质量不支持直接上**：先做 P0（体检 + 重建 + 关联清洗），否则会把
   乱码 chunk 和错误关联喂进提示词。
3. Copilot 侧只需**指令 + 一个薄工具**，不需要改执行引擎。
4. 全部改动都能用开关灰度，且**不改变「数据优先」这条底线**。
