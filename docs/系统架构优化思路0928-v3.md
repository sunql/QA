## 一、为什么不是"Text-to-SQL"

我们做的不是一个 NL2SQL 系统，而是一个完整的 **AI 智能问数 + 多轮数据分析 + 自动报告生成** 平台。

真正难的地方，不在「把自然语言转成 SQL」，而在：

> **让 AI 理解企业业务语义 → 正确选择数据 → 正确生成查询 → 验证结果 → 多轮推理分析 → 选择合适的表达方式 → 形成可信、可追溯的分析报告。**

完整的处理链条：

```
用户自然语言
   ↓
意图理解
   ↓
业务语义理解
   ↓
查询/分析规划
   ↓
数据资产选择
   ↓
SQL 生成
   ↓
SQL 验证
   ↓
数据库查询
   ↓
结果理解
   ↓
进一步查询 / 多轮分析
   ↓
分析结论
   ↓
报告规划
   ↓
文字 / 表格 / 图表
   ↓
最终报告
```

例如用户问「**帮我分析今年华东区域销售下降的原因**」，系统可能需要执行：

```
1.  今年销售额
2.  去年同期销售额
3.  按区域拆分
4.  找出华东下降情况
5.  再按客户拆分
6.  找出下降最大客户
7.  再按产品拆分
8.  找出下降最大产品
9.  订单数量
10. 平均订单金额
11. 价格变化
12. 客户流失情况
13. 综合分析下降原因
14. 生成报告
```

系统的本质定义应为：

> **Natural Language → Enterprise Semantic Model → Analytical Plan → Query Plan → SQL → Evidence → Insight → Report**

而不是简单的：

> Natural Language → SQL

## 二、10 个核心难点

决定系统成败的关键不在模型，而在以下 10 个工程问题：

| # | 难点 | 难度 | 核心问题 | 解决位置 |
|---|---|:--:|---|---|
| ① | 企业业务语义理解 | ★★★★★ | AI 能否理解"销售额""有效订单" | §4 Semantic |
| ② | Schema / 数据资产选择 | ★★★★★ | 3000 表中如何精确选表 | §4 + §16 |
| ③ | Text-to-SQL | ★★★★☆ | 生成正确 SQL | §11 Compiler |
| ④ | SQL 正确性验证 | ★★★★★ | SQL 能执行 ≠ SQL 正确 | §12 + §13 |
| ⑤ | 多步骤问题拆解 | ★★★★★ | 一句话对应 10~20 个查询 | §5 Planner |
| ⑥ | 多轮会话上下文 | ★★★★★ | "那华南呢？"指什么 | §15 Memory |
| ⑦ | 查询结果语义理解 | ★★★★★ | 从数字发现业务规律 | §5 Result Analyzer |
| ⑧ | 分析推理 | ★★★★★ | 从"下降 20%"找原因 | §5 Hypothesis |
| ⑨ | 图表自动选择 | ★★★★☆ | 数据 → 图表的映射 | §11 Report DSL |
| ⑩ | 报告生成与可信性 | ★★★★★ | 报告不能是 AI 乱编 | §12 可信性 |

**真正决定系统效果的是 ① + ② + ⑤ + ⑦/⑧**，而不是模型本身。

## 四、L5 · Enterprise Semantic & Knowledge Layer（核心）

> 这一层把传统数据治理体系与 LLM Wiki 体系连接起来，是整个系统的"AI 词典"。

### 4.1 核心思想

传统企业的数据架构是 `数据库 → 表 → 字段 → SQL`，AI 不应直接消费这个层级；应升级为：

```
Business → Business Object → Entity → Relation
        → Metric / Dimension → Semantic → Data Mapping → SQL/API
```

例如用户问"今年华东销售下降多少"，AI 真正理解的是：

```
Business Object: Sales
   ├── Metric: Sales Amount
   ├── Dimension: Region
   ├── Filter: Region = 华东
   └── Time: 2026
```

而非直接拼字符串。

### 4.2 12 类核心对象 + 6 辅助对象

| # | 对象 | 作用 | 现状 |
|---|---|---|---|
| ① | Business Object | 业务对象根（Customer / Supplier / Sales Order ...） | ✅ |

| ③ | Attribute | 业务对象属性 | ✅ |
| ④ | Relation | 对象间关系（1:N、M:N、引用） | ✅ |
| ⑤ | Metric | 指标（语义化定义） | ✅（KPI Catalog） |

### 4.3 Business Object：体系的根

> 企业业务世界中可被管理、分析、关联和决策的核心对象。

示例：

```
Customer（业务对象）
  Identity:    customer_id
  Attributes:  name, type, region, industry
  Relations:   Customer → Sales Order / Contract / Invoice
  Metrics:     Sales Amount / Order Amount / Receivable / Gross Profit
  Knowledge:   Customer Profile / Customer Agreement / Credit Policy
```

**它不是一张表，而是一个聚合语义根。** AI 用它作为理解企业的"词典入口"。

| 现状 | ✅ 已建 Business Object 模型 + 8 业务对象 seed |
|---|---|

### 4.4 Entity：实例层

```
Customer
   ├── Customer A
   ├── Customer B
   └── Customer C

Customer A
   ├── Sales = 1.2 亿
   ├── Orders = 382
   ├── Receivable = 800 万
   ├── Contract
   ├── Complaint
   ├── Meeting Minutes
   └── Customer Evaluation
```

Entity 把**结构化数据 + 知识 + 文档 + 事件 + 指标**汇聚到同一实例。

| 现状 | ✅ Neo4j 实例节点 + wiki_page_id 关联 |
|---|---|

### 4.5 Relation：让企业从"表"变成"业务网络"

典型关系网：

```
Customer → Sales Order → Product → Product Category
                                  ↓
                                BOM → Material → Supplier

Product → MBOM → Process Plan → Routing → Operation → Resource
```

Relation 必须**可枚举、可推理、可视化**，是图遍历与假设推理的基础。

| 现状 | ✅ semantic_relations + 图遍历 API |
|---|---|

### 4.6 Metric：不要把指标当字段

这是 AI 问数系统最关键的设计。指标不应是 `sales_order.amount`，而应是：

```yaml
Metric:
  code: SALES_AMOUNT
  name: 销售额

  definition: 有效销售订单的含税销售金额

  formula: SUM(SalesOrder.tax_amount)

  grain: SalesOrderLine
  time_dimension: OrderDate

  default_filter: OrderStatus NOT IN [Cancelled]

  dimensions:
    - Customer
    - Product
    - Region
    - Organization
    - SalesPerson

  source: DWS_SALES

  quality:
    completeness: ">99%"
    freshness: "T+1"
```

AI 生成 SQL 时**必须**调用这个模型，不应自己猜字段。

| 现状 | ✅ KPI Catalog 已建（含 metric_pipeline 冷指标晋升）|
|---|---|

### 4.7 Dimension：定义"怎么切数据"

销售额可切维度：时间 / 区域 / 客户 / 产品 / 产品类别 / 销售组织 / 销售人员 / 工厂。

用户说"按区域看"→ `Dimension = Region`
用户说"TOP 10 客户"→ `Dimension = Customer, Order=DESC, Limit=10`

| 现状 | ✅ 已建 dimension 字典，与 Metric 关联 |
|---|---|

### 4.8 Semantic：解决"同词不同义"

企业里"销售额 / 销售收入 / 订单金额 / 含税销售额 / 不含税销售额 / 开票金额 / 回款金额"完全不是一回事。

Semantic Model 必须描述：

```
Term
Definition
Synonym
Anti-Synonym（明确 NOT synonym）
Business Meaning
Scope
Formula
Related Object / Metric / Rule
```

例如：

```
Term: 销售额
Synonyms: 销售收入 / 销售金额
NOT Synonyms: 回款金额 / 开票金额
Definition: 有效销售订单的含税金额
Related Metric: SALES_AMOUNT
```

| 现状 | ✅ TermDictionary 已落地（含同义词 + 例外规则）|
|---|---|

### 4.9 Business Rule：让 AI 知道企业规则

```
有效客户 = 客户状态='正常' AND 客户类型 != '内部客户'
有效订单 = 订单状态 NOT IN ['取消','关闭']
有效物料 = 状态='启用' AND 删除标识='N'
成品     = MaterialCategory = 'FG'
```

这些规则**不能全部依赖 LLM**，必须是**可执行规则**，由 Knowledge Compiler 注入到 SQL 生成。

| 现状 | ✅ Feature Rule 已建（DQ 规则 + 业务规则统一引擎）|
|---|---|

### 4.10 Knowledge Page：LLM Wiki 的核心

> Wiki 不是给员工看的文档，而是**给 AI 使用的企业知识基础设施**。

```
Knowledge Page
   ├── Entity（绑定的实体）
   ├── Concept（涉及概念）
   ├── Business Object
   ├── Process / Metric / Rule
   ├── Claim
   └── Evidence
```

例如：

```
《客户信用管理规则》
   Concept:     Customer Credit
   Claim 1:     客户信用等级分 A/B/C/D
   Claim 2:     C 级客户账期不得超过 30 天
   Claim 3:     D 级客户原则上禁止赊销
   Evidence:    《客户信用管理制度》v3.2
   Authority:   财务管理部
   Effective:   2026-01-01
```

| 现状 | 🟡 wiki_pages + wiki_category 已建；Claim/Evidence/Authority 字段 🟡 部分 |
|---|---|

### 4.11 Knowledge Claim：解决"AI 依据什么说"

不是「文本 → Embedding → LLM」，而是：

```
Knowledge
   ↓
Claim（结构化声明）
   ↓
Evidence（证据）
   ↓
Authority（权威）
   ↓
Version（版本）
   ↓
Validity（生效 / 失效）
```

例如：

```
Claim:   "客户 A 属于战略客户。"
Evidence:《2026 年度战略客户名单》
Authority: 销售管理部
Version:  2026-V1
Effective:2026-01-01
Expire:   2026-12-31
```

**每个 Claim 必须可追溯到 Evidence**，这是企业 AI 可信性的核心。

| 现状 | 🟡 通过 wiki_link 部分实现；独立 Claim/Evidence 表 ⚪ |
|---|---|

### 4.12 Evidence：把"数据"也变成证据

Evidence 不仅 PDF，至少包括：

```
Document         （PDF/Word/Excel/Markdown）
Database Query   （执行过的 SQL + 结果哈希）
API Result       （外部 API 响应）
Metric Result    （指标计算快照）
Transaction      （业务单据）
Business Event   （系统事件）
System Record    （系统日志）
Human Confirmation（人工确认）
```

例：

```
Claim: 华东销售额同比下降 5.3%
Evidence:
  E001: SQL Query（具体 SQL + 参数）
  E002: 2026 销售额 = 9.42 亿
  E003: 2025 销售额 = 9.95 亿
  E004: 计算公式 (9.42-9.95)/9.95 = -5.33%
```

AI 的每个重要结论 = **Claim → Evidence 链**。

| 现状 | 🟡 部分实现（wiki_link）；独立 Evidence 表 + 多类型支持 ⚪ |
|---|---|

### 4.13 Authority：解决知识冲突

企业一定会出现：

```
A 部门说法 vs B 部门说法
旧制度 vs 新制度
ERP 系统规则 vs 人工补充规则
```

Authority 定义**谁有权定义这个知识**：

```
财务指标        → 财务部
客户定义        → CRM 管理部门
物料定义        → 主数据管理部门
生产工艺        → 工艺部门
质量标准        → 质量部门
```

冲突消解优先级：

```
Claim
   ↓
Authority（权威部门）
   ↓
Priority（优先级）
   ↓
Effective Date（生效日期）
   ↓
Version（版本号）
   ↓
最终采纳的 Claim
```

| 现状 | ⚪ 待建 |
|---|---|

### 4.14 Knowledge Compiler：体系"编译器"

**作用**：把人类定义的企业知识，编译成 AI 可执行的东西。

输入：

```
Business Object / Metric / Dimension / Relation /
Business Rule / Knowledge Claim / Data Mapping
```

输出：

```
Semantic Graph
Vector Index
SQL Metadata
Query Template
API Definition
Agent Tool
Prompt Context
Validation Rule
Policy
```

工作过程：

```
Business Definition
   ↓
Semantic Model
   ↓
Validation（完整性 / 冲突检测）
   ↓
Compile
   ↓
┌─────────────────────────┐
│ Semantic Graph          │
│ Vector Index            │
│ SQL Metadata            │
│ Query Template          │
│ API Tool                │
│ Validation Rule         │
│ Agent Context           │
└─────────────────────────┘
```

例：Metric `销售额` 经编译后产出：

```
Semantic ID:    METRIC.SALES_AMOUNT
SQL:            SUM(dws_sales.sales_amount)
Dimensions:     Customer / Product / Region / Month
Permission:     Sales.Manager
Quality:        Completeness > 99%
Evidence:       DWS_SALES
Tool:           query_sales_amount(metric, dims, filters)
```

这样 Agent 不需要每次重理解整个企业。

| 现状 | ⚪ 待建（当前编译逻辑分散在 ontology_service / agent_tool_config_registry 等模块）|
|---|---|

## 五、L6 · AI Data Analyst（8 个 Agent）

不是一个超级 Agent，而是**分工明确的协作 Agent**：

```
Conversation Agent
Intent Agent
Semantic Agent
Analysis Planner
Query Agent
Result Agent
Hypothesis Agent
Evidence Agent
Report Agent
```

### 5.1 Conversation Agent

**职责**：上下文维护、对话状态、追问解析。

```
用户："今年销售额是多少？"
   → Metric = Sales Amount
   → Year = 2026

下一轮："去年呢？"
   → Metric 继承
   → Year = 2025

下一轮："华东呢？"
   → Metric / Comparison 继承
   → Region = 华东
```

| 现状 | 🟡 chat_context + chat_service 已支持 |
|---|---|

### 5.2 Intent Agent

**职责**：识别用户意图类型。

```
Query（查询）       Comparison（对比）     Trend（趋势）
Ranking（排名）     Anomaly（异常）        Analysis（分析）
Forecast（预测）    Root Cause（归因）      Report（报告）
```

```
"今年销售额是多少？"             → Intent = Query
"今年比去年下降多少？"           → Intent = Comparison
"为什么华东下降？"               → Intent = Root Cause
"帮我做销售经营分析报告"         → Intent = Report
```

| 现状 | 🟡 IntentType 枚举已定义 |
|---|---|

### 5.3 Semantic Agent

**职责**：把自然语言映射到企业语义模型。

```
"华东大客户销售下降情况"
   ↓
{
  "object": "Customer",
  "metric": "Sales Amount",
  "region": "华东",
  "customer_type": "大客户",
  "comparison": "YoY"
}
```

**这里不应该直接生成 SQL。**

| 现状 | 🟡 semantic_recall + plan_drop 已部分实现 |

### 5.4 Analysis Planner：核心 Agent

## 十二、可信性：贯穿全链的设计原则

> 企业用户最终关心的是**你这个答案到底是真的假的？**

最终答案不能只有"华东销售下降 5.3%"，必须能展开：

```
结论：     华东销售额同比下降 5.3%
数据依据： 2026 1-9 月 9.42 亿；2025 同期 9.95 亿
计算：     (9.42 - 9.95) / 9.95 = -5.33%
主要影响： 客户 A：-1,200 万；客户 B：-800 万；产品 X：-650 万
数据来源： DWS_SALES_MONTHLY
统计时间： 2026-01-01 ~ 2026-09-30
SQL:      （可展开查看）
参数：    （可展开查看）
```

### 12.1 三层证据链

```
1. 数据层证据：SQL Query + Result Hash
2. 业务层证据：Business Rule + Definition
3. 知识层证据：Document + Authority + Version
```

### 12.2 置信度计算

Confidence **不是模型感觉**，必须按证据规则计算：

```
Confidence =
   数据完整度（行数 / 时间覆盖）
 × 业务规则匹配度（默认 filter 应用情况）
 × 来源权威度（Authority 优先级）
 × 历史准确率（同类型问题过往表现）
```

### 12.3 数据质量反馈

AI 回答前必须检查：

```
数据是否更新？（Freshness）
数据是否完整？（Completeness）
是否存在异常？（Validity）
是否在可信范围内？（Accuracy）
```

数据未更新时，应主动声明：

> "当前销售数据最后更新时间为昨天 22:00，以下结果暂不包含今天新增订单。"

| 现状 | 🟡 DQ 评分已建；Confidence 计算 ⚪ |

## 二十五、最核心的一句话

如果把整个系统压缩成一句技术路线：

> **不是「Natural Language → SQL」，而是「Natural Language → Enterprise Semantic Model → Analytical Plan → Query Plan → SQL → Evidence → Insight → Report」。**

其中：

```
                       AI 智能问数 / 分析
                              │
            ┌─────────────────┴─────────────────┐
            ↓                                   ↓
    Enterprise Semantic                    Agent / LLM
            Layer                              Layer
            │                                   │
   Business Object                         Intent
   Metric                                   Planning
   Dimension                                Reasoning
   Relation                                 Analysis
   Business Rule                            Report
            │                                   │
            └─────────────────┬─────────────────┘
                              ↓
                     Data Query Engine
                              ↓
                 SQL / API / OLAP / Lakehouse
                              ↓
                       Evidence / Result
                              ↓
                  Analysis & Validation
                              ↓
                    Text / Table / Chart
                              ↓
                    AI Analysis Report
```

**下一步建议**：不要直接进入技术选型，而是先把这套体系进一步落成 **Enterprise Semantic Layer 元模型详细设计**。把 Business Object / 指标体系 / 统一业务语义 / LLM Wiki / Knowledge Claim / Evidence / 数据血缘 全部融合，形成 **Enterprise Semantic Layer + AI Data Analyst** 完整架构，再细化到数据库表、知识模型、Agent、Prompt、API 和前后端模块。
