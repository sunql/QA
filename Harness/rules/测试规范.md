# 测试规范

## 强制要求（CRITICAL，不可违反）

后端测试**全面禁止** sqlite 内存库（含 `sqlite+aiosqlite:///:memory:` 和任何 sqlite 变体），不允许作为任何测试的 DB 后端。

必须同时满足：
1. **真实 PostgreSQL**：测试连独立测试库（如 `qa_metadata_test`），表结构由 Alembic 迁移（`upgrade head`）产生，使用真实的表/列/索引/唯一约束/默认值。
2. **完整 API 链路**：经 FastAPI 测试客户端（`AsyncClient` + `ASGITransport`）从 HTTP 入口发起，走路由 -> 中间件（参数校验/鉴权/限流）-> service -> repository -> 真实 PG。
3. **真实数据库对象**：准备数据与断言都落在真实 PG 行上（ORM 或 SQL），禁止用 mock 实体替代被测数据层。
4. **禁止降级**：未配置 `TEST_DATABASE_URL` 时 fail-fast，不允许静默降级到 sqlite。任何测试文件内的 `sqlite` 字符串都是 bug，review 时必须拦截。

## 为什么（本仓库实踩的坑）

sqlite 与 PG 行为有实质差异，sqlite 通过不代表 PG 正确：

- **迁移失真**：`Base.metadata.create_all` 不走 Alembic，模型变更（加列/加约束/建索引）在 sqlite 上照常通过，上线后 PG 迁移失败或行为漂移。
- **方言差异**：JSON/数组等类型、`autoflush` 语义、唯一约束、并发锁在 sqlite 上不成立。实际事故：生产 `database.py` 设 `autoflush=False`，未 flush 直接按旧值批量删除，真实 PG 上误删 43 条属性，sqlite 测试完全发现不了。
- **绕过 API 契约**：直接调用 service 跳过路由层校验（ValidationError -> 422）、鉴权、限流、错误封套，测试绿但真实请求 4xx/5xx。
- **假对象失真**：mock 实体无法覆盖 PG 约束/触发器/默认值，形成"测试绿、线上坏"。

## 例外（仅限无 IO 的纯逻辑）

- 纯函数/纯算法（不触 DB/网络）：可直接单测，无需真实库。
- 外部依赖（LLM、Milvus、Neo4j、外部 HTTP）：允许 test double（mock/stub），但 **PostgreSQL 数据层必须真实**，不得用假库代替。

## 落地方式

- 测试库约定：独立测试库（默认 `qa_metadata_test`，可用 `TEST_DATABASE_URL` 指定）；凭据走环境变量注入，禁止硬编码（见 [权限与安全规范](./权限与安全规范.md)）。
- 运行要求：真实 PG 测试需提供 `TEST_DATABASE_URL`（或 `DATABASE_URL` 指向真实 PostgreSQL），未配置时 **fail-fast**，不允许静默降级 sqlite。示例：
  `TEST_DATABASE_URL=postgresql+asyncpg://<user>:<pass>@localhost:5432/qa_metadata_test uv run pytest app/tests/integration/`
- 统一接管：`app/tests/integration/conftest.py` 覆盖根 conftest 的 sqlite `client`/`dbSession`，integration 目录内所有测试自动走真实 PG + 完整 API 链路，无需逐文件重复（模块级同名 fixture 可继续局部覆盖）。支撑见 `app/tests/_pg_support.py`。
- 迁移：测试 fixture 先对测试库执行 Alembic `upgrade head`（与生产同路径，见 `app/tests/_pg_support.py`），禁止 `create_all`。
- 隔离：每个测试 TRUNCATE 清库（RESTART IDENTITY CASCADE），互不依赖执行顺序；每个测试新建引擎并在结束 dispose（pytest-asyncio 每测试独立事件循环，跨测试共享 asyncpg 连接池会报 loop 错配）。
- ⚠️ **目录分片稳定性（往 `integration/` 加文件前必读）**：CI 的 `backend-integration` job 用
  `find app/tests/integration -name 'test_*.py' | sort` 取清单，再按 **下标 mod 4** 切 4 个分片
  ⇒ 在 `integration/` **新增 / 删除 / 重命名任何一个文件**，其后所有文件的下标整体 +1、
  分片归属轮转一位 ⇒ 依赖「同分片内文件执行顺序」的既有测试会突然红。
  实测踩中过两类既有顺序依赖：① Milvus 逻辑库 `qa_ci` 由 `ensureIsolatedDatabase()` **惰性**创建
  （只由 3 个文件经 `milvusCleanClient` 触发），分片里一个创建者都没有 ⇒ `database not found[database=qa_ci]`；
  ② Neo4j 的 `neo4jCleanDriver` **只在 teardown 清图、不在 setup 清** ⇒ 首个用到它的用例会吃到
  同分片更早文件留下的 Class 节点残留（报 `expected 0 diff, got 3`）。
  ⇒ **处置顺序**：① 只读结构、不需要业务数据的用例优先放 `unit/`（本批
  `backend/app/tests/unit/test_orm_schema_ssot.py` 即为此）；② 确需放 `integration/` 时，
  先确认没有文件依赖同分片邻居的副作用；③ 注意 **`unit/` 与 `integration/` 的 autouse 夹具
  都会 TRUNCATE 共享测试库**（`unit/conftest.py` 的 `warmBusinessObjectRegistry` →
  `dbSession` → `seedEngine` → `_truncateAll`；`integration/conftest.py` 的 `warmAgentCaches`
  同构）⇒ 换目录**不能**规避「共享库被截断」这条隐患，要根治得给该文件一个不继承截断型
  autouse 的独立夹具作用域。
  详见 `Harness/changes/fix-schema-ssot-alignment/summary.md` §8.9。
- ✅ **`backend-unit` 已改「路径稳定哈希」分片（2026-11-02）**：`backend-unit` 原先把整个 unit 套件
  （320 文件 / 5446 用例 / 基线 **42 分钟**）塞进**一个** job、`timeout-minutes: 45` ⇒ 余量仅 ~7%
  ⇒ runner 抖动 10% 就判 **`cancelled`**；而 **`cancelled` 的 job 失败集合是空的**
  ⇒ 「失败集合对差」会得出「净新增 0」的**假结论**（PR #98 首轮 unit job 即如此被取消）。
  现改为 **4 个分片 job**（`strategy.matrix.shard: [0,1,2,3]`），分片归属由
  **`app/utils/ci_shard.py`（路径 sha256 哈希）**决定：**增删/重命名任何一个文件都不会移动其它文件的
  分片归属**（与 integration/ 的「下标 mod N」相反，后者会让其后所有文件轮转一位，见上一条）。
  - ⚠️ `fail-fast: false` **必须保留**：matrix 默认 `fail-fast: true`，一个分片失败会取消其余分片
    ⇒ 被取消分片的失败集合同样是空的 ⇒ 又一次假「净新增 0」。
  - ⚠️ 每个分片跑完会打印 **`UNIT_SHARD_DONE shard=N status=<pytest 退出码>`**：
    - **有标记且 `status ∈ {0, 1}`** ⇒ pytest 跑完了（`0` 真绿 / `1` 真红）⇒ 失败集合**可用**，正常参与对差；
    - **有标记但 `status ∉ {0, 1}`** ⇒ pytest **没跑完**（`2` 中断 / `3` 内部错误 / `4` 用法错误 /
      `5` 未收集到用例 / `128+N` 被信号杀死，`137`=SIGKILL、`143`=SIGTERM）⇒ 失败集合不可信 ⇒ **不可参与对差**；
    - **无标记** ⇒ job 没跑完（被取消 / 被抢占）⇒ 失败集合是空的 ⇒ **不能参与对差，必须复跑该 job**。
    （标记必须在 pytest 失败时**也**打印 ⇒ 否则「真红」与「被取消」都缺标记，判据失效。
    ⚠️ 反过来：**标记在、退出码异常**同样不可信 —— CI 脚本用 `|| status=$?` 捕获退出码，
    pytest 被 OOM killer 杀掉时 bash 报 `137`，标记照样打印 ⇒ 旧工具据此判「跑完了、真红、
    失败集合为空」⇒ 结论「可合并」⇒ **假绿通道**。）
  - ⚠️ **空分片必须硬失败**：pytest 不带路径参数时会回落到 `testpaths=["app/tests"]`
    ⇒ 把 unit+integration+e2e 全收进来，而本 job 只有 postgres 服务 ⇒ 报错+超时 ⇒ job 被取消
    ⇒ 又是假「净新增 0」。⇒ 分片清单生成器的退出码必须可捕获（**命令替换**，不能是进程替换）
    且清单为空时直接 `exit 1`。
  - ⚠️ 每个分片 job 各起一个 postgres service ⇒ **各有独立的库**，分片之间不会互相 TRUNCATE。
  - 守卫：`backend/app/tests/unit/test_ci_shard.py`（10 条用例，含 3 条变异取证）。
    详见 `Harness/changes/fix-ci-unit-sharding/summary.md`。
- ✅ **`backend-integration` 已补齐「假绿」防护（2026-11-02）**：分片归属**仍是**「下标 mod 4」
  （**刻意不改**——integration/ 确实有跨文件副作用，见上一条；换哈希会移动 241/314 个文件的归属，
  必须先根治 Milvus/Neo4j 副作用）。本批只补防护：
  - `timeout-minutes` 60 → **90**（实测最坏分片 49:48 ⇒ 旧上限余量仅 **1.21×**，
    runner 抖动 12% 就判 `cancelled` ⇒ 失败集合为空 ⇒ 假「净新增 0」）。
  - 每个分片跑完打印 **`INTEGRATION_SHARD_DONE shard=N status=<pytest 退出码>`**
    （语义与 `UNIT_SHARD_DONE` 相同：有标记且 `status ∈ {0,1}` = 跑完了；`status ∉ {0,1}`
    = pytest 没跑完；无标记 = job 被取消 ⇒ 三种都不可参与对差）。
  - 测试文件清单改用**落临时文件**（`find -print0 | sort -z` + `mapfile -d ''`）：
    ① 退出码经 **pipefail** 传播（进程替换的退出码会被 `mapfile` 吞掉）；
    ② **NUL 分隔** ⇒ 文件名里含空格/换行也不会被拆坏；
    ③ 空清单 / 空分片一律**硬失败**（否则空数组喂给 pytest ⇒ 回落到
    `testpaths=["app/tests"]` ⇒ 把 unit+integration+e2e 全收进来 ⇒ 超时 ⇒ 又一次假绿）。
  - **统一失败出口 `fail_shard`**：所有跑不到 pytest 的失败路径都**先打完成标记再退出**
    （`status=4` = 「pytest 没能正常跑起来」）⇒ 日志里能区分「跑完了但没跑成」（重跑即可）
    与「被取消」（要先解决超时/抢占）。
  - **`::error::` 消息体必须转义**（`%`→`%25`、`\r`→`%0D`、`\n`→`%0A`）：GH workflow 命令
    协议会吞掉这些字符 ⇒ 消息里带它们时日志里看不到真实原因。
  - **`mktemp` 失败也必须走统一出口**：裸 `list_file=$(mktemp)` 在 `set -e` 下会让脚本
    **直接退出而不打标记** ⇒ 工具判「无标记 = 被取消」⇒ 原因失真。
  - **分片号必须校验**：`SHARD` 走 env（不进脚本文本，避免 `${{ }}` 注入面），
    校验为**不超过 3 位的**十进制非负整数并用 `10#$SHARD` 强制十进制；`SHARD_COUNT` 走 env 且
    **必须等于 `matrix.shard` 的长度**（否则有分片永远轮不到、或切出空分片 ⇒ 假绿）。
  - 守卫：`backend/app/tests/unit/test_ci_integration_step.py`（**24 条用例**：14 条静态结构断言
    + 10 条**行为**断言；行为部分需要 bash ≥ 4.4 ⇒ macOS 本机跳过、CI 必跑）。
    行为断言把 YAML 里那段 `run:` **原样抽出来**在真 bash 里跑：清单生成失败 / 清单为空 /
    空分片 / 分片号非数字 / 分片号越界 / pytest 真红 / pytest 全绿 / 分片切分 /
    **文件名带空格原样传递** / **文件名带换行作为一个实参传递**。
  - ⚠️ **完成标记里的分片号必须用已校验的数值**（`$shard_index`，不是 `$SHARD`）：
    `SHARD` 来自 `matrix`，而 **workflow 文件本身 PR 可改** ⇒ `SHARD` 可能是任意文本
    （含换行 ⇒ 可在日志里伪造一行完成标记）；而工具的标记正则是 `shard=(\d+)`
    ⇒ 非数字会让标记**解析不出来**（⇒ 判「缺完成标记」⇒ 不可用 —— fail-closed，
    但真实原因「分片号非法」在日志里却像「被取消」）。
    ⇒ 脚本里 `shard_index=0` 占位，**校验通过后**才覆盖。
  - ⚠️ **换哈希分片的前置条件（未做，单独立项）**：① `integration/conftest.py` 加 session 级
    autouse 预建 Milvus `qa_ci` 逻辑库；② `neo4jCleanDriver` 在 `yield` **之前**也清一次；
    ③ 6 个模块在**导入期**调 `isNeo4jAvailable()`（早于 session 级 `isolateNeo4jEnv`）
    ⇒ CI 里恒 False ⇒ 整个模块被 skip ⇒ 唯一带 before+after 清图的
    `test_ontology_relation_graph_integration.py` **从不执行**。
- ✅ **`backend-unit` 已与 integration 同款硬化（2026-11-02）**：`backend-unit` 的失败路径
  原本**裸退出**（`echo "::error::…"; exit 1`）⇒ **不打完成标记** ⇒ 工具判「被取消」而非
  「跑完了但没跑成」⇒ 原因失真。现已补：
  - 统一失败出口 `fail_unit`：**先打 `UNIT_SHARD_DONE shard=$SHARD status=4` 再退出**；
  - `::error::` 消息体转义（`%` / `\r` / `\n`）；
  - `SHARD` 校验为不超过 3 位的十进制非负整数（`10#$SHARD` 强制十进制）。
- ✅ **CI 合并判据已工具化（2026-11-02）**：判据拆成 4 个模块 ——
  `ci_failure_set.py`（判据主逻辑）/ `ci_text.py`（净化 + 脱敏）/ `ci_gh.py`（gh 适配层）/
  `ci_surface.py`（CI 相关面判定）；守卫 `backend/app/tests/unit/test_ci_{failure_set,text,gh,surface}.py`
  + `test_ci_integration_step.py` 共 **113 条用例**，含 **12 组变异取证**（每组都实测转红）。
  把「失败集合对差、净新增为空才合并」做成可执行判据：
  ```bash
  cd backend && uv run python -m app.utils.ci_failure_set \
      --repo sunql/QA --base-run <基线 runId> --pr-run <PR runId> \
      [--allow-ci-changes]
  ```
  退出码：`0` 可合并 / `1` 净新增失败 / `2` 存在不可用 job / `3` 运行错误 /
  `4` 两次 run 的 job 集合不等价（覆盖不等价）/ `5` 净丢失失败待人工确认 /
  `6` **PR 改了 CI 相关面（或判定不出）⇒ 失败集合不可比**。
  ⚠️ **`cancelled` / `skipped` / 缺完成标记 / 结论与标记矛盾 / 标记族名或分片号对不上 /
  pytest 退出码 ∉ {0,1} / 真红却零失败明细 / 真红却没有 pytest 收尾汇总行 /
  日志里出现多于一条完成标记 / job 名含 unit·integration·shard 却不匹配协议**
  的 job 一律判为「不可用」——
  它们的失败集合是空的，**只要有任一个不可用，结论就不是「可合并」**（这正是「假净新增 0」的根因）。
  ⚠️ **报告里的外部文本（job 名 / 失败用例 ID / gh stderr）必须先净化再脱敏**：净化剔控制字符
  （防 CSI 序列擦掉已打印的「结论：可合并」行、防 OSC 52 改写剪贴板），脱敏打码凭据
  （token / 密码 / DSN / SAS 签名 URL）；脱敏**只在展示时**做，对差比较的是**原始**失败 ID。
  完整判据见 [开发流程规范.md](./开发流程规范.md)「CI 合并判据」一节。
- 断言：以 API 响应（状态码、封套、错误映射）为准，并校验数据真实落库；LLM / Milvus / Neo4j / 外部 HTTP 允许注入桩替换该依赖，其余链路全真实。
- 覆盖门禁：`pytest --cov=app --cov-fail-under=80`（见 `unit-test-ci` 技能）。
