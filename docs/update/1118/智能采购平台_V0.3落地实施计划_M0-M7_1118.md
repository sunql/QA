## 2. 里程碑划分准则（七条 —— 为什么这样划才可靠）

这七条不是通用项目管理套话，每一条都对应本项目已经真实踩过的坑。

### 准则 A：里程碑的完成定义里**必须包含「开关被打开并跑通」**
> **证据**：D1–D62 交付了 7 个阶段，**每一个的开关都默认关**，本地从未开过、生产从未开过。结果是「仓库 85–90% 完成」与「业务可用度 0」并存。
> ⇒ 规则：里程碑 M 的 DoD = **能力在本地开关打开状态下端到端跑通 + 证据归档**。「合入 main」不算完成。

### 准则 B：判据必须**量化 + 双向断言 + 可归档**，禁止「测试通过」这种描述
> **证据**：仓内假绿史——断言状态码即假绿、identity map GC 致单跑绿全文件红、库升级致守卫枚举空集通过、基线过期致 merge-gate 假 exit 5。
> ⇒ 规则：每条判据写成「数字 + 断言方向 + 证据文件路径」；负向用例必须与正向同等对待。

### 准则 C：**外部依赖在 M0 就发出**，真正阻塞只允许出现在 M6
> **证据**：V0.3 §13 的 5 项业务待确认至今零回复；KPI 口径 12/12 mismatch 卡了数月；ERP/SRM 接口未提供。
> ⇒ 规则：M0 结束前必须发出 4 份书面问卷并回收 ≥3 份。
>
> **准则 C 修正版（2026-11-18，复核后收紧措辞）**：回收不足**只顺延链尾，不整体重排**。
>
> | 回收 | 处置 |
> |---|---|
> | ≥ 3 份 | 按原计划走 |
> | 2 份 | **M5 / M6 不启动**（缺审批矩阵或写接口）；**M1 / M2 / M2′ / M3 / M4 照常推进**（只需"部分答案 + 降级"） |
> | ≤ 1 份 | 触发**整体重排**（关键路径被打断） |
>
> **理由**：M5/M6 是**链尾**（15–25 人日），顺延不影响 M0–M4 的 50–70 人日主线；原表述会让"少回收 1 份"⇒"全部重排"，代价与收益不成比例。
> ⇒ 配套的**并行轨**设计见 [`智能采购平台_V0.3落地实施计划_并行轨与汇合点_1118.md`](./智能采购平台_V0.3落地实施计划_并行轨与汇合点_1118.md)：**回收窗口不是等待期**，用 M0 工程量填满。

### 准则 D：里程碑之间**不得有「后补前置」**
> **证据**：D3 的四项裁决（快照自包含、绑定 vs 单源、KPI 两层、Manifest 改名）就是为了消除这类返工才产生的。
> ⇒ 规则：每个里程碑开工前跑「前置依赖检查表」（§3.1 定义，§4 逐里程碑列出），缺项不开工。

### 准则 E：每个里程碑**自带验收包 + 数据在标准库可复现**
> **证据**：P4 pilot 数据只在 `qa_metadata_test_pilot`，未进生产；「本地栈 = 孤儿栈」曾导致结论要绕道容器内调服务层。
> ⇒ 规则：验收包落在 `docs/update/1118/M{n}/`；测试数据必须在**标准测试库**（`qa_metadata_test_*`）可重建。

### 准则 F：每个里程碑 **≤ 10 个工作日**
> 理由：超过 10 天，问题会拖到里程碑末才暴露（这正是 D1–D62 横向分层的代价）。
> ⇒ 规则：超过 10 天必须拆；拆出的子片本身也是里程碑。

### 准则 G：每个里程碑**自带独立回滚动作，并在当周演练一次**
> 理由：仓库既有 3 个独立灰度开关的设计先例；发版推迟到最后，回滚能力必须提前验证过。
> ⇒ 规则：回滚演练记录进验收包。

### 准则 I（范围裁决）：**复用现有 API 家族，不新建 `procurement/*` API 家族**
> **证据**：`procurement_knowledge.py` 已是「薄别名、零业务分支」的形态，并由 AST 守卫（`test_knowledge_procurement_alias.py`）固化。
> ⇒ 规则：本体发布复用 `/api/v1/semantic/releases`；知识查询复用 `/api/v1/semantic/knowledge/query` + 采购别名；工作流复用 `/api/v1/workflow/*`。**只有 Copilot 入口与场景目录是 V0.3 真正的新 API。**

### 准则 J（架构原则）：**口径 / 规则 / 流程一律是「数据」，程序是「通用解释器」**

> **证据（2026-11-18 实测）**：
> - `backend/app/services/kpi_sql_compiler.py`（685 行）里 grep `KPI_` / `SUPPLIER_OTD` / `DWD_` / `不良率` = **0 命中**（唯一 `THBI` 出现在一个讲 schema 前缀的 docstring 里）。它只认 **6 个配置维度**：dialect(3) / metric_type(3) / agg(4) / joinType(2) / aggregation_order / grain_keys。
> - 口径的每个要素都是 `ontology_metric` 的**一个字段**：`numerator_measure` / `denominator_measure` / `aggregation_order` / `grain_keys` / `filter_expression` / `time_grain` / `time_column` / `formula` / `execution_source` / `status`。
> - 路由也是数据驱动的：`planKpiExecution` 只读 `execution_source`（`COMPILED` / `ESCAPE_HATCH` / `NONE`）+ 几个布尔判定，**不嗅探 formula 文本、不认识任何一条 KPI**。
> - 状态机 `kpi_status_machine.py`：`DRAFT → PUBLISHED → DRAFT`；发布闸门 `kpi_metric_publish_gate.py`；对账 `kpi_metric_reconcile.py`。
>
> ⇒ **规则**：**口径变更 = 数据变更，不是代码变更。**
> 改 `numerator_measure` → 走状态机 → 过发布闸门 → 对账 ⇒ **不发版、不重启、不改代码**。
> ⇒ 只有「**口径形态本身编译器表达不了**」（例如要新增一种比率聚合语义）才允许动 `kpi_sql_compiler.py`，且必须另开发版。
> ⇒ **禁止**为了让某个 KPI 跑通而往代码里加 KPI 名、表名、阈值常量——那正是准则 J 要防的退化。

#### ⚠️ 但「写死」确实存在——只是在**数据里**，不在代码里

`execution_source` 三个值的语义差别就是「口径是否配置化」：

| `execution_source` | 口径形态 | 改口径的成本 | 现状 |
|---|---|---|---|
| `COMPILED` | **结构化配置**（`agg` / `expr` / `filter` / `class_id`） | 改 JSON 字段，编译器重新生成 SQL ⇒ 多方言、可组合、fail-closed | **0 条** |
| `ESCAPE_HATCH` | **手写 SQL 文本**存在 `formula` 字段 | 改口径 = 人工改 SQL 文本 ⇒ **事实上的「写死」** | **8 条** |
| `NONE` | 没有技术口径 | 路由判 **Tier C** ⇒ **LLM 自己理解生成** | **4 条** |

⇒ 这解释了 turn-A 的现象（**「AIChatService 不用定义、自己理解」**）：
**不是代码不支持，而是配置没到位**——4 条 `NONE` 直接落 Tier C，8 条虽有 formula 但走手写 SQL 逃生舱，**通用编译器一条都没启用**。
⇒ **该做的是「把配置补齐 + 迁到 COMPILED + 走发布」，不是「写代码把口径固定下来」。**

## 6. 需要拍板的决策点

### D1 — 表命名裁决（准则 H）
是否确认「**不建** `procurement_ontology_release` / `procurement_workflow_*` / `procurement_business_command` / `procurement_approval_record` / `procurement_outbox_event`」，全部复用 `semantic_release` / `workflow_*` / `business_command` / `approval_task` / `workflow_outbox`？
- **建议：确认**。理由：避免双写双口径；`workflow_definition.domain_code` 已预留 `'procurement'`；`test_workflow_write_gate.py:695` 守卫也指向这个方向。
- 影响面：V0.3 §7.3 与附录 C 需要做一次「设计文档修订」。

### D2 — 源绑定表形态
`procurement_source_binding` + `procurement_property_binding` 两张表（属性级独立建模），还是**合并成一张 + `binding_role` JSON**（更省事，但复合属性/多源冲突表达弱）？
- **建议：两张**。理由：属性级绑定是 SQL 编译与 RAG 过滤的直接输入；`ontology_property.source_column` 单字符串表达不了多源/表达式/单位/转换。

### D3 — 规则版本化
新建 `procurement_rule_definition` + `procurement_rule_version`（V0.3 附录 C.2），还是扩展 `feature_rule` 加 `version` 字段？
- **建议：先扩展 `feature_rule`**，`procurement_rule_*` 延后到 M6 决策。理由：`feature_rule` 已有 evaluator + registry + 阈值表 + CRUD；新表会与它形成第二套规则语义。

### D4 — 询价发不发（决定 M5/M6 范围）
首期询价**只到草稿 + 审批**（不发外部），还是**必须打通发送**？
- 若「只到草稿」：M5 完整、M6 只需扩展场景 ⇒ 少 8–11 人日，且**不依赖 ERP/SRM**。
- 若「必须打通发送」：M5/M6 均依赖外部接口，**整体交付受外部阻塞**，且 Q07 无法在本地真正验收。
- **建议：默认「只到草稿」**（与 V0.3 §13「默认仅草稿」一致），把 ERP/SRM 发送作为独立的第二期。

### D5 — KPI 口径轨道的归属
M2′（KPI 口径，**剩余 9–16 人日**，代码已全合）并入本计划主线，还是作为独立工作包单独排期？
- **建议：并入**，但**排在 M2 验收之前**。理由：不并入则「指标类问题」永远验收不了，而指标是采购问答的核心价值。

## 8. 与「暂不部署」决策的关系

- 本计划**不安排任何生产发版窗口**；发版集中在 M7 之后，作为一次独立活动（迁移 0144→0152+新迁移链、镜像、开关、Worker）。
- 发版推迟的**代价**（要显式承担）：
  1. 生产与本地版本差持续拉大（已从 0140/0143 拉到 0143/0152）；期间生产不具备任何新能力。
  2. 生产「本体+指标+KPI 目录」子集与本地可能继续漂移（M0.1 与 M7 需各做一次对账）。
  3. 一次性迁移链更长（9+ 个迁移）⇒ 发版当天的回滚成本更高 ⇒ M7 的回滚演练必须覆盖「整链回退」。
  4. G3 那类「开闸前后不一致」的问题在本地暴露得更晚 ⇒ M0 必须先把闸门打开。
- 缓解：**M0 之后本地必须常态保持「开关全开」**，本地环境成为准生产。
