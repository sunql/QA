## 三、方案与取舍

### 3.1 四路统一输入 `RouteInput`（本批的结构性改动）

D33 的四路各有各的签名（`question` / `release` / `domainCode` / `topK`），**没有权限口径**。
RAG 路必须拿 scope（否则过滤无从谈起）⇒ 若继续加参数，四路签名会分叉成四种形状。

⇒ 本批引入 `services/knowledge/route_input.py`：

```python
@dataclass(frozen=True, slots=True)
class RouteInput:
    question: str
    domain_code: str
    release: ResolvedRelease
    scope: KnowledgeScope          # ← 必填：即便某一路今天用不上也必须收下
    top_k: int = DEFAULT_TOP_K
    session: Any = None
```

> **纪律**：`scope` 必填 ⇒ 「四路同一口径」不是靠约定，是靠**构造时必须给**。
> 四路全部改为 `async def runXRoute(inp: RouteInput) -> RouteOutcome`（协议同形 ⇒ 编排层只有一个调用点）。

代价：图谱路 / 指标路的 22 处单测调用点要改（各文件加一个本地 `_input(...)` 辅助函数）⇒ 一次性成本。

### 3.2 SQL 路：**复原层 + 渲染器**，不走 NL2SQL 闸门（裁决 9）

| 选项 | 结论 |
|---|---|
| `semantic_schema_gate.renderSchemaWithRelease`（计划原文） | ✗ 它的开关是 **NL2SQL 特性开关**（默认关 ⇒ 恒降级），且降级语义是「直读治理表」⇒ 知识服务一旦直读治理表，**引用就没有版本可引**（与 G5「引用可回溯」直接冲突） |
| 自己写一套快照 → schema 渲染 | ✗ 与 `nl2sql_schema` 的渲染口径会**漂移**（两套表 / 列写法 ⇒ 知识服务说的表名与 NL2SQL 说的对不上） |
| **`restoreSnapshotSchema`（P2 复原层）+ `buildSchemaText`（仓内唯一渲染器）** | ✅ 采纳：**按发布读是构造出来的**（不需要开关），且渲染口径与 NL2SQL 逐字一致 |

⇒ 计划里 SQL 路的接线方式**改写**（见 `plan.md` §3 裁决 9）。

召回口径：
1. **先切域**（`domain_slice`）⇒ 只有请求域的类参与；
2. **再匹配**（与图谱路**同一套**词项口径 `matching.classTerms`）⇒ 两路命中一致；
3. **只渲染命中候选类**（L-P4-5：全量 schema 文本是 NL2SQL prompt 的事）；
4. **只渲染两端都在子集内的 JOIN**（复原层已把子集外的端置 `None`）；
5. 证据：`TABLE`（类块，含表 / 列 / 类型）+ `JOIN`（`表A.列A = 表B.列B`），全部带 `releaseId` / `releaseVersion` / `source=RELEASE`。

### 3.3 RAG 路：先判开关，**不发起 embedding 调用**

P3a 的口径是「声明了作用域而收窄能力不可用 ⇒ fail-closed（拒绝）」。
本路**永远带作用域** ⇒ 开关关 ⇒ **降级**。

⚠️ 关键取舍：**在调 embedding 之前**判开关（C-4）。
若先调 embedding 再调闸门，则：
- 越权的向量**已经算过**（白花钱）；
- 闸门返回空结果时，调用方会误判成「模型没召回到」（静默零召回，排查成本极高，P3a 模块文档原话）。

⇒ 开关关 ⇒ `DEGRADED` + `degradedReason`，**零外部调用**（单测用「embedding 替身直接抛错」钉住这一点）。

过滤器四维**全部取自同一份** `KnowledgeScope` 与 `ResolvedRelease`：

| 维度 | 取值 |
|---|---|
| `domainCodes` | `(请求域,)`（请求域已在编排层校验过可见） |
| `orgCodes` | `scope.org_codes` |
| `entityTypes` | `scope.entity_types` |
| `releaseId` | `release.release_id` |

⇒ 「四路同一口径」在 RAG 路**可证**：过滤器对象本身就是证据。

### 3.4 编排层兜底：单路异常不许炸整轮

「四路均可单独返回」⇒ 任一路抛未预期异常时，该路降级（`degradedReason` 落原因），**其余三路照常返回**。

## 七、约定沉淀（避免下一批再踩）

1. **四路协议同形**：`async def runXRoute(inp: RouteInput) -> RouteOutcome` ⇒ 编排层只有一个调用点，
   新增第五路时只加一行注册。
2. **`scope` 必填**：`RouteInput` 里 `scope` 没有默认值 ⇒ 任何一路都**必须**拿到同一份权限口径。
3. **降级要「显式」**：能力不可用 ⇒ `DEGRADED` + 原因；**不许**回落成「更宽的答案」冒充「按权限过滤的答案」。
4. **开关判定要早**：能判开关就别先调模型 / 先调外部服务（P3a 的教训：静默零召回的排查成本极高）。
5. **渲染口径只留一份**：schema 文本一律走 `nl2sql_schema.buildSchemaText`；快照解析一律走
   `semantic_schema_adapter.restoreSnapshotSchema` ⇒ 知识服务与 NL2SQL 不会两套口径。
6. **计量不许伪造**：拿不到会话级计量行就**记日志 + 登记遗留**，不许写「0 token」的假账（L-P4-9）。
