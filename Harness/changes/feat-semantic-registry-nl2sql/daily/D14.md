## 1. 决断：为什么是 (b)，(a)/(c) 为什么否

D12 的 F4 列了三条出路，D14 拍板。**判据不是偏好，是「直读侧的顺序到底是不是契约」**：

| 出路 | 判定 | 依据 |
|---|---|---|
| (a) 治理表侧也按 `property_name` 排序 ⇒ 两侧逐字一致 | ❌ 否决 | 改的是**生产 prompt**（plan §2.3：P2 不动生产路径）；且「今天的行为」被改成「今天之后不再存在的行为」⇒ 失去可比基线 |
| (b) 内容等价 = 0 为零差异判据，列序差异单列计量并显式记录 | ✅ **采纳** | 前提「直读侧的顺序本身不是契约」——**实测成立**（下） |
| (c) 快照侧保留治理表列序（编译器按 id 排序） | ❌ 否决 | 违反跨环境字节确定性（记忆 `qa-system-semantic-manifest-determinism`） |

### 1.1 「直读侧的顺序不是契约」的三条实测依据

| # | 事实 | 位置 | 推论 |
|---|---|---|---|
| 1 | `OntologyClass.properties` 关系**没有 `order_by`** | `app/domain/models.py:283-287` | SQL 语义**不保证**列序。实测是堆物理序：`DWD_BOM` 的列序是 `BOM_DESCRIPTION, BASE_QTY, VALID_FROM, UPDATE_DATE, …`（既非 id 序也非字典序） |
| 2 | `listJoins` 按 `OntologyJoin.id` 排序 | `app/services/ontology_service.py:1281` | = **插入序** ⇒ 跨环境不同（dev 与 prod 的导入顺序不一样）⇒ 今天的 dev prompt 与生产 prompt 本来就可能不逐字一致 |
| 3 | `listClasses` 按 `class_name` 排序 | `app/services/ontology_service.py:457` | **只有类序是契约**，列序与 JOIN 序都不是 |

⇒ 追「快照侧与直读侧逐字一致」是在追一个**自己会漂**的目标。

### 1.2 定稿判据（三条，全部机检）

| # | 判据 | 口径 | 脚本实现 | 退出码 |
|---|---|---|---|---|
| 1 | **内容等价 = 0** | 逐**类块**比行多重集 | `_contentDiff` + `_blockContentMismatches` | > 0 ⇒ 1 |
| 2 | **归因缺口 = 0** | 块级内容不等价的块 **+** 顺序差异落在已知清单外的块 | `_orderAttribution` 的 `gaps` | > 0 ⇒ 1 |
| 3 | **块顺序差 = 0** | 块与块之间的先后差（=「哪个类先出现」变了） | `_blockHeaderOrderGap`（本日新增） | > 0 ⇒ 1 |

**「已知差异」清单是封闭的**（本日新增 `_orderAttribution` 自动分类，不写死块类型）：

- **类内列序**（类块内列与列的先后）；
- **JOIN 条目序**（`### JOIN 关系` / `### 间接 JOIN 路径参考` 段内条目与条目的先后）。

出现第三类 ⇒ 归因缺口 > 0 ⇒ 退出码 **1**（必须修），**不许**并进「已知差异 3」。
⇒ 退出码 3 的语义从此是**封闭**的：只有上面两类差异才可能拿到 3。

> ⛔ **封闭性不是靠「排除法」实现的**（自查发现并已修，见 §4.3）：
> 若按「不是 JOIN 段 ⇒ 类块」分类，任何**新段落**（如「关键过滤口径摘要」）
> 的顺序差异都能借「类块」的名义混进已知差异清单 ⇒ 第三类差异绕过退出码 1。
> ⇒ 现在的分类是**正面认类块**（类块标题恒带 `: table=`），
> 认不出的一律进**归因缺口**。失败方向是**安全**的：渲染器改了标题格式
> ⇒ 类块不再被认出 ⇒ 退出码 1（吵闹），而不是静默放行（安静）。

### 1.3 「快照侧类名集合 == 治理表侧类名集合（顺序亦一致）」的口径澄清

计划里的「顺序」指的是**渲染出来的块顺序**，不是 manifest 内部的类存放顺序：

- 复原层按**调用方的召回子集顺序**复原（`restoreSnapshotSchema` 保留 `classNames` 顺序）；
  manifest 内部的类顺序**到不了输出**（`test_semantic_schema_equivalence.py` 的
  `test_打乱manifest类顺序不改变类id映射` 已证 id 映射不受影响）。
- 故判据落成「**块顺序差 = 0**」，由脚本机检（本日新增）。

## 2. 顺序差异的**逐条**结论

### 2.1 类内列序（37 个类块）

| 项 | 实测 |
|---|---|
| 顺序变的类 | **37 / 37**（全部） |
| 涉及的列 | **3,267 / 3,267**（全部） |
| 单列最大位移 | **287 位** |
| 首列变了的类 | **36 / 37**（`DIM_FACILITY` 之外全部首列不同） |

**根因**：治理表侧 = 堆物理序（无 `ORDER BY`）；快照侧 = 编译器按 `propertyName` 排序
（`semantic_compiler.py:217`）⇒ 快照侧是**按名**的稳定序，物理行序在编译时已丢失且不可重建
（重建它要按 id 排 ⇒ 违反字节确定性）。

### 2.2 JOIN 条目序（1 个 JOIN 段）

| 项 | 实测 |
|---|---|
| 边数 | 16（两侧一致，集合相等） |
| 顺序 | 不同 |
| 根因 | 治理表侧 = `OntologyJoin.id` 序（插入序）；快照侧 = `joinKey` 排序（`semantic_compiler.py:287`） |

### 2.3 「间接 JOIN 路径参考」段：**不受影响**（逐块序同）

该段由 `_buildIndirectJoinHints` 产出，内部 `sorted(...)` ⇒ 与输入顺序无关 ⇒ 两侧逐字相同。
（实测：`PYTHONHASHSEED=0..4` 与随机种子下输出 md5 一致 ⇒ 无哈希随机化带来的抖动。）

## 3. 影响面评估（顺序差异会怎样影响线上）

| 面 | 结论 | 依据 |
|---|---|---|
| prompt 的**内容** | **不变** | 逐类块行集合相等 + 归因缺口 0（全集与逐类子集双证） |
| prompt 里**类的先后** | **不变** | 块顺序差 = 0 |
| prompt 里**列的先后** | **变**（37/37 类，3,267 列） | 见 §2.1 |
| prompt 里 **JOIN 条目的先后** | **变**（16 条边） | 见 §2.2 |
| **结果消费** | **不受影响** | 结果按**列名**消费（`chat_service.py:1714` `data = [dict(r) for r in result.rows]`），不按位置；`resultColumns` 取的是**生成 SQL 的** SELECT 顺序（`chat_usage.py:209`），不是 prompt 顺序 |
| **SQL Guard** | **不受影响** | 守卫看 SQL 文本，不看 prompt 里列的先后 |
| **模型选列** | **风险低，但不为零** | ① 实测**同类内没有任何 business_alias / property_alias 命中多列的歧义组**（0 组 / 0 类）⇒ 「同义列二选一」这条路走不通；② 但 36/37 类的**首列变了** ⇒ 注意力分配（primacy）可能改变选列 ⇒ 生成的 SELECT **列顺序**可能变（列集合不变） |

### 3.1 残余风险登记（不在 P2 修）

| # | 风险 | 缓解 |
|---|---|---|
| **R-1** | 模型因列序变化而选了**不同的列**（不是同义列，而是「问题里的词更像哪个列名」这一层） | D17 切换演练要**抽样比对切换前后的生成 SQL**：列**集合**必须一致（顺序可不同）。这是 D17 的验收项之一 |
| **R-2** | 直读侧的列序/ JOIN 序**本来就跨环境不同**（物理行序 + 插入序）⇒ 今天的 dev prompt 与生产 prompt 本来就不逐字一致 | 这是**既有事实被量化**，不是快照引入的新差异。⇒ 切换后 prompt 反而**更可复现**（按名排序 ⇒ 跨环境一致），这一点应写进切换说明 |

### 4.3 ⚠️ 自查发现并已修：归因分类的「排除法」漏洞

**评审状态说明**：本日的 `code-reviewer` / `security-reviewer` 子代理**因 API 配额 429 未跑成**
（`Request rejected (429) · 已达到 Token Plan 用量上限`），故本节是**自查**结论，
不是第三方评审结论。⇒ **D15 起应补跑一次双评审**（配额恢复后）。

**发现**：第一版 `_orderBlockKind` 用的是**排除法**——「不是 JOIN 段 ⇒ 一律类块」。
这个写法让「已知差异清单封闭」只成立于**当天这份数据**：任何**新段落**
（实测渲染器就有「关键过滤口径摘要」「间接 JOIN 路径参考」两段非类块段落）
的顺序差异，都能借「类块」的名义混进已知差异清单 ⇒ **第三类差异绕过退出码 1**。
今天的实测值不受影响（那两段本来就逐字相同），但**判据本身漏了**。

**修法**（先红后绿，变异取证见 §4.1）：

| | 修前 | 修后 |
|---|---|---|
| 类块怎么认 | 排除法（不是 JOIN 就是类块） | **正面认**：标题含 `: table=`（渲染器 `nl2sql_schema.py:317` 无条件追加） |
| JOIN 段 | `startswith("### JOIN")` | 前缀白名单 `("### JOIN 关系", "### 间接 JOIN 路径参考")` |
| 认不出的块 | 落到「类块」（**静默放行**） | 落到「其它」⇒ **进归因缺口 ⇒ 退出码 1**（吵闹） |
| 缺口的口径 | 只有「块级内容不一致」 | ① 块级内容不一致 **或** ② 顺序差异落在已知清单外 |

⇒ 失败方向是**安全**的：渲染器改了标题格式 ⇒ 类块认不出 ⇒ 退出码 1（要人看），
而不是把新差异静默归进「已知差异」（安静）。

**回归**：修后重跑 dev 5433 只读实测，三条判据的数值**全部不变**
（内容 0 / 缺口 0 / 块顺序 0；归因仍是 类块 37 + JOIN 段 1）⇒ 本次修复只改判据，
不改结论。基线夹具重抓 ⇒ **与仓库里的逐字节相同**（`cmp` 零差异）。
