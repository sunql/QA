以**《智能采购平台研发评估与设计冻结报告 V1.0》作为直接评估依据，现有 QA-System 源代码作为实际评估对象**，其他设计文档作为目标架构和技术要求的参照。

不是单独依据某一份技术方案，也不是重新做一遍通用系统架构评估。

## 一、评估依据及优先级

按照以下体系开展：

| 优先级 | 文件/资料                   | 主要用途                   |
| --- | ----------------------- | ---------------------- |
| 1   | 研发评估与设计冻结报告 V1.0        | 确定评估范围、评估维度、待解决问题和评估方法 |
| 2   | 智能采购平台总体架构设计 V0.2       | 确定未来平台目标架构和技术方向        |
| 3   | 智能采购平台详细设计 V0.3         | 确定模块、接口、数据库和业务流程要求     |
| 4   | 采购本体模型与语义编译器详细设计 V0.1   | 重点评估本体模块的升级可行性         |
| 5   | 配套 SQL、JSON 文件          | 核对数据库设计和 Manifest 技术契约 |
| 6   | 开发实施方案 V0.2、WBS Excel   | 评估开发任务、工作量和实施顺序        |


其中，前六项是设计依据，最后一项是技术事实依据。

如果设计文档与实际代码不一致，以实际代码为准，并将差异记录为评估发现，而不是为了符合设计文档而假设功能已经存在。

## 二、具体评估需要采用的方法

采用三个维度交叉评估：

第一维：现有系统实际能力

检查源代码、数据库模型、接口和运行机制。

- 已经实现什么？
    
- 实现到什么程度？
    
- 是否存在功能缺口？
    

第二维：智能采购平台目标要求

以总体架构和详细设计为目标标准。

- 需要具备什么能力？
    
- 现有能力是否满足？
    
- 哪些地方需要升级？
    

第三维：实际改造可行性

结合代码结构、技术依赖、数据结构和部署环境。

- 是否可以直接复用？
    
- 是否需要重构？
    
- 是否需要新增模块？
    
- 改造成本和技术风险多大？
    

## 三、评估报告重点检查的模块

分为九个专题：

|专题|重点检查内容|
|---|---|
|01. 总体技术架构|FastAPI、React、服务分层、依赖关系、扩展能力|
|02. 本体管理|Class、Property、Relation、Join、Metric、BusinessObject|
|03. 数据集成与映射|DataSource、EntityMapping、统一编码、数据同步|
|04. 知识图谱|Neo4j 本体图、业务图、关系白名单、查询性能|
|05. RAG 知识引擎|文档解析、Embedding、Milvus、检索、权限|
|06. NL2SQL 与语义查询|本体 Schema 注入、JOIN、指标消费、SQL Guard|
|07. Agent 运行平台|Agent Registry、Tool Registry、ACL、Worker、编排|
|08. 模型与规则服务|模型路由、成本管理、规则引擎、上下文管理|
|09. 部署与运维|PostgreSQL、Docker、Compose、镜像、数据备份、升级回滚|

## 四、每个模块最终形成什么评估结果？

统一使用以下评估表：

|评估项目|内容|
|---|---|
|现有代码位置|具体文件、类、方法|
|现有功能|当前真实实现的功能|
|技术实现分析|代码架构、调用关系、数据库依赖|
|目标要求|智能采购平台需要达到的能力|
|差距分析|现有实现与目标的差异|
|改造建议|保留、优化、重构或新增|
|改造影响|数据库、API、前端、部署|
|技术风险|兼容性、性能、安全、数据一致性|
|工作量估算|后端、前端、数据、测试分别估算|

最终将每个模块归入四种改造类型：

- A 类
    
    直接复用，不需要实质性修改。
    
- B 类
    
    在现有代码上扩展。
    
- C 类
    
    需要局部重构。
    
- D 类
    
    需要新增开发。
    

## 五、最终评估要输出的成果

形成三份正式交付物：

1. 《QA-System 现有代码与技术架构深入评估报告》：全面分析现有系统及升级差距。
    
2. 《智能采购平台现有功能复用与改造清单》：落实到具体代码文件、数据库表、API 和前端页面。
    
3. 《智能采购平台技术改造工作量评估表》：明确开发工作量、人员、周期和风险。
    

这三份成果完成后，再修订开发实施方案 V0.2，形成真正可以执行的开发计划。
