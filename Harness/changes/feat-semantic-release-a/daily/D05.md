## 设计要点

1. **纯核心 + 薄加载层**：`compileFromRows` 不碰数据库（单测直接构造行对象），
   `compileManifest(session)` 只负责三条 `select`。核心因此可单测、可对任意数据源复用。
2. **确定性**：类按 `className`、属性按 `propertyName`、JOIN 按 `joinKey` 稳定排序；
   每个字段**显式出现**（标量缺省 `null`，列表缺省 `[]`）。
   Manifest 里**不出现**自增 id / created_by / version / valid_* 这些依赖实例的残留列 ——
   换一个环境（测试库 / 生产）必须得到同样的字节。
3. **活跃模型语义**：`valid_to` 非空 = 软删除墓碑（Phase 6 移除版本管理后的约定）。
   墓碑类、其属性、以及**任一端点是墓碑**的 JOIN 全部过滤掉。
4. **悬空引用分两种**：
   - 指向**墓碑类**的 `refClassName` / `parentClassName` → 编译为 `null`（目标已不在模型中）；
   - 指向**完全不存在**的 `class_id` → 抛 `ValueError`（数据被写坏了，不能静默降级）。
5. **同名活跃类直接抛错**：`uq_ontology_class_name_version` 只约束 (name, version)，
   Phase 6 之后同名多行属异常 —— 抛错而不是「挑一行发布」。
6. **`isNotNull` 三态保真**：库列本身可空（`None` = 未约束，`False` = 明确允许为空），
   不能用 `bool()` 压平，否则「未约束」会被误发布成「允许为空」。

## 设计错误（RED 阶段发现并纠正）

初版用例把「JOIN 端点指向墓碑类」也判为必须抛 `ValueError`。真实 dev 库一查：
**18 个墓碑类、463 条墓碑属性、72 条端点已删的 JOIN** —— 若按初版语义，编译在真实数据上
永远失败。改为「墓碑相关行过滤 / 墓碑引用编译为 `null`，只有**不存在**的 id 才抛错」，
重写受影响用例与模块 docstring。
