# 数据库环境使用规范

## 强制要求（CRITICAL，不可违反）

本仓库存在**两个 PostgreSQL 库**，开发与测试必须按下列规则使用，禁止混用：

| 库名 | 用途 | 何时使用 |
|---|---|---|
| `qa_metadata` | **正式数据库**（prod 同源，含 35 万 entity_mapping 等真实业务数据） | **表结构修改 / 新增表 / 数据迁移类需求**：必须先用 prod `qa_metadata` 开发的全部流程 |
| `qa_metadata_test` | **单元 / 集成测试库**（手动建空库） | pytest 集成测试（`TEST_DATABASE_URL` 必须显式指向它，详见 `测试规范.md`） |

## 默认规则

1. **涉及「表结构修改」或「新增表」的开发需求**：必须直接使用 prod `qa_metadata` 进行开发。
2. **执行任何 alembic upgrade / 表 DDL / 数据 INSERT|UPDATE|DELETE 之前**：必须先**备份受影响的表**。
3. **备份表命名约定**：`<原表名>_<YYYYMMDD>`（日期戳用本地日历日，例如 `organizations_20260908`）。
4. 备份完毕后即可在 prod `qa_metadata` 上跑迁移 / 改数据，不再回退到 `qa_metadata_test`。

## 为什么（本仓库实踩的坑）

- **两库 schema 漂移**：`qa_metadata_test` 与 prod `qa_metadata` 表结构可能不一致（Alembic 迁移未同步、初始数据缺失、列默认值差异），在 test 库跑通的迁移上线 prod 直接炸。
- **丢失真实业务数据特征**：prod 有 35 万 entity_mapping 等规模数据，PG 行为（执行计划、约束并发、索引选择）在 test 库空数据上不可复现，迁移可行性论证不足。
- **回滚盲区**：用户改 prod 数据的决策路径与改 test 数据的决策路径完全不同，在 test 库做的 DDL 演习与 prod 真实效果可能差异巨大；备份 + 直接改 prod 路径让决策证据更强。
- **典型事故**：`feat-org-tree` (commit 0046) 涉及 `organizations` 表加 `sort_order` 列 + 复合索引，直接 prod 跑 alembic upgrade + 一次 POST/PUT 冒烟覆盖全路径，避免了 test 库跑通的索引在 prod 命中行为差异。

## 备份操作流程（标准动作）

每次涉及 prod `qa_metadata` 的表结构 / 数据变更前：

```bash
# 1. 确认 prod 库连接（不要连错库）
docker exec qa-postgres psql -U qa_user -d qa_metadata -c "\dt" | grep -E "<待改表名>"

# 2. 备份表（DDL 含结构 + 数据）
docker exec qa-postgres pg_dump -U qa_user -d qa_metadata -t <table> > /tmp/<table>_<YYYYMMDD>.sql
# 或者纯数据备份（带结构备份给「我重置用」）：
docker exec qa-postgres pg_dump -U qa_user -d qa_metadata --table=<table> --no-owner > /tmp/<table>_<YYYYMMDD>.sql

# 3. 在 prod 上做迁移 / DDL
docker exec qa-backend bash -lc 'cd /app && alembic upgrade head'   # 或对应 SQL
# 或
docker exec qa-postgres psql -U qa_user -d qa_metadata -c "ALTER TABLE ..."

# 4. 冒烟：跑对应 API + 验证
curl -s -H "X-User-Id: admin" http://localhost:8000/api/v1/<endpoint> | jq .

# 5. 若 prod 改 DDL 且回归需要，把 schema 同步到 qa_metadata_test
TEST_DATABASE_URL=postgresql+asyncpg://qa_user:qa_pg_dev_2026@localhost:5433/qa_metadata_test \
  .venv/bin/alembic upgrade head
```

## 后端集成测试

测试仍走 `qa_metadata_test`，但 **schema 必须与 prod 当前 head 同步**（每次 alembic 升级后跑一次 `TEST_DATABASE_URL=... alembic upgrade head`）。详见 `测试规范.md`。

## 例外

- 纯算法 /纯计算 /前端组件单测：不触 DB，无需走 prod / test 任一库。
- 用户明确说「这次走 test 库」时：以用户指令为准，并在 commit / PR 描述里说明。

## 反模式（review 时拦截）

- ❌ 涉及表结构变更却在 `qa_metadata_test` 跑 alembic / DDL 后声称「验证通过」
- ❌ 在 prod `qa_metadata` 上执行 DDL / 数据迁移却没先 `pg_dump` 备份
- ❌ 把「在 test 库跑通了」当作 prod 上线的充要条件
- ❌ 备份表名没用日期后缀，导致多次备份互相覆盖、无法区分
- ❌ 「prod 怕炸所以我在 test 库先试一下」——按本规范，这种 reasoning 是禁止的，prod 该用就用，先备份
