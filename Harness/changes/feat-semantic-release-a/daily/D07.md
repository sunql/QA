## Schema 设计要点

1. **三道闸**：结构（JSON Schema draft 2020-12）→ 引用完整性（Schema 表达不了的跨分区约束）→ 哈希。
   编译器在输入侧已校验一遍，产物侧再校验一遍 —— **回放历史快照时不会再经过编译器**，
   这是第二遍存在的唯一理由。
2. **全链路 `additionalProperties: false`**：拼错的键被静默忽略是发布评审最不该有的失败模式。
   顶层、每个分区元素、度量对象、source 对象都关死。
3. **`required` = 全部键**：编译器对每个字段都显式产出（标量缺省 `null`、列表缺省 `[]`），
   所以「键必须齐」是准确约束。少字段 = 编译器被改坏，不该放行。
4. **枚举取自真实枚举类**（`app/domain/enums.py`）：`metricType` / `aggregationOrder` /
   `executionSource` / `metric.status` / `source.role` / `kpi.status` / `objectType`。
   实测取值分布：`WEIGHTED_RATIO`8 / `NONE`3 / `AVG_OF_RATIOS`1；`ESCAPE_HATCH`8 / `NONE`4；
   `Master`7 / `Transaction`8 / 空 39。**`joinType` / `relationType` 不做枚举约束** ——
   库侧是自由字符串（INNER / foreign_key），没有 Python 枚举作 SSOT，凭空冻结会误伤。
5. **`schemaVersion` 用 `const`**：只接受 v1。Schema 演进（加字段/加枚举值/改类型）必须 +1，
   旧快照按自身 `schemaVersion` 选 Schema，绝不偷偷放宽。
6. **哈希**：`json.dumps(sort_keys=True, ensure_ascii=False, separators=(",",":"), allow_nan=False)`
   → SHA-256。`allow_nan=False` 不是洁癖：NaN/Infinity 不是合法 JSON，放过去会让其他语言算不出同一个哈希。
7. **ORM 默认值守卫**：`test_release_orm_default_schema_version_matches` 断言
   `semantic_release.schema_version` 的 `server_default` 等于 `SCHEMA_VERSION`。
   迁移 0142 写死了 `'v1'`；将来 Schema +1 时这条先红，逼着做明确决定。

## 修正的 D6 缺陷（本日发现）

D6 的用例与 golden 用的是**自造取值**，不是治理表的真实形状。三处：

| 字段 | D6 写的 | 真实值 | 后果 |
|---|---|---|---|
| `metric.numeratorMeasure` | `{class, column, agg}` | `{agg, expr, filter, class_id, class_alias}` | D7 Schema 会拒；且**自增 `class_id` 被整份入档** |
| `metric.executionSource` | `ORACLE` | `ESCAPE_HATCH` / `NONE` / `COMPILED` | 非法枚举值 |
| `class.objectType` | `ENTITY` | `Master` / `Transaction` / `Reference` / `Event` | 非法枚举值 |
| `metric.aggregationOrder` | `DIVIDE_AFTER_AGGREGATE` | `WEIGHTED_RATIO` / `AVG_OF_RATIOS` / `NONE` | 非法枚举值 |

**`class_id` 泄漏是最严重的一条**：D5 设计要点 2 明写「Manifest 里不出现自增 id」，
但度量定义把 `class_id` 整份抄了进去 —— 同一份治理内容在两个环境编译出的字节不同，
回放快照时还会解析到新环境里的另一张表。修正为 `resolveMeasure`：`class_id` → `className`
（规则同 `refClassName`：墓碑类 → `null`，不存在的 id → 抛错），`class_alias` → `classAlias`，
返回**新字典**（不原地改 ORM 行上的 JSON）。

修正后真实库快照 `sha256 = d66d38ba14933466482b12f3c8ddbeac41e0bda80474f7d0914fd1f3a16fa791`，
`class_id` 出现次数 = 0（旧值 `0444e6fb…` 已作废）。

## 治理数据缺口（阻断 D9 发布闸门的输入，需业务/DBA）

D6 已记录「18 条 `ontology_metric_source` 里 15 条指向墓碑类 ⇒ 9/12 指标无源」。
本日归一化度量后发现**同源问题更严重**：

| 指标 | numeratorMeasure.className | denominatorMeasure.className |
|---|---|---|
| KPI_SUPPLIER_OTD 供应商准时交付率 | null（DWD_GOODS_RECEIPT_LINE 已删） | null（DWD_PURCHASE_ORDER_LINE 已删） |
| KPI_SUPPLIER_OVERDUE_RATIO 供应商逾期率 | null | null |
| KPI_PAYMENT_ON_TIME 付款及时率 | null（DWD_SUPPLIER_PAYMENT 已删） | null |
| KPI_INVOICE_MATCH_RATE 发票三单匹配率 | null（DWD_PURCHASE_INVOICE_LINE 已删） | null（DWD_PURCHASE_INVOICE 已删） |

即 **8/8 条结构化度量全部指向已被软删的 DWD 类**（18 个墓碑类中的 5 个）。
`executionSource` 仍为 `ESCAPE_HATCH`（formula 是可执行 SQL），所以运行期还能跑；
但「结构化轨道」在活跃模型里没有任何可解析的落点。

**给 D9 发布闸门的要求**（判据按指标状态分级 —— 快照如实收录 DRAFT 指标是 D6 的既定裁决，
闸门只对「已发布」的指标做硬拒绝）：
1. 指标 `sources` 为空 → 发布预览显式告警；
2. `status=PUBLISHED` 的 RATIO/DIFFERENCE 指标，分子/分母度量 `className` 为 null →
   **拒绝发布**（没有落点的比率不可执行）；`status=DRAFT` 的同型问题 ⇒ 仅告警。

当前 12 条指标全部是 `DRAFT`，所以首个快照不会被上述第 2 条卡住；但评审预览必须
把 8 条无落点指标与 9 条无源指标列出来，否则等于把治理债悄悄发布出去。

数据修复方向与 DW 本体重绑同源：把度量里的 `class_id` 指向活跃类（或重跑回填脚本）。
