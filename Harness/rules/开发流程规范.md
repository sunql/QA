# 开发流程规范

## 10 阶段工作流

每个特性/变更依次走以下阶段，结果沉淀到 `changes/<feature>/summary.md`。

1. **需求分析**：用 `request-analysis` 技能拆解需求，明确验收标准。
2. **专家评审**（可选）：复杂决策用 `expert-reviewer` 多视角评审。
3. **设计**：确定数据模型、接口契约、算法。更新对应 `wiki/`。
4. **测试先行（RED）**：先写失败测试，覆盖正常/边界/异常路径；数据层必须真实 PG + 完整 API 链路（见 [测试规范](./测试规范.md)）。
5. **实现（GREEN）**：最小实现让测试通过。
6. **重构（IMPROVE）**：在不破坏测试前提下优化结构。
7. **代码审查**：用 `code-review` 技能 + `python-reviewer`/`security-reviewer` 审查。
8. **覆盖率验证**：`pytest --cov=app --cov-fail-under=80` 与前端 `vitest run --coverage`。
9. **部署验证**：用 `deploy-verify` 技能跑 Docker Compose 冒烟，并先过「数据库迁移同步（部署门禁）」校验。
10. **记录变更**：在 `changes/<feature>/summary.md` 写 SSOT，更新 `wiki/` 与进度。

### 第 10 阶段 SSOT 强约束（部署阻塞项）

详见 [变更记录强制规范](./变更记录强制规范.md)。每个特性 / Bug fix / 重构合并前必填 5 条：

1. `Harness/changes/<feature>/summary.md` 9 段齐（不允许 TBD/TODO 占位）
2. 至少 1 个跨文件链接（关联变更 / wiki / rules 三选一）
3. 至少 1 条 MEMORY 索引（`~/.claude/projects/.../memory/<slug>.md` + MEMORY.md 加 1 行）
4. 相关 wiki 文档已更新（数据模型 / 接口 / 架构 / 前端 至少 1 处）
5. 涉及真实 SQL/DB 改动时 `scripts/<feature>_realdata.py` 跑通

**判定时机**：code-review 阶段 reviewer 必查，缺任一项打回。历史 SSOT 漏档走 `log-YYYYMMDD.md` 补救流程（见变更记录强制规范 §五）。

## 数据库迁移同步（部署门禁）

**事故教训**（2026-08-30）：data-quality 特性集成测试全绿，但 live 库 `alembic_version`
停在 `0016_ontology_join`，0017/0018/0019 从未应用 → 前端打开数据质量页
`GET /api/v1/data-quality/rules` 直接 500（`UndefinedTableError`：表不存在）。
**测试库迁移到位 ≠ 运行环境迁移到位**。docker compose 部署时容器启动会自动
`alembic upgrade head`，但本地/非容器化 DB（如本地 `qa_metadata` 5433）不会，
必须手工补跑。

**规则**：

1. 数据模型变更（新增/修改表）必须对**每个目标环境**执行 `alembic upgrade head`
   （测试库 + live/生产库），不允许只在一个环境应用。
2. 部署前必查：各环境 `SELECT version_num FROM alembic_version` 必须等于当前 head
   revision；环境之间迁移版本不一致即为**部署阻塞项**，先补齐再冒烟。
3. 新增表/列对应的接口，上线前必须对目标环境**冒烟**（curl 新端点返回非 5xx）；
   不能只依赖集成测试——集成测试连的是迁移齐全的测试库，覆盖不到 live 缺表场景。
4. 迁移脚本的部署验证段落写进 `changes/<feature>/summary.md` §8，并把新表/新端点的
   冒烟项追加到 `deploy-verify` 技能。

**二次复发 (2026-08-30 下午)**：feat-governance-hardening 合入后，`kpi_catalog` /
`entity_mapping` 在 live 库又缺表（落后 5 条迁移：0021-0025），前端报 500/404。
本次额外暴露两个加速排错的隐患：

- **本机 PG 端口不是 5432 而是 5433**：`docker-compose.yml` 把 Postgres 映射成
  `5433:5432`（避宿主 5432 OpenMetadata 占用）。连 5432 = ConnectionRefused。
  所有 `DATABASE_URL` / `TEST_DATABASE_URL` 一律 5433。
  详见 `Harness/wiki/operations-runbook.md`「迁移与端口映射」段。
- **陈旧 uvicorn 进程可能掩盖新端点注册失败**：本次一个 PID 34319 的旧 uvicorn
  早于 `kpi_catalog.router` 启动，导致 `/kpi-catalog` 报 404，让人误以为路由缺失；
  实际是进程没重启。重启 backend 后必须 `curl /openapi.json | jq '.paths | keys'`
  确认目标路由存在，再开始排查。

## 每轮真实数据验证（开发门禁）

**事故教训**（2026-08-30）：data-quality 特性单测 + 集成测试全绿（mock adapter +
fake rows + 真实 PG 5433 测试库），但**真实业务数据库**执行 SQL 时炸出 3 个
真实 bug，mock 测试 100% 漏检：

| Bug | 模拟测试 | 真实数据 |
|---|---|---|
| `_EXPR_RE` 正则拒绝 PG 双引号大小写敏感标识符（如 `"ORDERQTY" > 0`） | 测试用 `_`/`数字` 标识符假数据，永远走 `_IDENT_RE` 单 token 分支 | PG 表用大写列名 + 子查询必须双引号 → 校验直接拒 |
| 表达式消息缺特殊字符白名单提示（`"` 字符） | 测试用 `_`/数字/算术，无双引号场景 | 真实 SQL 必须含双引号才能命中 PG case-sensitive 表/列 |
| PostgreSQL 大小写折叠：unquoted → 全小写、quoted → 保留大小写 | 测试用 lowercase 数据，折叠前后等价 | Sage X3 / WMS 业务表都是大写命名 → 必须显式 `CREATE TABLE "PORDER"` 强制 quoted |

**根因**：单元/集成测试只覆盖「写好的代码路径」，覆盖不到「真实数据库方言 /
真实业务命名约定 / 真实数据分布 / 真实 SQL 计划器」。Mock 永远是「我以为它会
怎么跑」，真实数据是「它实际怎么跑」。

**规则**：

1. **每个特性完成后、写 change summary §8 前**，必须用**系统真实可用的数据**
   跑一遍端到端验证：
   - 业务数据库：当前环境的真实业务库（无 demo 数据时，可在本机 metadata DB
     临时建业务 schema + 真实业务表灌含缺陷的真实风格数据；不允许 `sqlite`、
     `monkeypatch`、纯 mock adapter 顶替）。
   - LLM 调用：若特性涉及模型路由/embedding/chat，至少跑一次真实调用并贴
     token 计量与响应片段到 change summary。
   - 第三方组件（Neo4j/Milvus/Redis）：特性涉及则真实跑一遍，至少一条写 + 一条
     读，贴日志。
2. **真实数据验证脚本**与 `scripts/seed_*.py` 同级，命名 `scripts/<feature>_realdata.py`，
   幂等 + 含缺陷样本（故意制造覆盖各种失败路径），用于：
   - 复现业务典型场景（真实命名、真实数据量级、真实 schema 命名约定）
   - 暴露 mock 漏掉的方言/特性差异
   - 给 reviewer 与运维一个「我可以自己跑一遍」的可重现入口
3. **真实数据验证输出**写进 `changes/<feature>/summary.md` 新增 §9「真实数据验证
   报告」：跑了哪些真实链路、贴关键 curl 输出 / 关键 SQL / 关键分数 / token 计量 /
   发现并修复的真实 bug 列表。无此节即视为**该 change 未通过门禁**。
4. **真实数据发现的问题**必须在合并前修复（包括补丁单测覆盖该真实场景，避免回归）；
   若因环境限制暂时绕到，必须在 §9 写明绕过的理由 + 后续整改计划。
5. **测试覆盖率的豁免**：`sqlite` 内存库 + mock-only 测试覆盖率达 80% **不构成**
   本节合规；覆盖率必须以**真实 DB + 真实 SQL** 的测试用例为主。

## 人工介入点（HITL）

- 安全敏感变更（认证、密钥、SQL Guard）必须人工确认后合并。
- 数据模型变更（新增/修改表）必须人工审查迁移脚本。
- 路由策略/成本阈值调整必须人工确认。

## 审查上限

- 单次审查发现 CRITICAL 必须修复后才能继续。
- HIGH 应在合并前修复。
- MEDIUM/LOW 记录为 TODO。

## 提交规范

- Conventional Commits：`feat:` / `fix:` / `refactor:` / `docs:` / `test:` / `chore:` / `perf:` / `ci:`
- 关闭 Attribution（全局已禁用）。

## 前端变更部署（必走 `docker compose build`）

**事故教训**（feat-user-auth，2026-09-20）：前端改动后 4 次「重建」都只在**本地沙箱**
跑 `cd frontend && npm run build`，把 `frontend/dist/` 写进**宿主机文件系统**——
容器内 nginx serve 的 `/usr/share/nginx/html` 来自**镜像构建时** `COPY --from=build /app/dist`，
**从未被刷新**。用户每次 hard refresh 看到的还是几天前 `docker compose build` bake
进去的旧 bundle（hash 比如 `index-BMm9puG4.js`），前端代码改动对用户**完全不可见**，
反复误导「明明代码改了为什么浏览器还报错」。本地 `frontend/dist/index-r3i6ixut.js`
与 nginx 服务的 bundle 是**两份完全不同的文件**，用「本地 build 是否通过」判断
「前端是否生效」是**错的心智模型**。

**规则**：

1. **任何**前端代码 / `.env` 里 `VITE_*` 变量改动后，部署命令必须包含镜像重建步骤：
   ```bash
   docker compose -f docker/docker-compose.yml build --no-cache frontend
   docker compose -f docker/docker-compose.yml up -d frontend
   ```
   不允许用 `docker cp frontend/dist qa-frontend:/usr/share/nginx/html` 临时覆盖
   （重建容器即回退；属于「看起来生效了」的反模式，详见 `fix-nginx-upstream-stale-ip`
   §3 的同类教训）。**也不允许**只跑 `cd frontend && npm run build` 后声称「前端已重建」。

2. **VITE_API_BASE_URL 默认指向 nginx 5173，不是 backend 8000**：
   - `docker/.env` 里 `VITE_API_BASE_URL=http://localhost:5173/api/v1`（走 nginx 反代）
   - 不写 `http://localhost:8000/api/v1`（绕过 nginx 直连 backend）。后者在 nginx
     剥离客户端伪造头（feat-user-auth §nginx）的策略下完全失效；axios baseURL
     直连 8000 时 nginx 拦截与 `X-User-*` 头过滤都不起作用。
   - `VITE_*` 是**构建期烘焙**进 bundle 的（不是运行时），改 `.env` 后必须重建镜像。

3. **诊断命令**（任何「前端已改但用户看不到」先跑这三步）：
   ```bash
   # (a) 容器里 dist/ 实际的 bundle hash
   docker exec qa-frontend ls /usr/share/nginx/html/assets/ | grep index-.*\.js

   # (b) 宿主机本地 dist/ 的 bundle hash
   ls frontend/dist/assets/ | grep index-.*\.js

   # (c) nginx serve 出去的入口 HTML 引用的 hash
   curl -s http://localhost:5173/ | grep -oE 'index-[A-Za-z0-9_-]+\.js'
   ```
   三个 hash 必须**完全一致**。(a) ≠ (c) 即镜像未重建；(b) ≠ (c) 即本地 build 未进
   容器；(a) = (c) 但浏览器 console 还看到旧 hash 即浏览器 / 代理缓存（少见，nginx
   `index.html` 已 `Cache-Control: no-cache`，通常硬刷即可）。

4. **`docker compose up -d frontend` 不重建镜像**：它只重启现有容器，原镜像层不变。
   「改完前端只跑 `up -d` 不生效」是同类事故的高频陷阱，必须 `build --no-cache` 再 `up -d`。

5. **后端变更也适用同规则**：后端代码改动后必须 `docker compose build --no-cache backend && up -d backend`；
   单纯 `docker cp backend/app qa-backend:/app/app` 是临时覆盖（详见 memory
   `qa-system-docker-cp-merge`），重建容器即回退，且 cp 容易漏 alembic 迁移导致 uvicorn
   起不来。

**与其他规则的关联**：
- 与 [变更记录强制规范 §5 真实数据验证](./变更记录强制规范.md) 互补——真实数据验证
  跑通 ≠ 用户能看到新前端行为，部署是另一道门。
- 与 [数据备份策略](./数据备份策略.md) 互补——前端部署不破坏数据，但 nginx
  `dist/` 与本地 `dist/` 错位会让所有前端回归测试失去意义。
- 与 `fix-nginx-upstream-stale-ip`（容器重建后 nginx 缓存旧 backend IP）属同一类
  「容器/IP/bundle 状态漂移」教训，共用诊断流程。
