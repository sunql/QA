# 变更记录强制规范（SSOT）

> 解决「特性开发完，变更记录没补，半年后回看已忘记为什么这么改」的问题。
>

>

> - 当初为什么用 JSONB 整块存 snapshot 而不是拆 `evaluation_report_metric` 表？

>

## 一、强约束（部署阻塞项）

每个特性 / 变更 / Bug fix 合并到共享分支（main / develop）**之前**，必须满足以下 5 条：

| # | 必填项 | 形式 | 不满足的后果 |
|---|--------|------|--------------|
| 1 | `Harness/changes/<feature>/summary.md` | 按 `_template/summary.md` 9 段填齐 | 部署阻塞；不允许「合并后补」 |
| 2 | 至少 1 个跨文件链接 | summary 关联变更 / wiki / rules 三选一 | 同上 |
| 3 | 至少 1 条 MEMORY 索引 | `~/.claude/projects/.../memory/<slug>.md` + MEMORY.md 加 1 行 | 同上 |
| 4 | 相关 wiki 文档已更新 | `Harness/wiki/*.md` 对应章节补齐（数据模型 / 接口 / 架构 / 前端） | 同上 |
| 5 | 真实数据验证脚本可跑（参考 [开发流程规范 §真实数据验证](./开发流程规范.md#每轮真实数据验证开发门禁)） | `scripts/<feature>_realdata.py` 幂等且能复现 | 涉及真实 SQL/DB 改动时阻塞 |

> **判定时机**：code-review 阶段 reviewer 必查，缺任一项打回并要求补齐再合。

## 二、summary.md 必填 9 段

照搬 `_template/summary.md` 模板的 9 段，**不允许出现 `TBD / TODO / 待补` 占位**：

1. **需求**：背景 + 验收标准（用户视角、可测量）
2. **设计评审**：≥ 2 个候选方案对比 + 取舍 + 最终决定（避免「只有一个方案」的伪设计）
3. **数据模型变更**：新增 / 修改 / 删除的表 / 列 / 索引 / CheckConstraint；迁移文件名（含 ≤ 32 字符校验）
4. **接口契约变更**：新增 / 修改 / 删除的 API、DTO 字段、状态机
5. **实现要点**：关键文件路径 + 算法 + 依赖注入点
6. **测试**：新增测试用例名 + 覆盖率结果（≥ 80%）
7. **安全审查**：是否触发 security-reviewer + 结果（CRITICAL/HIGH/MEDIUM/LOW）
8. **部署验证**：docker compose 冒烟结果 + 真实数据验证脚本输出
9. **关联**：设计稿 + wiki 路径 + rules 路径 + MEMORY 路径

### frontmatter 必填元数据

```markdown
# 变更：<feature-name>

- **日期**：YYYY-MM-DD
- **作者**：Claude / <姓名>
- **Phase**：Phase X.Y <模块名>
- **状态**：draft / in-review / done / superseded
- **关联变更**：[feat-xxx](../feat-xxx/summary.md)（如有 predecessor / successor）
- **迁移版本**：0069_xxx, 0074_xxx（如有）
- **MEMORY**：[../../../../../.claude/projects/.../memory/<slug>.md](...)
```

`状态` 字段的语义：

- `draft` — 草稿（不允许合）
- `in-review` — 评审中（code-review 通过后会切 `done`）
- `done` — 已合并到主分支
- `superseded` — 已被新变更替代（保留供追溯；summary 内必须指出由谁替代）

## 三、特性 / Bug fix / 重构 的 SSOT 差异

| 类型 | 必填段 | 可省略段 |
|------|--------|----------|
| 特性（feat） | 全部 9 段 | 无 |
| Bug fix（fix） | 1/2/3/4/6/7/8/9（可省设计评审 → 写「根因 + 修复方案」） | 设计评审（如为简单 fix） |
| 重构（refactor） | 1/2/5/6/9（接口契约无变化可省 4） | 数据模型变更、接口契约变更、部署验证 |

## 五、SSOT 补档流程（事后补救）

如果发现历史特性漏写了 SSOT，**不允许直接补档到原位置**。流程：

1. 在 `Harness/changes/log-YYYYMMDD.md` 写明发现 + 补救清单
2. 给每个漏档特性创建 `Harness/changes/feat-<name>/summary.md`
3. summary 顶部 metadata 加 `状态：done（事后补档）` + 在「关联变更」段引用 `log-YYYYMMDD.md`
4. 同步更新相关 wiki 文档 + MEMORY 索引
5. 在该日 log 末尾写明补档完成

> 2026-09-15 的 Phase 8/9 早期补档是首次走此流程，参考 `changes/log-20260915.md`。

## 六、自动化校验（后续）

未来可在 CI 加一个 `scripts/check_ssot.py`，扫所有 `Harness/changes/feat-*/summary.md`：

- frontmatter 元数据齐全
- 9 段都非空
- `关联变更` / `MEMORY` / `迁移版本` 字段对应的文件存在
- 引用的 wiki 路径存在

校验失败 → CI 红 → 不允许合。本期先人工 reviewer 把关，后续 PR 提上。
