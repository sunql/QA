## 0 · 摘要

**G3 第 2 条「切换前后回放结果一致」当前 ❌**（2026-11-15 裁决：**不改代码、如实登记**）。
生产打开 `ENABLE_SEMANTIC_REGISTRY_NL2SQL` 的前置条件是：
① **答案级影子评估**；② **「是否统一渲染顺序」二次拍板**。

**本文件交付这两件事**：

| 交付 | 内容 | 章节 |
|---|---|---|
| **修复方案** | 把差异**根除**（不是评估、不是容忍）：让直读侧与快照侧**渲染出逐字节相同的 schema 文本** ⇒ 开关切换对 prompt 变成**恒等变换** | §3 |
| **答案级评估口径** | 即使差异根除，也必须有一套**可复现、可归档**的评估来证明"开闸不影响答案" | §4 |

**核心结论（一句话）**：G3 之所以不过，是因为**渲染顺序在两条路径上不同**，而**模型对行序敏感**。修顺序是治本；评估是治标 + 兜底。**两者都要，但顺序上先做评估、再做修复**——因为修复会一次性改变今天关态的 prompt 与回答，这个影响必须**先被量化**才敢动。

### 1.1 已验证的事实链

| # | 事实 | 证据 |
|---|---|---|
| F1 | 两态 schema 文本**内容等价**：602 / 602 行，按块行多重集**差异块 0** | D17 §4 判据 1 |

| F5 | 快照侧顺序由 **manifest 显式排序**决定（字节确定性）；直读侧**没有对应排序** | `semantic_compiler.py:137/217/287` |

### 1.2 已排除的猜想（**不要重复排查**）

| 猜想 | 排除理由 |
|---|---|
| 「快照丢了事实」 | F1：内容差异块 0 |
| 「模型随机」 | F2：同态抖动 = 0 |
| 「类顺序不同」 | `_topoSortByInheritance`（`nl2sql_schema.py:561`）**已按 `(class_name, id)` 排序**⇒ 两态类序一致 |
| 「JOIN 条目内容不同」 | F1：块行多重集一致 |
| 「守卫链差异」 | G3 判据 3 ✅：两态 SQL 都过 `_assert_read_only` + `findShareDenominatorIssues` |

### 1.3 真正的差异：**只有两个轴**

`buildSchemaText`（`backend/app/services/nl2sql_schema.py:262`）里有两处**直接遍历输入顺序**、**不做排序**：

| # | 位置 | 代码 | 直读侧（OFF）顺序 | 快照侧（ON）顺序 | manifest 侧的排序键 |
|---|---|---|---|---|---|
| **轴 1** | `nl2sql_schema.py:318` | `for prop in cls.properties:` | ORM `selectin` 的**物理行序**（`domain/models.py:283`，**无 `order_by`**） | manifest 序 | `propertyName`（`semantic_compiler.py:217`） |
| **轴 2** | `nl2sql_schema.py:369` → `_renderJoinLines` 的 `for join in joins:` | 渲染 `### JOIN 关系` 块 | 调用方传入的 **ORM 物理行序** | manifest 序 | `joinKey`（`semantic_compiler.py:287`） |

> **轴 1 的额外严重性**：`ontology_class.properties` 是 `lazy="selectin"` 且**没有 `order_by`** ⇒ 直读侧的属性序**连"自己和自己一致"都不保证**（PG 无 `ORDER BY` 的返回序随物理布局 / 更新历史变化）。**这不只是"与快照不一致"，而是"直读侧本身非确定性"。**

## 2 · 三个候选方案

| | 方案 A：快照侧改回直读顺序 | 方案 B：**两侧统一到 manifest 顺序** | 方案 C：只评估、不改顺序 |
|---|---|---|---|
| 做法 | 让快照按物理行序渲染 | 让**直读侧**按 `propertyName` / `joinKey` 排序 | 保持现状，用评估量化影响并接受 |
| G3 第 2 条 | ❌ 仍不过（只是把差异反向） | ✅ **结构性通过**（两侧逐字节相同 ⇒ prompt 恒等） | ❌ 仍不过（差异依旧） |
| 破坏的契约 | ❌ 破坏 **D16 钉住重放**（`Test顺序确定性` 钉死"顺序由 manifest 决定"；改后同一版发布在不同机器/时间渲染不同） | ⚠️ 破坏 **D15「关 = 逐字节等于今天」**（今天的关态 prompt 会变） | 不破坏任何契约 |
| 副作用 | 直读侧**仍非确定性**（轴 1 的病根未除） | ✅ **顺带修掉直读侧非确定性** | ⚠️ 直读侧继续非确定性 ⇒ **今天就可能偶发** |
| 额外代价 | — | 需独立发版 + 答案级评估量化影响 | 每次开闸都要接受"答案会变" |
| 结论 | **否决**（2026-11-15 已否决，本文件复核确认） | **推荐** | **不推荐**（治标不治本，且把不确定性留到生产） |

## 3 · 方案 B 详述（推荐）

### 3.1 改动点：**3 处，纯函数，零 schema 变更**

> **原则**：排序发生在**渲染时**，不改 ORM 关系、不改查询、不改 manifest 格式。
> **理由**：改 ORM `relationship(order_by=...)` 会影响全仓所有读该关系的代码（面太大）；改查询会引入新的排序来源（更容易漂移）。**渲染时排序是影响面最小、语义最清晰的位置。**

| # | 文件 / 位置 | 改动 | 排序键来源 |
|---|---|---|---|
| **C1** | `nl2sql_schema.py:318` `for prop in cls.properties:` | 改为 `for prop in _sortedProperties(cls.properties):` | `property_name`，**升序、Unicode 码位序** |
| **C2** | `nl2sql_schema.py:369` `if joins:` → `_renderJoinLines(classes, joins, safePrefix)` | 改为传入**已排序**的 joins | `join_key`，**升序** |
| **C3** | 新增共享排序原语 | **放在 `semantic_manifest_common.py`**（与编译器共用，**不复制实现**）⇒ `sortBy(items, key=...)` 已是共享原语，只需把**键的定义**也共享 | — |

**关键纪律（对齐已记录的教训）**：
- 排序键**必须与编译器用同一个表达式**（`propertyName` / `joinKey`），否则两侧还是不一致 ⇒ **禁止在渲染侧重新推导键**；
- 排序键缺失时**必须有确定的兜底**（例如 `join_key` 为 `None` ⇒ 排到末尾并按 `(source_class_id, target_class_id, str(columns))` 兜底），**不得**因缺键而抛错——渲染路径不能因为排序失败而挂；
- 排序**必须是稳定排序**（相同键保持输入相对序），避免引入新的不确定性。

### 3.2 为什么必须"两侧统一"，而不是"只修快照"

一句话：**开闸的意义是让生产用上「可钉住、可复现」的发布语义**。若两侧顺序不同，则：
- 开闸后，**同一份发布**在不同机器/不同时间渲染出的 prompt 可能不同（直读侧非确定性，轴 1）⇒ **钉住重放塌掉**；
- 关闸与开闸**答案不同** ⇒ 用户会感知到"开了个开关，答案就变了" ⇒ 不可接受。

⇒ 方案 B 同时解决：**开闸无影响**（两侧恒等）+ **钉住可复现**（两侧都确定）。

### 3.3 影响面与风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **今天的关态答案会变** | 顺序变了 ⇒ 模型输出可能变（D17 已证模型对行序敏感） | **必须先做 §4 答案级评估**量化幅度；发版作为**独立一次**，前后各留一份评估对照 |
| 其他依赖 `cls.properties` 顺序的代码 | 本次**不改 ORM 关系**，只改渲染器 ⇒ 依赖关系的代码不受影响 | `grep -rn "\.properties" backend/app` 复核；单测覆盖 |
| 排序键为空的行 | `property_name` DB NOT NULL ⇒ 安全；`join_key` 可能有空 | 兜底排序 + 单测钉住 |
| 大 schema 的 prompt 长度 | 排序不改变行数与内容 ⇒ 长度不变 | — |

### 3.4 D15 契约「关 = 逐字节等于今天」怎么处理

D15 是 **P1b 那一批**的交付契约（"关态必须与上线前逐字节相同"）。方案 B **必然违反它**。处理方式：

1. **不在 P1b/P2 的分支上做** —— 方案 B 属于 **M0 的独立发版**，自带一次"契约变更"记录；
2. **变更记录里显式写明**：契约从「关 = 逐字节等于今天（2026-11-XX 之前）」改为「关 = 逐字节等于**排序统一后的今天**」，并附**变更前后两份评估对照**；
3. **回滚路径**：方案 B 是纯渲染逻辑改动 ⇒ 回滚 = 还原 3 处代码 ⇒ **无 DDL、无数据迁移、无配置**⇒ 回滚成本极低（判据 7）。

### 3.5 发版策略

| 步骤 | 内容 |
|---|---|
| S1 | 建 `feat/m0-g3-render-order` 分支；实现 C1/C2/C3 + 单测（排序键、稳定性、兜底、与编译器键一致） |
| S2 | **先跑 §4 的答案级评估**（在**改动前**的 OFF 态与**改动后**的 OFF 态之间对比）⇒ 得到"顺序变化本身对答案的影响幅度" |
| S3 | 跑 §4 的评估（改动后的 OFF vs ON）⇒ 两侧应**逐字节相同** ⇒ 差异必然为 0 ⇒ G3 第 2 条结构性通过 |
| S4 | 合并 → 独立发版（**不与其他批次混发**） |
| S5 | 发版后重跑一次评估作为**生产侧基线** |

> **S2 与 S3 的区别很重要**：S2 量化的是"**顺序变化对答案的影响**"（这是方案 B 的真实风险）；S3 证明的是"**开关切换对答案无影响**"（这是开闸的安全性）。**两者不能互相替代。**

## 4 · 答案级评估口径（**本文件的核心交付**）

### 4.1 为什么必须是"答案级"

D17 的做法是比 **SQL 文本**——这已经比"schema 文本"进了一步，但**仍然不够**：

- SQL 文本不同 ≠ 答案不同（换别名、换写法，结果一样）；
- SQL 文本相同 ≠ 答案一定相同（数据在变、执行环境在变）；
- 而**真正要保护的是用户的答案**。

⇒ 评估的**主对象是答案**；SQL 文本只是**定位差异原因**的中间量。

同时，**不能只比答案**：模型会输出措辞差异（"约为 92%" vs "92.3%"），纯文本比对会把噪声当信号。⇒ 必须**分层**。

### 4.2 评估对象

| 项 | 定义 |
|---|---|
| **被评估的问题集** | 固定版本号的业务问题集（§4.6），来自问卷 D 的真实问题 |
| **两个态** | OFF（`ENABLE_SEMANTIC_REGISTRY_NL2SQL=false`，直读）/ ON（`true`，走快照） |
| **同态对照** | 每个态**各跑 2 遍**，得到该态的**抖动基线**（§4.4） |
| **评估产物** | 逐题对照表 + 汇总报告（§4.8） |

### 4.3 五个差异层次（L1 → L5）

> **判定顺序：自上而下。L3 一旦不一致，**不再往下比**（因为"查的东西不一样"时，比数值没有意义）。**

| 层 | 比什么 | 怎么比 | 归一化规则 | 允许差异 |
|---|---|---|---|---|
| **L1 · SQL 文本** | 生成的 SQL | 规范化后逐字比 | 空白折叠、去表别名前缀差异（`A.`/`B.` 任意命名）、大小写统一、去尾分号 | 允许（**仅作定位**，不判失败） |
| **L2 · 结果集** | 查询返回的行 | **行序无关**的多重集比较（排序后逐行比） | 数值列按容差比（§4.5）；浮点统一 6 位小数 | 允许（除非触及 L3/L4） |
| **L3 · 口径覆盖** | 查询**包含了哪些过滤/关联谓词** | 抽取 SQL 中的 WHERE 谓词 / JOIN 条件，**归一化为集合**后求差集 | 谓词文本归一（去括号空白、统一 `=`/`IN` 写法、列名去表别名前缀） | **不允许（硬红线）** |
| **L4 · 数值等价** | 答案里的关键数字 | 数值提取后按容差比 | 金额容差 0.01 元；比率容差 0.1 个百分点；天数/计数**精确相等** | 见 §4.5 |
| **L5 · 答案等价** | 最终给用户的结论 | 人工评审 + 结构化要素比对（结论 / 依据条数 / 关键值 / 限定条件） | — | 见 §4.5 |

> **L3 是这套口径的核心**。D17 实测到的正是 L3 级差异：**ON 丢了 `DIM_IMATERIAL` 的 JOIN 与 `ENAFLG_0 = 2` / `TCLCOD_0 IN (...)` 两条口径**。这类差异"看起来只是 SQL 写法不同"，实际上**查的是不同的数据** ⇒ 必须判红。

**L3 的量化**：
```
口径覆盖差异率 = |OFF 谓词集 Δ ON 谓词集| / |OFF 谓词集 ∪ ON 谓词集|
```
**硬红线：口径覆盖差异率 = 0**（不是"足够小"，是**零**）。

### 4.4 同态抖动基线（**把"模型随机"从"真差异"里剥出来**）

| 步骤 | 做法 | 产出 |
|---|---|---|
| B1 | OFF 态跑 **2 遍**（同问题集、同环境、同数据快照） | OFF 的 L1/L2/L3/L4/L5 **同态差异集** |
| B2 | ON 态跑 **2 遍** | ON 的同态差异集 |
| B3 | 计算 | **抖动基线 J** = 两态同态差异的**并集规模**（按层分别记） |

**判定规则**：
- 若 **J > 0**（同态本身就不一致）⇒ 抖动粒度 **大于**判据 ⇒ 本轮评估**不可判定**（退出码 `6`，与 D17 一致），**必须先降抖动**（固定温度/seed/数据快照）再评；
- 只有当 OFF/ON 的差异**严格大于 J**时，才算**真差异**；
- D17 实测同态**逐字相同** ⇒ **J = 0** ⇒ 任何 OFF/ON 差异都是真差异（**这是本次评估最省事的前提，必须先复验**）。

> **纪律**：**不得**用"OFF/ON 差异率 < 5% 就算过"这类阈值。阈值会把 L3 的口径丢失稀释掉。**L3 = 0 是硬红线。**

### 4.5 通过线

| 层 | 通过线 |
|---|---|
| L1 | 不判失败（仅定位用） |
| L2 | 结果集不一致的题目数 **= 0**（除非该题已在"允许答不出来"清单里） |
| **L3** | **口径覆盖差异率 = 0**（硬红线） |
| L4 | 关键数值不一致的题目数 **= 0**；比率/金额容差见上 |
| **L5** | 答案等价率 **≥ 95%**，且**「绝对不能答错」清单**（问卷 D 的 D2.4）内题目等价率 **= 100%** |

**总体结论**：
- **全过** ⇒ 允许把 `ENABLE_SEMANTIC_REGISTRY_NL2SQL` 纳入生产开闸清单；
- **L3 有差异** ⇒ **不允许开闸**（无论 L4/L5 看起来多接近）；
- **L1/L2 有差异但 L3/L4/L5 全过** ⇒ 可开闸，但**必须在变更记录里登记差异清单**（说明差异不影响答案）。

> **与落地计划 DoD 的关系（避免两处口径打架）**
> 落地计划 M0 的 DoD 第 2 条写的是「同一问在开关开/关两态下**答案一致（逐字）**」。
> 本节给的是**分层**判定，两者不冲突，关系是：
>
> | | 计划 DoD 的「逐字」 | 本节的分层判定 |
> |---|---|---|
> | 定位 | **最严**的一档，是**目标态** | **执行态**：把"逐字"拆成可客观测的 L1–L5 |
> | 用途 | 方案 B + 固定 seed 达成后即可宣告满足 | 定位差异在哪一层，避免把措辞噪声当信号 |
> | 硬红线 | — | **L3 = 0、L4 = 0**（客观、可自动化） |
>
> ⇒ **执行顺序**：先做方案 B（两侧 schema 逐字节相同）⇒ 固定 seed ⇒ 逐字一致**通常可达成** ⇒ 同时满足计划 DoD；
> 若逐字未达成而 L3/L4 全过，**按分层判定放行**，但必须在报告里写明"逐字未达成、差异层级为 L1/L2、不影响答案"。

### 4.6 问题集规范

| 要求 | 规定 |
|---|---|
| **来源** | 问卷 D 的真实问题（20–30 条）；附录 B 的 Q01–Q07 作为**最低集** |
| **版本化** | `questions.json` 带 `version` + `sha256`；**改了就是新版本**，评估报告必须写版本号 |
| **覆盖面** | 必须覆盖 5 类：供应关系 / 指标统计 / 风险合规 / 制度规则 / 价格对比；**每类 ≥ 2 题** |
| **含负例** | ≥ 3 题是**边界题**（问未接入的数据域 / 越权数据）⇒ 断言系统**明确说"未接入/无权限"**，**不是编一个数** |
| **不造数** | 问题必须打在**真实数据**上；数据快照须固定（评估期间冻结数据变更） |
| **可复现** | 问题 + 数据快照标识 + 两态配置 + 模型档位，**全部入库** |

### 4.7 执行流程

```
① 冻结数据快照 + 固定模型档位（记录 endpoint / model / 温度 / seed）
② OFF 态：跑 2 遍 → 产出 OFF-1 / OFF-2
③ ON  态：跑 2 遍 → 产出 ON-1 / ON-2
④ 计算同态抖动基线 J（按层）
   └─ J > 0 ⇒ 退出码 6「不可判定」，先降抖动
⑤ 跨态比对（OFF vs ON）→ 逐层差异集
⑥ 判定：L3 = 0 ？ L2/L4 = 0 ？ L5 ≥ 95% ？
⑦ 产出报告 + 归档
```

**工具**：复用 `backend/scripts/diag_semantic_switchover.py` 的两态回放与退出码契约（0/2/3/4/5/6），**扩展**为答案级评估脚本 `backend/scripts/eval_semantic_answer_parity.py`（**新增，不改**现有脚本，避免影响已归档证据的可复现性）。

| 退出码 | 含义 |
|---|---|
| `0` | 全部通过 |
| `2` | 两态 schema **内容**不等价（快照丢了事实）⇒ **前置故障**，不是评估结论 |
| `3` | 跨态**答案**不一致且超过抖动基线 ⇒ **不通过** |
| `4` | 前置条件不满足 / 执行异常 |
| `5` | SQL Guard 链失效 |
| `6` | **不可判定**（同态抖动 J > 0 / SQL 不可解析 / 某态产不出 SQL） |

> **与 D17 退出码的对齐**：D17 的 `3` 是"跨态回放确定性不一致"（SQL 层），新脚本的 `3` 是"跨态答案不一致"（答案层）。**两者互补**：D17 保证"机制层确定"，本脚本保证"结果层等价"。

### 4.9 模型档位与**不可外推声明**（**必读**）

D17 演练用的是**本地 27B**（Qwen3.8-27B-4bit），**不是生产 DeepSeek**。因此：

| 档位 | 作用 |
|---|---|
| **本地档**（27B） | 证**机制**（顺序变化会不会导致答案变化） |
| **生产档**（DeepSeek） | 证**幅度**（生产上会差多少） |

**纪律**：
- 本地档的结论**不得**直接外推为"生产也安全"；
- **开闸前必须在生产档复跑一次**（可在生产的**影子/只读**模式下跑，**不落库、不对外**）；
- 报告里**必须写明档位**，且**禁止**把"本地档通过"写成"已通过"。

### 4.10 失败处置

| 失败类型 | 处置 |
|---|---|
| L3 差异 > 0 | **不开闸**。走方案 B（§3）⇒ 顺序统一 ⇒ 复评 |
| L5 差异但 L3/L4 等价 | 可开闸；**登记差异清单**；若差异集中在措辞，可评估是否需要 prompt 侧归一（**另立项**，不在 M0.4） |
| J > 0（抖动） | 先降抖动（固定 seed/温度、冻结数据）；**不得**用"跑 3 次取多数"糊弄 |
| 某态产不出 SQL | 走 §5 的降级路径（见下） |
