## 1. 需求

**背景**：开发 / 测试访问数据库（prod `qa_metadata`、`qa_metadata_test`、Oracle 业务库等）时，若**首次连接密码错误**，按既有习惯会反复重试（最多见过一段脚本无封顶重试 20+ 次）。

**风险**：
1. 部分数据库 / 认证代理在**连续密码错误 5~10 次后会锁定账号 / 触发风控**。无封顶重试 = 把生产账号打挂，恢复流程比修一次密码长得多。
2. 密码错误是**确定信号**而非网络抖动，盲目重试不会改变凭证有效性，只放大事故。
3. 无策略 ⇒ 不同开发者行为不一致 ⇒ 事故复盘时无法定责。

**验收标准**：
- 任何手工命令 / 自动化脚本访问 DB 时，密码错误**最多重试 5 次**（含首次）。
- 第 6 次连接尝试必须中止，整理错误给用户，**询问如何处理**。
- 不得用 sleep / backoff / "最后再试一次"绕过。
- 写入 `Harness/rules/数据库环境使用规范.md` 新增"数据库密码失败策略"段 + 反模式列表 + 标准动作模板。

## 5. 实现要点

**关键文件**：`Harness/rules/数据库环境使用规范.md`

新增"数据库密码失败策略（CRITICAL，强制执行）"段，含：
- 触发场景判定（典型信号枚举：`password authentication failed for user` / `ORA-01017` / `Access denied for user` / SQLAlchemy `OperationalError` 含 password）
- 4 条强制规则（5 次封顶 / 不绕过 / 不 sleep / 不到 6）
- 适用范围（手工命令 + pytest + alembic + 容器内连接 + 本地）
- 为什么段（实踩坑：账号锁定 / 失败非抖动 / 5 次足够区分"手抖"与"配置错"）
- 标准动作模板（含给用户的 4 选项）
- 反模式 5 条（无封顶 / sleep 拉长 / "最后一次" / 吞 stderr / 自动化脚本 `attempt < 999`）

**未实现自动化**：本策略依赖**人**遵守，不写强制脚本。理由：
1. 写脚本可绕过（人仍直接 `psql`）。
2. 密码错误后的处理是**人**的决策，脚本无权代决。
3. 与项目既有"Harness 规则是 SSOT + code-review 拦截"模式一致。
