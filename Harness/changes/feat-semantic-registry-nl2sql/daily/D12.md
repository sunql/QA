## 本日关键发现（改写计划的地方）

### F1 ⛔ 快照是 name-keyed，渲染器是 id-keyed ⇒ 必须有一层 id 合成

`nl2sql_schema.buildSchemaText` 全线按 id 索引（`classesById = {cls.id: cls}`，父类 / 外键 / JOIN 两端按 id 回查），
而发布快照**不带 id**、一律按类名引用。快照不带 id 是 P0 裁决一 + 字节确定性的必然结果（自增 id 跨环境不同）。

⇒ 采纳 plan §3.3 方案 A：在**整份 manifest** 上按类名排序分配合成 id（1..N）。
「整份」而非「子集」是关键：子集每次召回都变，按子集分配会让同一个类的 id 随同伴漂移 ⇒ 快照不可复现、diff 不可比。

### F2 ⚠️ `__dict__` 陷阱：复原对象不能用 slots

`nl2sql_schema` 用 `"parent" in cls.__dict__` / `"ref_class" in prop.__dict__` 探测 SQLAlchemy 的
惰性关系是否已加载。`slots=True` 的 dataclass 没有实例 `__dict__` ⇒ `AttributeError: __dict__`。
⇒ 三个复原类型都是**无 slots** 的 dataclass，且刻意不声明 `parent` / `ref_class` 字段。

### F3 ✅ 子集外的引用 = 查不到 = None（与 ORM 路径同口径 —— 但**有前提**，见 F5）

ORM 路径里 `classesById` 只含召回子集 ⇒ 子集外的父类 / 外键目标就是查不到。
墓碑类同理：编译器把墓碑引用编译成 `None`，ORM 路径里墓碑 id 也不在 `classesById` 里。
⇒ 复原侧照抄：parent / ref / join 两端在子集外一律 `None`。单测 + 真实渲染器双向钉死。

⚠️ **口径修正（原措辞「天然同口径」过强）**：同口径成立的前提是「ORM 侧的关系未加载」
（见 F5 的变体 A）。关系一旦被加载（变体 B），ORM 侧会渲染出**子集外**的父类块与
外键目标表 ⇒ 与复原侧**不等价**。本日实测生产会话状态 = 变体 A（`ref_class` 加载率
0/3267），且生产渲染路径**从不**把 `OntologyProperty` 作为主实体查询 ⇒ 生产走变体 A。
⇒ 结论改成「**在生产会话状态下同口径**」，并用 ORM-vs-复原黄金测试把这个前提钉死。

### HIGH ⛔ DSN 的 query string 能改掉**驱动实际连接的服务器** ⇒ 正式库写入没有回滚点

**根因（可执行证据，不是推测）**：

| 环节 | 旧实现取到的目标 |
|---|---|
| 驱动实际连接 | `PGDialect_asyncpg().create_connect_args()` ⇒ `{'host': 'evil.internal', 'port': 6432, 'database': 'qa_metadata', ...}` |
| `pg_dump` 备份 | 手搓 `-h localhost -p 5433`（**只读 DSN 路径**） |

asyncpg 方言把 `url.query` 合并进 connect kwargs ⇒
`postgresql+asyncpg://u:pw@localhost:5433/qa_metadata?host=evil.internal&port=6432`
让**驱动连到 evil.internal:6432**，而备份的是 localhost:5433
⇒ **备份的是 A 库、写入的是 B 库** ⇒ 正式库写入**没有回滚点**。
且 `SELECT current_database()` **看不出来** —— 两台机器上库名相同（`qa_metadata`）。

**修法（三处同时上，缺一不可）**：

| # | 位置 | 修法 |
|---|---|---|
| ① | `db_snapshot_guard.dumpTarget` | 备份目标改为从**驱动自己的 connect kwargs** 取（`url.get_dialect()().create_connect_args(url)`）⇒ 备份目标与写入目标**同一个来源**，白名单以后放宽也不会漂 |
| ② | `db_snapshot_guard.assertNoTargetOverride` | 写路径**拒绝**会改目标的 query 参数（白名单只留 `sslmode` / `ssl` / `application_name` / `connect_timeout` / `command_timeout`）；目标必须写在 DSN 路径上（一眼可见） |
| ③ | `db_snapshot_guard.resolveDatabaseUrl` | 两道闸挂在**唯一 DSN 入口**上 ⇒ 三个脚本（发布 / 影子比对 / 回填）都绕不过去（fail-closed） |

`?sslmode=require` 这类**不改目标**的参数仍然放行，并翻译成 `pg_dump` 认识的
`PGSSLMODE` / `PGAPPNAME` / `PGCONNECT_TIMEOUT` ⇒ 备份与写入走**同一条连接路径**。
