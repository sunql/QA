# 系统差距评估报告：采购域 AI-Ready 数据标准 vs QA-System 当前能力

> **评估对象**：`docs/data-knowledge/` 下三份规划资料——企业 AI-Ready 数据标准体系（12 模块）、采购域落地样板（9 大能力）、采购域数据标准模板（22 个内容 Sheet）
> **对照对象**：qa-system 当前已实现功能（基于 `Harness/wiki/`、`docs/功能完成度分析.md`、后端 ORM 与 API 实测）
> **评估目标**：在**不修改系统代码**的前提下，从系统层面对比，给出待补充/完善项与优先级建议
> **评估日期**：2026-08-29

## 一、评估框架

### 1.1 三份规划资料的结构化拆解

### 1.2 评估方法

按 **AI-Ready 数据标准体系 5 级成熟度模型**（Data Available → Data Standardized → Data Governed → AI Ready → AI Native Enterprise）对照当前系统：
- **L1 数据可用**：系统是否能直连业务库？
- **L2 数据标准化**：ODS/DIM/DWD 分层是否建立？
- **L3 数据治理**：质量 / 元数据 / 血缘 / 主数据是否落地？
- **L4 AI Ready**：语义层 / 特征层 / 知识层是否完整？
- **L5 AI Native**：AI Agent / 知识图谱 / 自动化决策是否上线？

### 1.3 当前系统在体系中的定位（结论先行）

| 维度 | 当前等级 | 主要支撑 |
|---|---|---|
| 整体 | **L3 上探 L4 下沿**（数据治理部分完成、AI Ready 初步具备） |
| 数据可用 | ✅ L1 已达 | `BusinessDBPool` 直连 MySQL/PG/Oracle 多方言 |
| 数据标准化 | ⚠️ L2 部分 | 仅 DWD 层通过 `OntologyClass` 抽象；ODS/DIM/DWS/ADS 无独立分层模型 |
| 数据治理 | ⚠️ L3 部分 | 元数据 ✓、主数据部分（需手工 seed）、质量 ✗、血缘 ✗、RACI ✗ |
| AI Ready | ⚠️ L4 部分 | 语义层 ✓（`TermDictionary` + 本体 description）、特征层 ✗、知识层 ✗ |
| AI Native | ❌ L5 未启 | 无 Agent 平台、无知识图谱推理 |

## 三、纵向维度：采购域 9 大能力 vs 系统能力（按能力逐项对比）

### 能力 ① 统一业务对象

**规划要求**：
- 18 个核心业务对象（SUPPLIER / MATERIAL / PR / RFQ / QUOT / PO / POL / CONTRACT / ASN / DELIVERY / GR / IQC / NCR / INV / PAY / BUYER / PLANT / SUP_PERF）
- 每个对象：对象代码 / 中文名 / 英文名 / 定义 / 类型 / Owner

**系统现状**：
| 维度 | 系统实现 |
|---|---|
| 对象载体 | `OntologyClass`（class_name / class_alias / description / source_table） |
| 已映射 | BPSUPPLIER / PORDER / PORDERQ / YPRECEIPT / YPRECEIPTD / PRECEIPT / PRECEIPTD / ITMMASTER / PPRICCONF / PPRICFICH / PPRICLIST 等 20 类 |
| 缺口 | ❌ 无 `object_type`（Master/Transaction/Reference）字段；❌ 无 `object_owner` 字段；❌ 无对象生命周期状态管理 |
| 缺失对象 | **未建模**：RFQ / QUOT / CONTRACT / ASN / DELIVERY / NCR / INV / PAY / SUP_PERF 9 个 |

**差距评估**：⚠️ **覆盖率 50%**（建模 10/18），元数据字段缺 2 项。

---

### 能力 ② 统一编码与跨系统标识映射

**规划要求**：
- `SUPPLIER_KEY` + `SUPPLIER_CODE` + `SUPPLIER_NAME`（企业统一）
- `DIM_ENTITY_MAPPING`：跨系统编码映射（ERP/SRM/QMS 三方对照）
- Business Key 与 Warehouse Surrogate Key 区分

**系统现状**：
| 维度 | 系统实现 |
|---|---|
| 编码规则 | `OntologyProperty.source_column` 强制对齐物理列；class_name 全大写匹配 Oracle 表名 |
| 跨系统映射 | ❌ **无 `EntityMapping` 表**；多源 SUPPLIER 在 BPSUPPLIER 中按 vendor_code 区分，缺 enterprise_key 抽象 |
| 代理键 | ❌ 业务库自维护主键；无仓库层 surrogate key 概念（OWNS direct query） |
| 已应用实例 | `BUSINESS_JOINS` 用 `from_col → to_col` 显式声明（满足部分需求） |

**差距评估**：❌ **缺失最严重的能力之一**。采购域多源对账（ERP/SRM/QMS 同一供应商不同编码）当前无模型支撑。

---

### 能力 ③ 统一数据模型（维度 + 事实）

**规划要求**：
- 维度：DIM_SUPPLIER / DIM_MATERIAL / DIM_PRODUCT / DIM_ORGANIZATION / DIM_PLANT / DIM_PURCHASE_ORG / DIM_BUYER / DIM_CURRENCY / DIM_DATE / DIM_WAREHOUSE / DIM_PURCHASE_CATEGORY（11 张）
- 事实：DWD_PURCHASE_REQUISITION / DWD_RFQ / DWD_SUPPLIER_QUOTATION / DWD_PURCHASE_ORDER / DWD_PURCHASE_DELIVERY / DWD_GOODS_RECEIPT / DWD_INCOMING_INSPECTION / DWD_PURCHASE_INVOICE / DWD_SUPPLIER_PAYMENT / DWD_SUPPLIER_PERFORMANCE（10 张）
- 每张事实表显式定义 GRAIN / 主键 / 维度关联 / 度量 / 来源 / 刷新频率

**系统现状**：
| 维度 | 系统实现 |
|---|---|
| 事实模型载体 | `OntologyClass`（一个 class = 一个事实表，例 `PurchaseOrder` 类 → `PORDER` 表） |
| GRAIN 显式登记 | ❌ 缺失（`description` 含部分语义但非结构化字段） |
| 维度关联 | ⚠️ `OntologyProperty.is_foreign_key` + `ref_class_id` 部分表达 |
| 已建事实 | 仅 `PurchaseOrder`、`GoodsReceipt`、`IncomingInspection` 等少量（DWD 层的子集） |
| 缺失事实 | **PR / RFQ / QUOT / DELIVERY / INV / PAY / SUP_PERF 7 张未建模** |

**差距评估**：⚠️ 现有 `OntologyClass` 概念上能覆盖「统一数据模型」，但缺 GRAIN 等结构化字段；覆盖广度不到规划 50%。

---

### 能力 ④ 统一业务语义

**规划要求**：
- 业务术语库：TERM_CODE / TERM_NAME / TERM_EN / DEFINITION / SYNONYM / OWNER（25 条）
- 关键字段语义：REQUEST_DATE / PROMISED_DATE / ACTUAL_RECEIPT_DATE 三件套

**系统现状**：
| 维度 | 系统实现 |
|---|---|
| 术语库 | ✅ `TermDictionary` 表 + `TermDictionaryService.renderDictionaryText` 注入 plan prompt |
| UI | ✅ `TermDictionaryManager` + `TermDictionaryButton` 在 ChatPanel |
| 字段语义 | ⚠️ `OntologyProperty.description` 含部分语义，但无独立 `DataSemantic` 模型（如「交期三件套」明确分类） |
| 缺口 | ❌ 无 SYNONYM（业务别名未结构化为独立字段）；❌ 无 TERM_OWNER 字段；❌ 无 TERM→OntologyClass 反向链接统计 |

**差距评估**：✅ **体系内最完整的能力**。术语库已上线并可被 NL2SQL 消费，仅缺少量元数据字段。

---

### 能力 ⑤ 统一指标口径（KPI Catalog）

**规划要求**：
- 12 个核心 KPI（KPI_SUPPLIER_OTD / KPI_OVERDUE_PO_RATIO / KPI_PURCHASE_CYCLE_TIME / KPI_AVG_DELAY_DAYS / KPI_SUPPLIER_DEFECT_RATE / KPI_FIRST_PASS_YIELD / KPI_NCR_RATE / KPI_PURCHASE_PRICE_VARIANCE / KPI_COST_SAVING / KPI_INVOICE_MATCH_RATE / KPI_PAYMENT_ON_TIME / KPI_MAINTENANCE_SPEND_RATIO）
- 每条 KPI 字段：KPI_CODE / KPI_NAME / BUSINESS_DEFINITION / FORMULA / NUMERATOR / DENOMINATOR / GRAIN / UNIT / DATA_SOURCE / OWNER / VERSION

**系统现状**：
| 维度 | 系统实现 |
|---|---|
| 指标载体 | `OntologyMetric`（metric_name / formula / agg_function / target_class_id / dimension_defaults） |
| 派生指标 formula 必填 | ✅ `validatePlan` 强制占比/比率类必须填 formula |
| 缺口 | ❌ **无 KPI_VERSION 字段**；❌ 无 OWNER；❌ 无 NUMERATOR/DENOMINATOR 分字段；❌ 无 UNIT 字段；❌ 无 GRAIN 字段；❌ 无 DATA_SOURCE 字段；❌ 无 KPI_CATEGORY 字段（OTD/质量/价格/财务 4 类权重） |
| UI | ⚠️ `MetricTab` 可 CRUD，但缺 KPI 分类 / 权重展示 |

**差距评估**：⚠️ **公式执行层完善，治理元数据薄弱**。新增 KPI 概念字段后可承接 12 个核心指标。

---

### 能力 ⑥ 完整数据血缘

**规划要求**：
- `DATA_LINEAGE` 表：`上游 / 下游 / 转换规则 / 刷新频率 / Owner`
- 端到端：Source → ODS → DIM/DWD → DWS → ADS → KPI / AI（20 条血缘样例）

**系统现状**：
| 维度 | 系统实现 |
|---|---|
| 表存在 | ❌ **无 `DATA_LINEAGE` 表** |
| 列级血缘 | ❌ 无字段级自动解析 |
| 间接能力 | `ontology-drift` 端点能发现「本体类 vs 物理表 schema」漂移（覆盖了部分场景） |
| Wiki 文档 | 仅在概念层提到，无落表 |

**差距评估**：❌ **完全缺失**。当前是「无血缘数据，仅靠 prompt 注入 ER 图描述」。

---

### 能力 ⑦ 可信数据质量

**规划要求**：
- 6 维 DQ：完整性 / 准确性 / 一致性 / 唯一性 / 及时性 / 有效性
- 20 条规则样例（DQ001~DQ020）
- 综合 `QUALITY_SCORE`：>=95 高可信 / 80-94 一般 / <80 仅供参考
- AI 应用读取 `Data Quality Score` 判断结论可信度

**系统现状**：
| 维度 | 系统实现 |
|---|---|
| DQ 规则表 | ❌ **无 `DataQualityRule` 表** |
| 校验引擎 | ❌ 无自动执行；仅有一次性脚本（`scripts/verify_invariants.py`、`scripts/verify_enums.py`、`verify_ontology_consistency.py`） |
| 质量评分 | ❌ 无 `QualityScore` 表 / 无评分计算 |
| 文档要求 | ✅ `docs/20260828-new-module-data-standard.md` 已定义 6 维准入要求（脚本级，未系统化） |

**差距评估**：❌ **完全缺失治理层**。文档层已沉淀「准入标准」，但缺自动化执行引擎 + 评分服务 + AI 可读接口。

---

### 能力 ⑧ 结构化数据关系（Entity Relation）

**规划要求**：
- `ENTITY_RELATION` 表：SOURCE_TYPE / SOURCE_KEY / RELATION_TYPE / TARGET_TYPE / TARGET_KEY / VALID_FROM / VALID_TO / CARDINALITY
- 30+ 条样例：SUPPLIES / CONTAINS / GENERATES / INSPECTED_BY / CONTRACTED_WITH 等语义关系
- 让 AI 可推理「供应商 → 物料 → 订单 → 收货 → 问题」

**系统现状**：
| 维度 | 系统实现 |
|---|---|
| 关系表 | ⚠️ 仅 `OntologyJoin`（FROM_TABLE.TO_TABLE → TO_TABLE.TO_TABLE 物理键关联） |
| Neo4j 边 | ⚠️ 仅 `HAS_PROPERTY` / `REFERENCES` / `SUBCLASS_OF` 物理关系 |
| 语义关系 | ❌ 无 SUPPLIES / DELIVERED_BY / INSPECTED_BY / GENERATES 等业务动词 |
| 应用场景 | 知识图谱推理（AI 应用基于图遍历）→ 当前**未启用** |

**差距评估**：⚠️ **物理关系完整，业务语义关系缺失**。Neo4j 已具备图存储能力，扩展主要是新增语义关系类型 + 应用层推理 API。

---

### 能力 ⑨ 非结构化知识关联（Document Layer）

**规划要求**：
- 18 个核心文档类型（CONTRACT / AUDIT_REPORT / SPECIFICATION / 8D_REPORT / POLICY / QUALITY_AGREEMENT / INSPECTION_SPEC / REMEDIATION_REPORT / PURCHASE_SPEC / MEETING_MINUTES / SOP / SAFETY_SHEET 等）
- `DOCUMENT_CATALOG` + `DOCUMENT_ENTITY_RELATION`（文档 ↔ 实体关联）
- RAG：CHUNK_ID / DOCUMENT_ID / CHUNK_TEXT / CHUNK_SEQUENCE / EMBEDDING_VERSION / EFFECTIVE_DATE / SECURITY_LEVEL

**系统现状**：
| 维度 | 系统实现 |
|---|---|
| Document 表 | ❌ **无 `DocumentCatalog` 表** |
| 文档-实体关联 | ❌ 无 |
| RAG 通道 | ❌ 无（Milvus 仅承载 ontology / query embeddings，无 document embedding） |
| 间接能力 | `EmbeddingProvider` 注册可支撑未来 RAG |

**差距评估**：❌ **完全缺失**。是采购域「AI 回答可解释性」的关键基础（参见采购域.md 第七节 §Step 7 检索非结构化知识）。

## 五、系统层面「应当补充」的能力清单（按优先级）

### P0 — 必须补充（采购域 AI 落地的 4 大卡点）

为避免只谈缺口，列出系统已经做到 / 部分做到的能力（在 AI-Ready 体系中可圈可点）：

   - 多方言（Oracle/MySQL/PG）安全执行

   - 这是 L4「AI Ready」语义层的核心能力

## 七、关键结论与建议

### 7.1 三个关键判断

1. **当前系统处于「L3 数据治理上探 L4 AI Ready 下沿」**
   - L1-L2 通过 `OntologyClass` + 直接查询业务库达成
   - L3 仅完成元数据 / 主数据部分；质量 / 血缘 / RACI 缺失
   - L4 仅完成语义层（TermDictionary + 本体 description）；特征层 / 知识层缺失

2. **「采购域 AI 真实落地」最大的 4 个缺口都在数据基础设施层**
   - 血缘 / 质量 / 分层模型 / 跨系统编码映射
   - 这些不是「本体编辑」能解决的，是「数据库模型 + ETL + 治理引擎」的工作

3. **本体的「治理字段」普遍不足**
   - `OntologyClass` / `OntologyProperty` / `OntologyMetric` 都缺 OWNER / VERSION / UNIT / GRAIN 等治理元数据
   - 当前架构能让 LLM 用上数据，但不能让「业务用户治理好数据」

### 7.2 不修改代码的改进建议（产品 / 流程层）

| 维度 | 建议 | 紧迫度 |
|---|---|---|
| **架构定位** | 把 qa-system 定位从「NL2SQL 引擎」升级为「**企业 AI 数据底座 v1.0**」——增加治理组件（DQ/LINEAGE/FEATURE/DOC） | 高 |
| **演进路线** | 沿采购域.md §十三 建议的 4 阶段推进：L1-L2 标准化 → L3 治理 → L4 AI Ready → L5 AI 应用 | 高 |
