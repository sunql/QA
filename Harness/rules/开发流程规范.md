# 开发流程规范

## 10 阶段工作流

每个特性/变更依次走以下阶段，结果沉淀到 `changes/<feature>/summary.md`。

1. **需求分析**：用 `request-analysis` 技能拆解需求，明确验收标准。
2. **专家评审**（可选）：复杂决策用 `expert-reviewer` 多视角评审。
3. **设计**：确定数据模型、接口契约、算法。更新对应 `wiki/`。
4. **测试先行（RED）**：先写失败测试，覆盖正常/边界/异常路径；数据层必须真实 PG + 完整 API 链路（见 [测试规范](./测试规范.md)）。
5. **实现（GREEN）**：最小实现让测试通过。
6. **重构（IMPROVE）**：在不破坏测试前提下优化结构。
7. **代码审查**：用 `code-review` 技能 + `python-reviewer`/`security-reviewer` 审查。
8. **覆盖率验证**：`pytest --cov=app --cov-fail-under=80` 与前端 `vitest run --coverage`。
9. **部署验证**：用 `deploy-verify` 技能跑 Docker Compose 冒烟，并先过「数据库迁移同步（部署门禁）」校验。
10. **记录变更**：在 `changes/<feature>/summary.md` 写 SSOT，更新 `wiki/` 与进度。

### 第 10 阶段 SSOT 强约束（部署阻塞项）

详见 [变更记录强制规范](./变更记录强制规范.md)。每个特性 / Bug fix / 重构合并前必填 5 条：

1. `Harness/changes/<feature>/summary.md` 9 段齐（不允许 TBD/TODO 占位）
2. 至少 1 个跨文件链接（关联变更 / wiki / rules 三选一）
3. 至少 1 条 MEMORY 索引（`~/.claude/projects/.../memory/<slug>.md` + MEMORY.md 加 1 行）
4. 相关 wiki 文档已更新（数据模型 / 接口 / 架构 / 前端 至少 1 处）
5. 涉及真实 SQL/DB 改动时 `scripts/<feature>_realdata.py` 跑通

**判定时机**：code-review 阶段 reviewer 必查，缺任一项打回。历史 SSOT 漏档走 `log-YYYYMMDD.md` 补救流程（见变更记录强制规范 §五）。

## 数据库迁移同步（部署门禁）

**事故教训**（2026-08-30）：data-quality 特性集成测试全绿，但 live 库 `alembic_version`
停在 `0016_ontology_join`，0017/0018/0019 从未应用 → 前端打开数据质量页
`GET /api/v1/data-quality/rules` 直接 500（`UndefinedTableError`：表不存在）。
**测试库迁移到位 ≠ 运行环境迁移到位**。docker compose 部署时容器启动会自动
`alembic upgrade head`，但本地/非容器化 DB（如本地 `qa_metadata` 5433）不会，
必须手工补跑。

**规则**：

1. 数据模型变更（新增/修改表）必须对**每个目标环境**执行 `alembic upgrade head`
   （测试库 + live/生产库），不允许只在一个环境应用。
2. 部署前必查：各环境 `SELECT version_num FROM alembic_version` 必须等于当前 head
   revision；环境之间迁移版本不一致即为**部署阻塞项**，先补齐再冒烟。
3. 新增表/列对应的接口，上线前必须对目标环境**冒烟**（curl 新端点返回非 5xx）；
   不能只依赖集成测试——集成测试连的是迁移齐全的测试库，覆盖不到 live 缺表场景。
4. 迁移脚本的部署验证段落写进 `changes/<feature>/summary.md` §8，并把新表/新端点的
   冒烟项追加到 `deploy-verify` 技能。

**二次复发 (2026-08-30 下午)**：feat-governance-hardening 合入后，`kpi_catalog` /
`entity_mapping` 在 live 库又缺表（落后 5 条迁移：0021-0025），前端报 500/404。
本次额外暴露两个加速排错的隐患：

- **本机 PG 端口不是 5432 而是 5433**：`docker-compose.yml` 把 Postgres 映射成
  `5433:5432`（避宿主 5432 OpenMetadata 占用）。连 5432 = ConnectionRefused。
  所有 `DATABASE_URL` / `TEST_DATABASE_URL` 一律 5433。
  详见 `Harness/wiki/operations-runbook.md`「迁移与端口映射」段。
- **陈旧 uvicorn 进程可能掩盖新端点注册失败**：本次一个 PID 34319 的旧 uvicorn
  早于 `kpi_catalog.router` 启动，导致 `/kpi-catalog` 报 404，让人误以为路由缺失；
  实际是进程没重启。重启 backend 后必须 `curl /openapi.json | jq '.paths | keys'`
  确认目标路由存在，再开始排查。

## 每轮真实数据验证（开发门禁）

**事故教训**（2026-08-30）：data-quality 特性单测 + 集成测试全绿（mock adapter +
fake rows + 真实 PG 5433 测试库），但**真实业务数据库**执行 SQL 时炸出 3 个
真实 bug，mock 测试 100% 漏检：

| Bug | 模拟测试 | 真实数据 |
|---|---|---|
| `_EXPR_RE` 正则拒绝 PG 双引号大小写敏感标识符（如 `"ORDERQTY" > 0`） | 测试用 `_`/`数字` 标识符假数据，永远走 `_IDENT_RE` 单 token 分支 | PG 表用大写列名 + 子查询必须双引号 → 校验直接拒 |
| 表达式消息缺特殊字符白名单提示（`"` 字符） | 测试用 `_`/数字/算术，无双引号场景 | 真实 SQL 必须含双引号才能命中 PG case-sensitive 表/列 |
| PostgreSQL 大小写折叠：unquoted → 全小写、quoted → 保留大小写 | 测试用 lowercase 数据，折叠前后等价 | Sage X3 / WMS 业务表都是大写命名 → 必须显式 `CREATE TABLE "PORDER"` 强制 quoted |

**根因**：单元/集成测试只覆盖「写好的代码路径」，覆盖不到「真实数据库方言 /
真实业务命名约定 / 真实数据分布 / 真实 SQL 计划器」。Mock 永远是「我以为它会
怎么跑」，真实数据是「它实际怎么跑」。

**规则**：

1. **每个特性完成后、写 change summary §8 前**，必须用**系统真实可用的数据**
   跑一遍端到端验证：
   - 业务数据库：当前环境的真实业务库（无 demo 数据时，可在本机 metadata DB
     临时建业务 schema + 真实业务表灌含缺陷的真实风格数据；不允许 `sqlite`、
     `monkeypatch`、纯 mock adapter 顶替）。
   - LLM 调用：若特性涉及模型路由/embedding/chat，至少跑一次真实调用并贴
     token 计量与响应片段到 change summary。
   - 第三方组件（Neo4j/Milvus/Redis）：特性涉及则真实跑一遍，至少一条写 + 一条
     读，贴日志。
2. **真实数据验证脚本**与 `scripts/seed_*.py` 同级，命名 `scripts/<feature>_realdata.py`，
   幂等 + 含缺陷样本（故意制造覆盖各种失败路径），用于：
   - 复现业务典型场景（真实命名、真实数据量级、真实 schema 命名约定）
   - 暴露 mock 漏掉的方言/特性差异
   - 给 reviewer 与运维一个「我可以自己跑一遍」的可重现入口
3. **真实数据验证输出**写进 `changes/<feature>/summary.md` 新增 §9「真实数据验证
   报告」：跑了哪些真实链路、贴关键 curl 输出 / 关键 SQL / 关键分数 / token 计量 /
   发现并修复的真实 bug 列表。无此节即视为**该 change 未通过门禁**。
4. **真实数据发现的问题**必须在合并前修复（包括补丁单测覆盖该真实场景，避免回归）；
   若因环境限制暂时绕到，必须在 §9 写明绕过的理由 + 后续整改计划。
5. **测试覆盖率的豁免**：`sqlite` 内存库 + mock-only 测试覆盖率达 80% **不构成**
   本节合规；覆盖率必须以**真实 DB + 真实 SQL** 的测试用例为主。

## CI 合并判据（失败集合对差）

**事故教训**（2026-10-31 ~ 2026-11-02，PR #98 / #99 批次）：本仓 CI **基线是红的**
（`main` 上即有既有失败）⇒ 判据**不是**「等 CI 变绿」。而人工做「失败集合对差」时
连续踩了六个坑，其中一个直接导致**假「净新增 0」**：

| 坑 | 现象 | 后果 |
|---|---|---|
| `cancelled` 的 job 失败集合是**空的** | GH Actions 把超时 job 标成 `cancelled`（**不是** `failure`），它没跑完 ⇒ 失败集合为空 | 拿它对差 ⇒ 得出「净新增 0」的**假结论** ⇒ 把回归合进 main |
| 缺完成标记 = 没跑完 | 分片 job 被取消时同样没有失败集合 | 同上 |
| 日志行带时间戳前缀 | GH Actions 每行形如 `2026-11-02T07:10:13.4960640Z FAILED ...` ⇒ `^FAILED` 一条都匹配不到 | 抽不出失败集合 ⇒ 对差形同虚设 |
| `comm` 要求两侧同序同 collation | python `sorted()`（码位序）与 `sort -u`（locale 序）不同序时 | `comm -23` 与 `comm -13` **都非空** ⇒ 假差异 |
| **pytest 被信号杀死也会打出完成标记** | CI 脚本用 `|| status=$?` 捕获退出码 ⇒ OOM killer 杀掉 pytest 时 bash 报 **137**，标记照样打印 | 旧实现判「跑完了、真红、失败集合为空」⇒ **结论「可合并」** ⇒ 假绿通道 |
| **两次 run 跑的 job 不一样** | PR 把 `matrix.shard` 改窄、或给某个 shard 加 `if: false` | PR 失败集合只会**变小** ⇒ 「净新增 0」是假的，且 GitHub 上 CI **全绿** ⇒ 连二次防线都没有 |
| **真红但没有 pytest 收尾汇总行** | 用例里一句 `os._exit(1)` 让 pytest **中途夭折**，却留下退出码 1 ⇒ CI 脚本照样打出 `status=1` | 失败集合只覆盖**前半截** ⇒ 对差失真 ⇒ 假「净新增 0」 |
| **PR 改了 conftest / workflow** | 用 `pytest_collection_modifyitems` 把失败用例跳过、或加 `--deselect` ⇒ 失败用例**根本不产生 `FAILED` 行** | 失败集合与基线**完全相同** ⇒ 假「净新增 0」，且 CI 还全绿 ⇒ 没有二次防线 |

**规则**：

1. **判据 = 失败集合对差，不是「CI 变绿」。** 取同一个 CI 在 PR 与基线（`main` 上
   最近一次）两次 run 的失败用例集合，**净新增为空**才合并；净丢失要**人工确认**
   （确认不是「把失败藏起来了」）。
2. **不可用 job 一律排除在判据之外，并必须复跑。** 下列 job 的失败集合**不可信**
   （通常是空的）：
   - 结论为 `cancelled`（超时 / 被抢占）或 `skipped` 的 job；
   - 日志里**缺少分片完成标记**（`X_SHARD_DONE shard=N status=<pytest 退出码>`）的 job；
   - 结论与完成标记互相矛盾（`success` 但 `status!=0`，或 `failure` 但 `status=0`）的 job；
   - 完成标记的 **族名 / 分片号与 job 名对不上**（`Backend / unit shard 0` 的日志里
     出现 `INTEGRATION_SHARD_DONE shard=1`）的 job；
   - **pytest 退出码不在 {0, 1}** 的 job —— pytest 只有 `0`（跑完全绿）与 `1`（跑完有失败）
     代表「跑完了」；`2`=中断 / `3`=内部错误 / `4`=用法错误 / `5`=未收集到用例 /
     `128+N`=被信号杀死（`137`=SIGKILL、`143`=SIGTERM）都意味着**没跑完或等于没跑**
     ⇒ 失败集合是空的或不可信；
   - **真红（`status=1`）但一条 `FAILED`/`ERROR` 都没有**的 job（失败明细抽不出来 ⇒
     失败集合是空的）；
   - **日志里没有 pytest 的收尾汇总行**（形如 `2 failed, 118 passed in 812.34s`）的 job
     —— **对所有状态都要求**，不只 `status=1`：pytest 只有在整个 session 跑完时才打印这行；
     用例里一句 `os._exit(0)`（或 `os._exit(1)`）就能让 pytest **中途夭折**却留下退出码
     ⇒ 失败集合只覆盖前半截。⚠️ 旧实现只在 `status=1` 时要求 ⇒ `os._exit(0)` 那条
     **最便宜**的绕过通道是敞开的（用例 `test_assessJob_rejects_green_run_without_pytest_summary`
     钉死这条）；
   - **汇总行里的失败数 ≠ 抽出来的失败 ID 数**的 job —— 失败集合不完整 ⇒ 不可用；
   - **日志里出现多于一条完成标记**的 job —— pytest 的 stdout 由 PR 作者可控
     （测试里可以 print）⇒ 可以伪造一条 `X_SHARD_DONE shard=N status=0` 洗白真红；
     真标记只会打一次 ⇒ 多于一条必须人工确认；
   - **job 名含 `unit` / `integration` / `shard` 却不匹配已知分片协议**的 job
     （协议被改过 ⇒ 「这个 job 到底是哪个分片」不确定 ⇒ 它贡献的集合不能参与对差）。

   ⇒ **只要有任何一个 job 不可用，结论就是「不可用，必须复跑」**，即使净新增为空
   —— 这是「假净新增 0」的全部来源。复跑单 job：
   `gh api -X POST repos/sunql/QA/actions/jobs/<job_id>/rerun`
3. **两次 run 必须跑同一批 job（覆盖等价）。** 比对维度是 **job 名**（job id 每次都变，
   而 job 名里带着分片号）。两侧 job 名集合不等价 ⇒ **对差不成立** ⇒ 必须人工确认
   （PR 确实少跑了 job ⇒ 失败集合只会变小 ⇒「净新增 0」是假的）。
   ⚠️ 这条是**硬阻断**，不能靠「CI 全绿」绕过：少跑的分片没人失败 ⇒ GitHub 显示全绿。
   ⚠️ 同理，**两次 run 不能填同一个 id**（自比自 ⇒ 失败集合必然相同 ⇒ 假「净新增 0」）。
   ⚠️ **PR run 必须是 PR 当前 head 跑的**：工具会比对 run 的 `head_sha` 与分支当前 head
   ⇒ 不一致（PR 推了新 commit，run 已过期）⇒ **退出码 3**。
   否则「拿上一次绿的 run 来对差」就是一条现成的绕过通道（旧的绿 vs 基线 ⇒ 净新增 0）。
4. **PR 改了「CI 相关面」⇒ 两次 run 的失败集合不再可比 ⇒ 一律判「不可合并」。**
   CI 相关面 = `.github/workflows/`、**任意深度**的 `conftest.py` / `pytest.ini` /
   `setup.cfg` / `tox.ini`、`backend/pyproject.toml` 与 `backend/uv.lock`、
   分片清单生成器（`ci_shard.py`）、以及**判定工具自身的每一个模块**
   （`ci_{failure_set,judge,pytest_log,report,head,text,gh,surface,shard,flakes}.py`）
   与**已知抖动白名单数据文件**（`.github/ci-known-flaky-tests.json`）。
   ⚠️ **守卫自身与授权面也在「CI 相关面」里**：
   `backend/app/tests/(?:.*/)?test_ci_*.py`（守卫用例，**任意深度**）、
   `backend/app/tests/(?:.*/)?_ci_*_support.py`（守卫的**共享替身**）与 `.github/CODEOWNERS`
   ⇒ **改守卫 = 解除守卫**（断言被删 ⇒ 守卫不会再红 ⇒ CI 全绿 ⇒ 没有二次防线）；
   改替身 = 改守卫的**观测对象**（例如把「失败集合」替身改成永远返回空 ⇒ 全部对差守卫恒绿）；
   改 CODEOWNERS = 换复核人 ⇒ 判据就没人把关了。
   ⚠️ 守卫必须按**任意深度**判定：只扫 `unit/` ⇒ 把守卫挪到 `integration/` 就同时逃出
   ①「CI 相关面」判定 与 ②CODEOWNERS 反查 ⇒ 改守卫 = 解除守卫且无人复核。
   ⚠️ 必须按 **basename / 路径形态**判定，**不能枚举「今天有哪几个 conftest」** ——
   pytest 会从 rootdir 往下逐层收集 conftest ⇒ `backend/app/conftest.py` 对
   `backend/app/tests/**` 全部生效 ⇒ 枚举式判定会漏掉新加的那一层。
   ⚠️ 工具模块清单必须**覆盖每一个模块**（守卫从文件系统反查 ⇒ 漏一个就转红）——
   漏掉 `ci_judge.py`（判定逻辑）就能把「被取消的 job」判成「可用」；
   漏掉 `ci_report.py`（报告渲染）就能把「净新增失败清单」从报告里抹掉。
   ⚠️ **改名也算改动**：树对树差异天然表现为「旧路径删除 + 新路径新增」
   ⇒ **两个路径都在**改动清单里 ⇒ 把 CI 相关面文件**改名**逃不出人工仲裁。
   （compare API 对一次改名**只给一个条目**（新路径在 `filename`、旧路径在
   `previous_filename`）⇒ 若改走 compare 就会漏掉旧路径 ⇒ 这也是不走 compare `files` 的原因之一。）
   ⚠️ **CODEOWNERS 是「最后匹配者生效」** ⇒ 复核「某路径归谁」必须算**生效归属**，
   不能只查「路径出现过」⇒ 在文件**末尾**追加一行 `* @someone-else` 就能把全部 CI 路径的
   复核人换掉而守卫仍绿。
   ⚠️ compare API 的 `files` 数组**最多 300 项** ⇒ **不要用它**取改动清单
   （已改走 Trees API 树对树，见下）；若谁再把它接回来 ⇒ 命中上限必须**报错**
   （⇒ 退出码 6），不能当成「就这些文件」。
   ⚠️ **CI 相关面的判定集合 = `A ∪ P` ∩「CI 相关面清单」**（2026-11-07 定稿，N6 第三版）：

   | 集合 | 内容 | 采集方式 | 用途 |
   |---|---|---|---|
   | `A` | main 在 `[M_base, M_T]` 之间的**内容推进** | Trees API 树对树比（`git/trees/{sha}?recursive=1`） | 参与判定 + 措辞 |
   | `P` | **PR 自己**改的文件（三点语义，分叉点 = `merge_base(M_T, PR 头)`） | compare API 只取 `merge_base_commit`，差异自己用树对树算 | 参与判定 + 措辞 |
   | **判定集合 = `A ∪ P`** | | | **判定** |

   ⚠️⚠️ **判定集合必须等于「两次 run 实际跑的那两份代码的差异」**
   （`ci.yml` 对 `pull_request` 触发，三个 `actions/checkout` **都不带 `with: ref:`**
   ⇒ 检出的是 `refs/pull/N/merge` ⇒ **PR 的 CI 跑的是 merge(main@run 时点, PR 头)**。
   实证：PR #111 的 run `42281369007` 的 `head_sha` = PR 头 `1d226997…`，
   而 job 日志写着 `HEAD is now at 23db713 Merge 1d226997… into 87f8e8e6…`）。
   ⇒ 拿「基线树 vs **PR 头树**」比 ⇒ ① main 改了 CI 文件 ⇒ **系统性假拦**
   （实测 PR #92/#94/#95/#107 的净变更 CI 命中 1/29/29/17，而三点归因命中 **0**）；
   ② 更糟 —— **fail-open**：PR 头树与基线树**同样旧** ⇒ 差异为空 ⇒ 判「没改」
   ⇒ 而 PR run 实际跑的是合并后的**新** CI ⇒ 两次 run 的 CI 定义不同 ⇒ 判不出来。
   ⇒ **为什么 `A ∪ P` 就是它**：合并结果的树逐路径看是「**PR 动过就取 PR 的版本，
   否则取 `M_T` 的版本**」⇒ 路径级差异 = 「基线 vs `M_T`」（`A`）∪「PR 动过的路径」（`P`）。
   ⇒ **两边都不能少**：只算 `P` ⇒ main 改了 CI 文件而 PR 没跟上 ⇒ **fail-open**；
   只算 `A` ⇒ PR 自己改了 CI 文件却**看不见** ⇒ **假放行**。
   ⚠️ **不要去取 `refs/pull/N/merge` 那个 commit 的树**：它是**临时 ref**
   （`pulls/{n}.merge_commit_sha` 是它的**当前值**，main 一推进就漂移；PR 合并后 404）
   ⇒ **回溯历史 run 时根本取不到** ⇒ 只能用 `A ∪ P` 在算法上合成。
   ⚠️ **`M_T`（PR run 事件派发那一刻 main 的 tip）怎么取**（工具侧**独立取**）：
   上界 = PR run 的 **`created_at`（事件派发时刻）** + 120 秒宽限
   ⇒ 取 main 的 **push run 列表**，逐条过三条硬条件
   （`event == "push"` ∧ `head_branch == "main"` ∧ `head_repository == 本仓库`，大小写不敏感）
   ⇒ 再过时间窗 `created_at <= cutoff` ⇒ 取最新一条的 `head_sha`。
   ⇒ 一条都不合格 ⇒ **判定不出来（退出码 6），不许随便返回一个 sha**。
   ⇒ **`M_T` 不许由闸门代取后传入**（否则工具失去独立复核的机会）。
   ⚠️ **`M_T` 取两条腿**（run 腿 + commit-date 腿），`A` 取**两条腿的并集**：
   main 的那次 push **没触发** workflow、或它的 run **创建得太晚**（排队 > 宽限）⇒ run 腿偏旧；
   commit 日期 ≠ push 时刻（rebase / 时钟偏斜）⇒ commit-date 腿也可能偏旧
   ⇒ 单用一条会漏掉 main 的推进 ⇒ 两次 run 的 CI 定义可能其实不同 ⇒ **fail-open**。
   ⇒ 两条腿都偏旧且偏到同一处时仍会漏（残留窗口，见变更记录的「已知局限」）。
   ⚠️⚠️ **上界必须锚 `created_at`，不能锚 `run_started_at`**（2026-11-07 代码评审 CRITICAL-1）：
   `pull_request` 事件的**合并 commit 在事件派发那一刻就被冻结**了
   ⇒ 复跑（re-run）**不会**重新计算它 ⇒ 复跑检出的仍是**同一个**合并 commit
   ⇒ 它的 main 侧底座是**派发那一刻**的 main。
   实测（PR #105 run `41908498247`，attempt=2）：`created_at=2026-11-04T20:38:19Z`、
   `run_started_at=2026-11-04T22:24:11Z`；合并 commit `57a267a9` 的
   committer.date = `20:38:18Z`、第一父 = `83581e10`（= 派发那一刻的 main）；
   attempt-2 的 job 日志写着
   `git fetch … +57a267a93f…:refs/remotes/pull/105/merge` ⇒ **同一个**合并 commit。
   ⇒ 锚 `run_started_at` ⇒ `M_T` 取到**派发之后**的 main；
   而闸门侧若同样用它取基线 ⇒ 基线树与执行树都落到那个更晚的 main
   ⇒ `A` 变成空集 ⇒ 两次 run 实际跑的 CI 定义不同却判「可合并」⇒ **fail-open**。
   ⚠️ **两边的锚点必须同时换**（工具侧 `ci_gh.mainTipCutoff` 与 workflow 侧
   `PR_RUN_CREATED_AT`）⇒ 一边换一边不换 ⇒ 同样 fail-open。
   ⚠️ **`mainTipCutoff` 的两个时间戳必须 keyword-only 传**：
   这次的缺陷正是「位置传参 + 锚点写反」⇒ 两个时间戳都是合法值
   ⇒ 传反了**不会报错** ⇒ 判定静默用错锚点 ⇒ 具名传 ⇒ 顺序再也没法搞错。
   ⚠️ **基线取法同步收紧**：基线 = **PR 的 CI 事件派发之前** main 上最新完成的 push run
   （workflow 侧用 `PR_RUN_CREATED_AT` 做 `created_at <=` 窗口，
   该值取 **`created_at`（事件派发时刻）**；**为空 ⇒ 显式 fail-closed**）
   ⇒ 因为 PR run 执行的是「PR CI 事件派发那一刻的 main」⇒ 基线若取了**之后**才推的 main
   ⇒ 两次 run 天然不同 ⇒ 又是假拦。
   ⚠️ **底座核对**：若基线 run 的 commit ≠ `M_T` ⇒ main 在基线之后推进过
   ⇒ 两次 run 的 CI 定义可能不同 ⇒ 报告里必须提示「**重新运行 PR 的 CI**」
   （让它合上最新的 main），而不是直接放行。
   ⚠️ 但这条提示**只在判出 CI 相关面变更时**出现（`M_base ≠ M_T` 是**常态**
   ⇒ 无条件提示就是噪音 ⇒ 提示变噪音就会被无视 ⇒ 提示就失效）。
   ⚠️ **判定必须落在判定集合（`A ∪ P`）上**：两次 run 跑的 CI 定义若**本身就不同**
   （main 在 PR 分叉之后改了 CI 文件、PR 分支没跟上）⇒ 失败集合**不可比** ⇒ 必须拦；
   若只用「三点归因集」判定，这种情形会被**放过去**（fail-open 洞）。
   ⚠️ **归因集 = `P`（三点语义）**：判定集合不区分「谁改的」⇒ 需要知道是「PR 自己改了 CI 文件」
   还是「归因不到本 PR」（通常 = main 改了而 PR 没跟上）⇒ 两种情形的处理与措辞不同。
   ⚠️ **不能用 compare 的 `files` 数组**：它**最多 300 项** ⇒ 大 PR 被静默截断
   ⇒ 归因集不完整 ⇒ 真改的 CI 文件被排除 ⇒ fail-open
   ⇒ 只从 compare 取 `merge_base_commit`，差异一律走 Trees API 树对树（无 300 项上限）。
   ⚠️ **净变更拉不到时不许退回三点 diff** —— 那正是本条要消除的假阳性来源
   ⇒ 拉不到就**判定不出来**（退出码 6，保守拦下）。
   ⚠️ Trees API 的递归树**可能被服务端截断**（响应里 `truncated=true` ⇒ **少给**条目）
   ⇒ 命中截断必须**报错**（fail-closed），不能当成「就这些文件」；
   `truncated` 键**缺失**同样按「不完整」处理。
   ⚠️ 递归树条目类型：`blob`（文件）与 `commit`（子模块）要收，`tree`（目录）**必须排除**
   ⇒ 否则「一边多一个空目录」会被当成「改了一个文件」。
   ⚠️ **基线 run 必须先验可信**：必须是**本仓库 main 分支上的 push run**
   （`event == "push"` ∧ `head_branch == "main"` ∧ `head_repository == 本仓库`）
   ⇒ GitHub 的 `runs?branch=main` **不区分事件**（实测会返回 `pull_request` 的 run）
   ⇒ 一个**名叫 main 的 fork 分支**也会命中 ⇒ 基线可能变成**攻击者自己的代码**
   ⇒ 对差被中和。**工具侧必须独立复核**（不能只靠 workflow 的查询串）。
   ⚠️ **抖动豁免的前置条件也用净变更**：若只用三点归因集 ⇒ main 侧改过的测试文件
   会被当成「没改过」⇒ 抖动豁免吃掉真回归。
   ⚠️ **分支一律以 main 的 tip 为底座起，不要用「重建 main 的 tree 的合成提交」同步**
   —— 合成提交让 main 的 tip 不是分支的祖先 ⇒ 三点归因的 merge-base 退到老底座
   ⇒ 即使判定已改用净变更，归因**措辞**仍会失真。
   攻击路径：PR 用 `pytest_collection_modifyitems` 把失败用例跳过、或在 workflow 里加
   `--deselect` ⇒ 失败用例**根本不产生 `FAILED` 行** ⇒ 失败集合与基线完全相同 ⇒
   假「净新增 0」，而 GitHub 上 CI 还**全绿** ⇒ 没有二次防线。
   ⇒ 工具对此返回**退出码 6**；确认无影响时用 `--allow-ci-changes` **显式**豁免
   （豁免是人的决定，不是工具的默认行为）。
   ⚠️ 判定不出改动清单（拉取失败）时**保守拦下** ——「不知道」不等于「没有」。
5. **用工具，不要手搓。** 仓库自带可执行判据：
   ```bash
   cd backend && uv run python -m app.utils.ci_failure_set \
       --repo sunql/QA --base-run <基线 runId> --pr-run <PR runId> \
       [--allow-ci-changes]
   ```
   退出码：

   | 码 | 含义 |
   |---|---|
   | `0` | 净新增 0、无待确认项、全部 job 可用且覆盖等价 ⇒ **可合并** |
   | `1` | 净新增失败非空 ⇒ 不可合并 |
   | `2` | 存在不可用 job ⇒ 必须复跑后再对差 |
   | `3` | 运行错误（gh 调用失败、参数非法、两次 run 填了同一个 id、某侧 0 个 job、**已知抖动白名单读不到/非法**） |
   | `4` | 两次 run 的 job 集合不等价 ⇒ 对差不成立 ⇒ 人工确认 |
   | `5` | 净丢失失败用例非空 ⇒ 须人工确认不是「把失败藏起来了」 |
   | `6` | PR 改了 CI 相关面（或判定不出）⇒ 失败集合不可比 ⇒ 人工确认 |

   取日志需要 `gh api … --allow-escape-sequences`（GH Actions 日志含终端转义序列，
   不加这个 flag `gh api` 直接报错拒绝输出）。
   ⚠️ 报告里的外部文本（job 名、失败用例 ID、gh stderr）**必须先净化再脱敏**：
   净化剔控制字符（防 CSI 序列擦掉已打印的「结论：可合并」行、防 OSC 52 改写剪贴板），
   脱敏打码凭据（token / 密码 / DSN / SAS 签名 URL）。
6. **禁止用 `deselect` / `xfail` 掩盖既有失败来「求绿」** —— 基线红是既有事实，
   合并判据看的是**净新增**，不是绝对绿。
7. **CI 的 `fail-fast: false` 必须保留。** matrix 默认 `fail-fast: true`：一个分片失败
   会取消其余分片 ⇒ 被取消分片的失败集合同样是空的 ⇒ 又一次假「净新增 0」。
8. **CI 结果要写进变更记录**（`changes/<feature>/summary.md`）：基线 runId、PR runId、
   逐 job 结论、失败集合条数、净新增/净丢失明细。没有这些数字 = 没有对差 = 不可合并。
9. **威胁模型（必须如实理解，别把工具当「绝对防线」）** —— 失败集合对差工具
   **读的是 pytest 的 stdout**，而 stdout 由 PR 作者可控（测试里可以 `print`）。
   ⇒ 工具能可靠挡住的是**偶然**的假绿：
   `cancelled` / 夭折（`os._exit`）/ OOM 杀死 / 被信号杀死 / 空分片收全树 /
   改 `conftest` 或 pytest 配置把失败用例跳过 / 改 workflow 让两次 run 跑的不是同一批 job。
   ⇒ 工具**挡不住**的是**敌意**的伪造：作者可以伪造收尾汇总行、伪造 `FAILED` 行、
   甚至杀死 CI shell 后自己打印一条看起来合法的完成标记。
   ⇒ **合并授权的落点必须是人**，不是工具：
   - **保护分支 + 必需状态检查**（PR 不得直接推 main）；
   - **`.github/CODEOWNERS`**：`.github/workflows/` 与 `backend/app/utils/ci_*.py`
     必须由 CODEOWNER 复核（改这些 = 改判据本身）；
   - 工具的 `MERGEABLE` 结论是**必要条件**，不是充分条件。

   ⚠️ 因此「工具说可合并」**不等于**「可以合并」。判据是**对差**，
   对差证明的是「**没有净新增失败**」，证明不了「没有被人为伪造」。
10. **已知抖动白名单：让「结论不确定的用例」不再充当判据。**

    **事故教训**（PR #107，2026-11-06）：闸门判据是「失败集合对差」
    ⇒ **任何一个用例在两侧的「失败与否」不同，就一律拦下**。
    而 `app/tests/integration/test_reconcile_milvus_id_mapping.py::test_backfill_is_idempotent`
    因 Milvus 可见性竞态**随机红** ⇒ 同一份代码、两次 run 给出不同结论
    ⇒ 按「两侧独立同分布、每侧失败概率 p」估算，闸门因它误拦的概率是 `2p(1-p)`；
    实测 p≈0.5 ⇒ **约一半的 PR 被随机挡下** ⇒ 每次都要人工做三件套证伪。

    ⇒ 白名单文件：**`.github/ci-known-flaky-tests.json`**
    （放在 `.github/` 下 ⇒ 与 CODEOWNERS 同处 ⇒ 授权面一眼可见）
    ⇒ 条目形如
    `{"nodeId": "<精确 node ID>", "reason": "<为什么信它>", "since": "YYYY-MM-DD"}`
    ⇒ **对称豁免**：命中的用例从**两侧**失败集合里都剔除，**再**对差。

    四条硬约束（**不得放宽**）：

    | # | 约束 | 落地 |
    |---|---|---|
    | 1 | **精确 node ID**，不豁免文件 / 前缀 / 通配 | 加载时校验必须含 `::`；文件级 ID（收集期错误）**不豁免** ⇒ 宁可漏豁免，不可错豁免。⚠️ 校验必须用 `fullmatch`（**不是** `^...$`）：Python 的 `$` 匹配末尾换行**之前** ⇒ `"a.py::t\n"` 能过校验却永远匹配不到任何真实失败 ID ⇒ 条目**静默失效** |
    | 2 | **失败关闭** | 白名单读不到 / JSON 非法 / 条目不合规 ⇒ **退出码 3** ⇒ **绝不**退化成「空白名单」（判据读不出来 ⇒「不知道」不等于「没有」）。加载器只捕**一类**异常 ⇒ 别的异常形态（`OSError` / `KeyError` …）也必须落到同一个失败关闭出口 |
    | 3 | **只许 main 上 CODEOWNER 维护** | 文件属于「CI 相关面」（改它 = 改判据 ⇒ 退出码 6）**且**闸门 workflow **显式** checkout 默认分支 ⇒ **PR 不能给自己开豁免** |
    | 4 | **豁免条件化在「该用例所在文件本次未被改动」** | PR 改了那个文件 ⇒ **不豁免** ⇒ 该用例照常计入判据 ⇒ 闸门拦下，并明示「**豁免未生效**」（不静默）。⚠️ 该判据只依赖「改了哪些文件」（服务端事实）⇒ **不引入随机阻塞**。⚠️ 两套路径基准必须对齐：node ID 里是 **rootdir 相对**（`app/tests/...`），compare API 给的是**仓库相对**（`backend/app/tests/...`） |

    ⚠️ **改名也算「CI 相关面改动」**：GitHub compare API 对一次改名**只给一个条目**
    （新路径在 `filename`、旧路径在 `previous_filename`）⇒ 只取 `filename` 的话，
    把 `.github/ci-known-flaky-tests.json` 改名就**不再出现在改动清单**里
    ⇒ 「CI 相关面」守卫看不到 ⇒ **静默绕过**退出码 6 的人工仲裁
    ⇒ 改动清单必须**同时**收 `filename` 与 `previous_filename`（去重）。

    ⚠️ **豁免只影响「对差」**：不可用 job 判定 / 覆盖等价 / CI 相关面 / run 新鲜度
    **都不看**白名单 ⇒ 白名单**不能**用来掩盖「job 没跑完」「少跑了分片」「改了 conftest」。
    ⚠️ **对称豁免的代价（必须承认）**：PR 侧若**确定性**弄红了一个白名单用例，
    闸门也不会拦它 ⇒ 兜底是**每次豁免都出现在报告里**（含「PR 侧命中」的 ⚠ 明示）
    ⇒ 该用例的确定性红会立刻体现在 main 的 CI 上（人看得到）。
    ⚠️ **理由必须写清楚**（「为什么信它」是审计依据）⇒ 空理由 = 无授权 ⇒ 加载器直接拒绝。

    **条目的四个字段（全部必填，缺一即加载失败 ⇒ 退出码 3）**：

    | 字段 | 约束 | 为什么必填 |
    |---|---|---|
    | `nodeId` | **精确 node ID**，含 `::`；文件级 / 前缀 / 通配**一律拒绝** | 爆炸半径 = 1 个用例 |
    | `reason` | 非空字符串 | 「为什么信它」是**审计依据**；空理由 = 无授权 |
    | `since` | **必填**，`YYYY-MM-DD`，且必须是**真实存在的日历日期**、**不得在未来** | 签发日期是**老化审查**的锚点；可选 ⇒ 永远没人回头看它。⚠️ 只用正则校验会让 `2026-02-30` 过 ⇒ 它一路活到**渲染报告**时 `date.fromisoformat` 才抛 ⇒ 闸门对**全仓每个 PR** 都以「渲染报告失败」结束（退出码 3）⇒ 判据整体瘫痪且报错指向错误方向 ⇒ 日历合法性必须在**加载期**校验。⚠️ 未来日期 ⇒ 该条在老化上限内**永不老化** ⇒ 老化机制对它彻底失效 |
    | （隐含）`entries` | 顶层 `{"entries": [...]}`，每条一个对象 | 形状固定 ⇒ 加载器可一次校验到位 |

    **老化上限 180 天**（`ci_flakes.MAX_ENTRY_AGE_DAYS`）：超过上限的条目在报告里带 ⚠「老化」
    ⇒ **不是**自动失效（自动失效 ⇒ 抖动被修好后突然拦人 ⇒ 又变成随机阻塞），
    而是**逼人回头看它**：抖动早就修好了 ⇒ 就该把这条删掉。
    ⚠️ `since` **必须必填**：没有签发日期的条目**没有老化锚点** ⇒ 永久有效 ⇒ 白名单只会单调增长。

    **可见性义务（豁免不许静默）** —— 四处，缺任一处即视为实现不合规：

    1. **报告正文**：「已知抖动豁免 N 条」段 ⇒ 逐条列 node ID / 出现侧（基线侧 / PR 侧 / 两侧）/
       理由 / **签发日期 `since`**；PR 侧命中额外 ⚠；超过 180 天额外 ⚠「老化」。
    2. **报告头部**：同时给「原始失败条数」与「计入对差的条数」⇒ 差额由豁免明细解释，
       不许靠「加法还原」蒙混（渲染层不做还原 ⇒ 原始条数**显式传参**）。
    3. **check 标题**：GitHub 上人第一眼看到的是**标题**不是正文 ⇒ 标题里带**豁免条数**
       （PR 侧新增红时额外点明「PR 侧命中，请人工确认」）。
       ⚠️ **标题必须走独立文件**（工具写 `--gate-title-file <path>`，workflow 再写进
       check 的 `title`）⇒ **不得**从人读的报告正文里 `grep` 标题
       ⇒ 报告是给人读的文本 ⇒ 改一下渲染（加缩进、换前缀、把标题挪到会被截断的尾部）
       就**静默失效** ⇒ 豁免提示从标题消失 ⇒ **真相被盖住**且无人察觉。
       ⚠️ 标题写盘失败必须**响亮失败**（退出码 3）且**不得**自动建父目录
       （路径写错必须立刻暴露）。
       ⚠️ **不能改成 `neutral` 来「真拦人」** —— GitHub 的 required check 把 `neutral`
       视为**通过** ⇒ 改 neutral 并不真拦；而任何「PR 侧命中就拦」的规则都会
       **重新引入随机阻塞**（那正是 B7 要消除的东西）⇒ 只能**最大化可见性**。
    4. **未命中提示**：白名单里写了但本次没命中的条目 ⇒ 报告里明示「未命中 N 条」
       ⇒ 拼错 node ID / 条目已失效 / 抖动已修好 ⇒ 都能看见，而不是悄悄躺着。
    5. **「豁免未生效」提示**：命中白名单但因「文件被改动」而**没有**豁免 ⇒ 必须明示
       ⇒ 否则读者会以为「这条豁免了」，而它其实照常计入判据。

    ⚠️ **两套截断单位必须统一到字节**：渲染层与 workflow 摘要窗口若一个按行、一个按字节
    ⇒ 报告自认「我没超上限」而 workflow 仍砍尾 ⇒ **证据被静默挤出摘要**。
    ⇒ 工具侧 `MAX_REPORT_BYTES = 20000`（**由工具负责截断并明示**，提示插在**头部第 2 行**
    ——尾部会被自己砍掉）；workflow 摘要窗口 `head -c 30000`（**只搬运，不二次截断**）
    ⇒ 窗口必须**宽于**报告上限。
    ⇒ 展示顺序固定为：header → 原因 → 提示 → **净丢失 → 净新增 → 豁免 → job 明细**
    （**证据优先于说明** ⇒ 尾部砍时最后受损的是说明）。

    **「PR 侧命中」的人工确认义务**：对称豁免意味着 PR 侧**确定性**弄红白名单用例也不拦
    ⇒ 因此这类改动**必须**由人工确认「这个红是抖动、不是这次改动引入的」，
    且**确定性红会在 main 的 CI 上立刻暴露**（豁免只在 main 生效 ⇒ main 上照红）⇒ 人看得见。

    ⚠️ **CI 相关面必须覆盖「守卫自身」**：白名单机制的唯一防线是**守卫用例**，
    而守卫用例文件与 `.github/CODEOWNERS` 属于「CI 相关面」
    ⇒ **改守卫 = 解除守卫** ⇒ 改它们 ⇒ 退出码 6 ⇒ 必须人工仲裁。

## 前端变更部署（必走 `docker compose build`）

**事故教训**（feat-user-auth，2026-09-20）：前端改动后 4 次「重建」都只在**本地沙箱**
跑 `cd frontend && npm run build`，把 `frontend/dist/` 写进**宿主机文件系统**——
容器内 nginx serve 的 `/usr/share/nginx/html` 来自**镜像构建时** `COPY --from=build /app/dist`，
**从未被刷新**。用户每次 hard refresh 看到的还是几天前 `docker compose build` bake
进去的旧 bundle（hash 比如 `index-BMm9puG4.js`），前端代码改动对用户**完全不可见**，
反复误导「明明代码改了为什么浏览器还报错」。本地 `frontend/dist/index-r3i6ixut.js`
与 nginx 服务的 bundle 是**两份完全不同的文件**，用「本地 build 是否通过」判断
「前端是否生效」是**错的心智模型**。

**规则**：

1. **任何**前端代码 / `.env` 里 `VITE_*` 变量改动后，部署命令必须包含镜像重建步骤：
   ```bash
   docker compose -f docker/docker-compose.yml build --no-cache frontend
   docker compose -f docker/docker-compose.yml up -d frontend
   ```
   不允许用 `docker cp frontend/dist qa-frontend:/usr/share/nginx/html` 临时覆盖
   （重建容器即回退；属于「看起来生效了」的反模式，详见 `fix-nginx-upstream-stale-ip`
   §3 的同类教训）。**也不允许**只跑 `cd frontend && npm run build` 后声称「前端已重建」。

2. **VITE_API_BASE_URL 默认指向 nginx 5173，不是 backend 8000**：
   - `docker/.env` 里 `VITE_API_BASE_URL=http://localhost:5173/api/v1`（走 nginx 反代）
   - 不写 `http://localhost:8000/api/v1`（绕过 nginx 直连 backend）。后者在 nginx
     剥离客户端伪造头（feat-user-auth §nginx）的策略下完全失效；axios baseURL
     直连 8000 时 nginx 拦截与 `X-User-*` 头过滤都不起作用。
   - `VITE_*` 是**构建期烘焙**进 bundle 的（不是运行时），改 `.env` 后必须重建镜像。

3. **诊断命令**（任何「前端已改但用户看不到」先跑这三步）：
   ```bash
   # (a) 容器里 dist/ 实际的 bundle hash
   docker exec qa-frontend ls /usr/share/nginx/html/assets/ | grep index-.*\.js

   # (b) 宿主机本地 dist/ 的 bundle hash
   ls frontend/dist/assets/ | grep index-.*\.js

   # (c) nginx serve 出去的入口 HTML 引用的 hash
   curl -s http://localhost:5173/ | grep -oE 'index-[A-Za-z0-9_-]+\.js'
   ```
   三个 hash 必须**完全一致**。(a) ≠ (c) 即镜像未重建；(b) ≠ (c) 即本地 build 未进
   容器；(a) = (c) 但浏览器 console 还看到旧 hash 即浏览器 / 代理缓存（少见，nginx
   `index.html` 已 `Cache-Control: no-cache`，通常硬刷即可）。

4. **`docker compose up -d frontend` 不重建镜像**：它只重启现有容器，原镜像层不变。
   「改完前端只跑 `up -d` 不生效」是同类事故的高频陷阱，必须 `build --no-cache` 再 `up -d`。

5. **后端变更也适用同规则**：后端代码改动后必须 `docker compose build --no-cache backend && up -d backend`；
   单纯 `docker cp backend/app qa-backend:/app/app` 是临时覆盖（详见 memory
   `qa-system-docker-cp-merge`），重建容器即回退，且 cp 容易漏 alembic 迁移导致 uvicorn
   起不来。

**与其他规则的关联**：
- 与 [变更记录强制规范 §5 真实数据验证](./变更记录强制规范.md) 互补——真实数据验证
  跑通 ≠ 用户能看到新前端行为，部署是另一道门。
- 与 [数据备份策略](./数据备份策略.md) 互补——前端部署不破坏数据，但 nginx
  `dist/` 与本地 `dist/` 错位会让所有前端回归测试失去意义。
- 与 `fix-nginx-upstream-stale-ip`（容器重建后 nginx 缓存旧 backend IP）属同一类
  「容器/IP/bundle 状态漂移」教训，共用诊断流程。
