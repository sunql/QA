# 工程结构规范

## 目录布局

```
qa-system/
├── backend/   # FastAPI 后端
├── frontend/  # React + Vite 前端
├── docker/    # Docker Compose 与 Dockerfile
├── Harness/   # 架构治理系统
└── docs/      # 设计文档
```

## 后端分层

严格分层，依赖方向：`api -> services -> domain`，`services -> infrastructure`。禁止反向依赖。

| 层 | 路径 | 职责 |
|----|------|------|
| api | `app/api/v1/` | HTTP 路由、DTO 序列化、依赖注入 |
| services | `app/services/` | 业务编排、领域逻辑、事务边界 |
| domain | `app/domain/` | 模型（ORM）、枚举、Schema、异常 |
| infrastructure | `app/infrastructure/` | 数据库、LLM 客户端、Token 计数、安全 |

## 文件规模

- 单文件 200-400 行为宜，**硬上限 800 行**。
- 函数 < 50 行。
- 嵌套 ≤ 4 层（用早返回降低嵌套）。
- 高内聚低耦合，按领域组织而非按类型。

## 命名

- 后端 Python 包：`app`，模块文件 `snake_case.py`。
- 后端代码内部：函数/变量 `camelCase`，类型 `PascalCase`，常量 `UPPER_SNAKE_CASE`。
- ORM 列与 Pydantic 字段：`snake_case`（与 DB 列及 JSON 契约对齐，刻意偏离）。
- JSON 输出：`camelCase`（由 `CamelModel.alias_generator` 保证）。
- 前端：组件 `PascalCase`，hooks `useXxx`，工具 `camelCase`。

## Schema 漂移防护（强制 CRITICAL）

**问题（实踩事故）**：ORM `Base.metadata` 新增了表/列，但生产 DB 没跑 `alembic upgrade head`，
应用启动后第一个查询就抛 `asyncpg.exceptions.UndefinedTableError: relation "X" does not exist`。
原因：lifespan 仅建引擎，未校验 DB schema 与 ORM 一致性；本地 `uvicorn` 启动绕过了 docker
entrypoint 的 `alembic upgrade head && uvicorn` 链。

**强制要求**：

1. **本地开发 / 部署 / 测试任何场景下，必须先执行 `alembic upgrade head` 再启动应用**。
   - Docker：`Dockerfile.backend` 已固化 `alembic upgrade head && uvicorn ...`。
   - 本地 venv：`uv run alembic upgrade head && uv run uvicorn app.main:app`。
   - 集成测试：`app/tests/_pg_support.py` 的 `_ensureSchema` 已自动 `alembic upgrade head`。
2. **应用启动时强制 schema drift 校验**：`app/main.py` 的 `lifespan` 在启动时调用
   `scripts/check_schema_drift.py:_checkDrift`，对比：
   - Alembic head（最新迁移 revision）vs DB `alembic_version` 当前值
   - ORM `Base.metadata.tables` vs DB `pg_tables` 表集合
   任意一项不一致即 `RuntimeError` 阻断启动，错误信息直指「执行 alembic upgrade head」。
3. **紧急回滚兜底**：可通过 `SKIP_SCHEMA_CHECK=1` 跳过校验。**禁止日常开发使用**，
   仅紧急回滚 + 旧镜像兼容（如老 DB 与新代码不匹配、临时降版本）才允许。
   该环境变量必须出现在 PR 描述与 change summary 中，否则视为违规。

**为什么这样设计**：
- 「ORM 引用但 DB 缺表」是「启动期可检测」的错误（不像「列类型不匹配」要等查询触发）。
  fail-fast 让 CI/部署立刻拒绝，而不是线上 5xx。
- ORM vs Alembic 双轨检查：Alembic 版本滞后捕获「差一个 migration」；ORM 表 vs DB 表捕获
  「开发改了模型忘了写迁移」或「手动 DROP 了表」。
- 不动 DB（只读 SELECT `pg_tables` / `alembic_version`），与现有「SQL 业务库只读护栏」精神一致。

**本地调试 schema drift**：

```bash
cd backend
uv run python scripts/check_schema_drift.py --database-url $DATABASE_URL
# 退出码 0 = OK；1 = 漂移；2 = 参数/连接错误
```

**CI 门禁建议**：在 `unit-test-ci` 技能里加一步：

```bash
TEST_DATABASE_URL=... uv run python scripts/check_schema_drift.py \
    --database-url $TEST_DATABASE_URL --strict
# --strict 让「多余表」也算漂移（CI 必须零容忍）
```

**变更流程**：
- 新增 / 修改 ORM 模型：必须在同一 PR 中包含对应 Alembic 迁移（`alembic/versions/00XX_*.py`）。
- 迁移 review 检查项：`down_revision` 指向当前 head；`upgrade()` 创建表/列与模型一致；
  索引、CheckConstraint、外键与模型 `__table_args__` 一致；`downgrade()` 可逆。
- 严禁「先发 PR 加模型不写迁移，下一次再补」——会立即被启动校验阻断。
