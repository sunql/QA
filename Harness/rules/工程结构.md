# 工程结构规范

## 目录布局

```
qa-system/
├── backend/   # FastAPI 后端
├── frontend/  # React + Vite 前端
├── docker/    # Docker Compose 与 Dockerfile
├── Harness/   # 架构治理系统
└── docs/      # 设计文档
```

## 后端分层

严格分层，依赖方向：`api -> services -> domain`，`services -> infrastructure`。禁止反向依赖。

| 层 | 路径 | 职责 |
|----|------|------|
| api | `app/api/v1/` | HTTP 路由、DTO 序列化、依赖注入 |
| services | `app/services/` | 业务编排、领域逻辑、事务边界 |
| domain | `app/domain/` | 模型（ORM）、枚举、Schema、异常 |
| infrastructure | `app/infrastructure/` | 数据库、LLM 客户端、Token 计数、安全 |

## 文件规模

- 单文件 200-400 行为宜，**硬上限 800 行**。
- 函数 < 50 行。
- 嵌套 ≤ 4 层（用早返回降低嵌套）。
- 高内聚低耦合，按领域组织而非按类型。

## 命名

- 后端 Python 包：`app`，模块文件 `snake_case.py`。
- 后端代码内部：函数/变量 `camelCase`，类型 `PascalCase`，常量 `UPPER_SNAKE_CASE`。
- ORM 列与 Pydantic 字段：`snake_case`（与 DB 列及 JSON 契约对齐，刻意偏离）。
- JSON 输出：`camelCase`（由 `CamelModel.alias_generator` 保证）。
- 前端：组件 `PascalCase`，hooks `useXxx`，工具 `camelCase`。

## Schema 漂移防护（强制 CRITICAL）

**问题（实踩事故）**：ORM `Base.metadata` 新增了表/列，但生产 DB 没跑 `alembic upgrade head`，
应用启动后第一个查询就抛 `asyncpg.exceptions.UndefinedTableError: relation "X" does not exist`。
原因：lifespan 仅建引擎，未校验 DB schema 与 ORM 一致性；本地 `uvicorn` 启动绕过了 docker
entrypoint 的 `alembic upgrade head && uvicorn` 链。

**强制要求**：

1. **本地开发 / 部署 / 测试任何场景下，必须先执行 `alembic upgrade head` 再启动应用**。
   - Docker：`Dockerfile.backend` 已固化 `alembic upgrade head && uvicorn ...`。
   - 本地 venv：`uv run alembic upgrade head && uv run uvicorn app.main:app`。
   - 集成测试：`app/tests/_pg_support.py` 的 `_ensureSchema` 已自动 `alembic upgrade head`。
2. **应用启动时强制 schema drift 校验**：`app/main.py` 的 `lifespan` 在启动时调用
   `scripts/check_schema_drift.py:_checkDriftAsync`，按三层粒度对比，**全部只读**：
   - **迁移级**：Alembic head（最新迁移 revision）vs DB `alembic_version` 当前值
   - **表级**：ORM `Base.metadata.tables` vs DB `pg_tables` 表集合
   - **列 / 索引级**：ORM `Column` vs `information_schema.columns`；
     ORM `Index` / `UniqueConstraint` vs `pg_index`（列序 + 唯一性 + 约束归属）

   每条漂移携带严重级，`_SEVERITY_BY_CODE` 是**单一事实源**，CLI 与 lifespan 共用
   `_splitBySeverity` 切分，不得各自判定：

   | 严重级 | 判定 | 处置 |
   |---|---|---|
   | **blocking** | 迁移版本滞后；ORM 声明而 DB 缺 **表 / 列 / 索引**；同名索引列序不一致 | `RuntimeError` 阻断启动 |
   | **warning** | DB 有而 ORM **未声明**的表 / 列 / 索引 | 仅记 WARNING 日志，放行 |

   **只有 blocking 非空才阻断。** 理由：blocking 那类必然导致运行时
   `relation/column does not exist`；而 DB 多出来的对象是历史残留（手工 DDL、旧迁移遗留、
   已废弃特性），既不影响正确性，又是**唯一可能装着真实数据**的东西 —— 判成阻断等于
   让线上起不来，且会诱使运维直接 `SKIP_SCHEMA_CHECK=1` 把整道防线废掉。
   warning 不是「没事」：它必须出现在启动日志里，由人决定是否补迁移 / 补 ORM 声明 / 清理。

   **索引比较的两条归一化规则**（不做则会产生上百条假阳性，防线当场失效）：
   - PG 为每个 PK / `UniqueConstraint` 都建了支撑索引；ORM 侧 `UniqueConstraint` 通常
     **无名**（`name=None`）而 DB 侧叫 `uq_xxx`。故**约束支撑的索引必须按列集合匹配**
     （`OrmTableShape.uniqueColumnSets`），不能比名字。
   - 表达式索引（`lower(x)`、`text("x DESC")`）在 `pg_index.indkey` 里 attnum=0，
     读出来是哨兵 `<expr>`，无法与列名比 —— 两侧任一为表达式即**跳过列比较**，不比不报。
3. **紧急回滚兜底**：可通过 `SKIP_SCHEMA_CHECK=1` 跳过校验。**禁止日常开发使用**，
   仅紧急回滚 + 旧镜像兼容（如老 DB 与新代码不匹配、临时降版本）才允许。
   该环境变量必须出现在 PR 描述与 change summary 中，否则视为违规。

**为什么这样设计**：
- 「ORM 引用但 DB 缺表/列/索引」是「启动期可检测」的错误（不像「列类型不匹配」要等查询触发）。
  fail-fast 让 CI/部署立刻拒绝，而不是线上 5xx。
- **粒度必须到列 + 索引**：2026-09-12 那两库漂移（`qa_metadata` vs `qa_metadata_test`）
  **全部是列级与索引级**——迁移链里漏了一条 `CREATE INDEX IF NOT EXISTS`、4 个死列只在一边。
  当时只比表集合的校验器**完全静默**，漂移直到写测试断言才发现。
- 三级互补：Alembic 版本滞后捕获「差一个 migration」；表级捕获「改了模型忘了写迁移」或
  「手动 DROP 了表」；列 / 索引级捕获「迁移里少建了一个索引」这类表级看不见的缺口。
- 不动 DB（只读 `pg_tables` / `information_schema` / `pg_index` / `alembic_version`），
  与现有「SQL 业务库只读护栏」精神一致。

**同类别的多条问题聚合成一行**：库里现存 24 个 ORM 未声明的遗留索引，逐条打印会刷屏 →
告警疲劳 → 有人直接 `SKIP_SCHEMA_CHECK=1`。`_formatIssues` 按 code 聚合，一行列出全部对象名。

**本地调试 schema drift**：

```bash
cd backend
uv run python scripts/check_schema_drift.py --database-url $DATABASE_URL
# 退出码 0 = 无 blocking（可能仍有 warning）；1 = 有 blocking，或带 --strict 时存在任意漂移；
#        2 = 参数/连接错误
```

**CI 门禁建议**：在 `unit-test-ci` 技能里加一步：

```bash
TEST_DATABASE_URL=... uv run python scripts/check_schema_drift.py \
    --database-url $TEST_DATABASE_URL --strict
# --strict 把 warning 也升级为门禁（CI 必须零容忍）。
# 注意：现存 24 个遗留索引会让 --strict 在干净测试库上直接失败 ——
# 启用前需先决定这批索引的去留（补进 ORM / 补迁移 / 建基线豁免名单）。
```

**变更流程**：
- 新增 / 修改 ORM 模型：必须在同一 PR 中包含对应 Alembic 迁移（`alembic/versions/00XX_*.py`）。
- 迁移 review 检查项：`down_revision` 指向当前 head；`upgrade()` 创建表/列与模型一致；
  索引、CheckConstraint、外键与模型 `__table_args__` 一致；`downgrade()` 可逆。
- 严禁「先发 PR 加模型不写迁移，下一次再补」——会立即被启动校验阻断。
