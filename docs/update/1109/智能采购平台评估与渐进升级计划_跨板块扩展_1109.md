# 智能采购平台评估与渐进升级计划（跨板块扩展版）

> 本文修订并取代《智能采购平台需求评估_代码基线核查_1109.md》的结论口径，新增两个硬约束：
> **① 基础设施软件版本一律使用现场当前版本，不升级；② 采购只是试点，系统必须可平滑扩展到其他业务板块。**
> 代码基线：`origin/main` @ `40a8497d`（2026-11-09）。原则：以代码为准，与冻结报告不一致处标注并给出修订建议。

---

## 1. 硬约束（红线）

| 约束 | 具体含义 |
|---|---|
| **版本冻结** | 现场实测：PostgreSQL 16.15、Neo4j 5.23-community、etcd 3.5.5、Milvus 2.4.6、MinIO（2024-06-13 / 2023-03-20 两套）、**Docker 19.03.9 + docker-compose 1.29.2（v1 二进制，无 `docker compose` 子命令）**；MySQL 容器当前未运行。全部维持现场版本，**不升级** |
| **不新增中间件** | 不引入 Kafka / Redis / RabbitMQ / Elasticsearch 等新组件；异步一律走「数据库 outbox + 现有 Worker 容器」模式（`research_event_outbox` 已有先例） |
| **平滑不破坏** | 每个阶段独立可发布、可回滚；现有接口、现有页面、现有语义不变；数据库只做**加法**（新表/新可空列），不做破坏性 DDL |
| **多板块优先** | 新增的表、接口、命名一律**领域无关**；采购专属内容只允许存在于数据（`data_domain` 行、BO 映射、审批矩阵配置）与薄适配层，不写进核心代码 |

## 2. 结论：能不能满足？

**能，且无需升级任何基础设施版本。** 九个专题全部有真实实现，采购试点与后续板块扩展共用同一套本体/指标/知识/Agent 底座。逐能力判断：

| 目标能力 | 现有支撑（代码位置） | 类型 | 冻结版本下可行 |
|---|---|---|---|
| 采购知识问答（SQL + 图谱 + 文档） | `nl2sql_*`、`graph_traversal.py`、`rag_service.py` | A/B | ✅ |
| 供应商画像 / 评价 / 寻源 | `supplier_360.py`、`supplier_risk.py`、BO/指标体系 | A/B | ✅ |
| 本体治理与语义发布 | `ontology_service.py`（治理表 CRUD 完整） | C+D | ✅（发布层新增） |
| 语义查询（Registry 驱动） | `nl2sql_schema.buildSchemaText` 干净注入点 | B | ✅ |
| 只读 Agent / Copilot | 工具白名单 + `AgentAccessPolicy` + 只读 Worker | A/B | ✅ |
| 工作流 / 审批 / 业务指令（写） | **无**（需新增） | D | ✅（PG 状态机 + 现有 Worker，无需新中间件） |
| 多源 / 复合键绑定 | 单源字段 + `EntityMapping`（已有生效期） | D+B | ✅ |
| **扩展其他业务板块** | `data_domain` 注册表 + `BusinessObject.primary_domain_id` + `BusinessObjectDomain` + `agent_definition.data_domains` | B | ✅（新板块=新增数据，不改代码） |

**两个前提**（不满足则会返工）：
1. 发布快照必须**自包含**（编译产物落库）——现有本体的 `version/valid_from/valid_to` 是 Phase 6 移除版本管理后的**兼容残留**，不能承载发布语义（见 §7）。
2. 多板块扩展必须在**命名与作用域**层面从一开始就通用化（见 §4）。

### 部署路径（P0-D1 已实测拍板：Compose v1）

现场是 **docker-compose 1.29.2（v1 二进制）**，且生产**并不使用仓库里的 centos overlay**：

| 事实 | 结论 |
|---|---|
| 生产入口 | `docker-compose -p qa-system --env-file /opt/qa-system/docker/.env -f /opt/qa-system/docker/docker-compose.centos7.yml "$@"` |
| 仓库 `docker/docker-compose.centos.yml` | 用了 `!override`（需 ≥2.24）与 `profiles`（v2）⇒ **生产不可用，不得作为部署依据** |
| 后端/前端镜像 | 离线镜像手工 `docker load` + `docker tag`（`qa-backend:offline`、`qa-system_frontend`） |
| 仓库外服务 | 生产还有 `qa-ollama-https`（nginx TLS 代理），仓库 compose 中没有 |

⇒ **P5 新增 Worker/服务：写 v1 兼容的 compose 片段追加到 `/opt/qa-system/docker/docker-compose.centos7.yml`（或显式 `docker-compose run`），走离线镜像 runbook，首次部署前 `config --quiet` 校验。禁止依赖 `!override` / `profiles` / `docker compose` 子命令。**

另：`ollama/ollama:latest` 属版本漂移风险，处置是**记录当前 image ID**（锁定现状，不升级）。

## 4. 多板块扩展设计原则（系统级）

### 4.1 现成锚点：域已经是一等公民

代码中已有完整域模型，新板块无需新建概念：

- `data_domain(code, name, primary_org_id, description, enabled)` —— 域注册表（DB SSOT，`dataDomainRegistry` 预热）；
- `business_object.primary_domain_id`（必填，一个本体类只允许一个 BO 作 header）+ `business_object_domain`（附域）；
- `agent_definition.data_domains`（JSONB，Agent 授权域词表）。

⇒ **接入一个新板块 = 新增 `data_domain` 行 + 给该域挂 BO/本体/指标 + 编译一次发布 + 绑定 Agent**。理论上零代码。

### 4.2 命名与作用域规则（写入评审清单）

1. **新表/新接口不带 `procurement` 前缀**：
   - 发布表命名 `semantic_release`（`domain_code` 可空：`NULL` = 全企业快照，首期即用此形态；非空 = 未来按域独立发布）；
   - 通用接口 `/api/v1/semantic/*`（发布、查询、知识服务）；
   - 若试点必须遵守冻结报告的 `/api/v1/procurement/*` 契约，只做**薄别名适配**（固定 domain 参数转发到通用 Facade），业务逻辑一律在通用层。
2. **采购专属内容只许是数据**：审批矩阵、寻源规则、评价指标配置都落在 `definition_json` / 配置表，不写死常量。
3. **发布快照自包含**：`manifest_json` + 确定性 `manifest_hash` 落库，消费方只读快照，不依赖治理表当前状态。
4. **指标两层 SSOT（代码已定，正式入档）**：`ontology_metric` = 技术形态（SQL 生成用），`kpi_catalog` = 业务治理视角，二者经 `metric_id` 弱关联（源码 docstring 明写「业务定义可先行，技术实现后置」）。Manifest 的 `metrics` 段 = 技术口径 + 可选治理引用；**不要再造第三套指标模型**。
5. **Registry 永远不是硬依赖**：任何消费方在开关关闭或无激活发布时，必须回落到直读治理表（现状路径）。
6. **每个阶段必须有「第二域 dry-run」证据**：用数据而非代码证明扩展性。

## 5. 目标分层（只新增一层运行时依赖）

```
治理层（PG 现有表：ontology_class/property/join/metric、business_object、data_domain、kpi_catalog）
        │  （唯一写入口不变）
   Semantic Compiler（新增，离线/发布时运行）
        │
   semantic_release（新增表：自包含 manifest + hash + 状态机）
        │
   Semantic Registry（新增只读服务；开关门控；无发布时回落直读）
        │
 ├─ NL2SQL（buildSchemaText 注入点）
 ├─ RAG（权限/域/有效期过滤）
 ├─ Neo4j 镜像（按发布重建/校验）
 ├─ Agent Run（快照固定 release_id）
 └─ Knowledge Facade（跨域通用）
        │
   采购试点薄适配（/api/v1/procurement/* → 通用 Facade）
```

## 6. 渐进升级计划（P0–P6，每阶段独立可发布可回滚）

> **日级排程（D1–D62，每天有产出与完成定义）见《智能采购平台升级计划_日级排程_1109.md》。**
> 规模标注：S ≈ 数天，M ≈ 1–2 周，L ≈ 数周；P0 现场核验后再做正式人日重估。
> 所有阶段共同约束：开关默认关闭（沿用 `ENABLE_AGENT_ORCHESTRATION` 的「关则不注册路由、不 import 模块」模式）、只做加法 DDL、手写迁移。

### P0 —— 基线冻结与四项裁决（无代码，规模 S）

- **现场核验清单**：生产 Docker/Compose 版本；各镜像实际 digest；`alembic current`；Neo4j 回填状态与标签统计；Milvus 各 collection 实际 schema 与数据量；ERP/SRM/OA/合同系统接口可用性；各业务表数据量。
- **四项裁决（不裁决就返工）**：
  1. 发布快照自包含（不建在 `version/valid_from/valid_to` 上）；
  2. 多源绑定与现有 `source_table/source_column` 单源字段的 SSOT 关系（建议：绑定生效后治理表字段降级为默认值，由守卫钉住）；
  3. 指标两层模型正式入档（§4.2-4）；
  4. `SemanticManifest` 改名 `SemanticReleaseManifest`（与现有 `RelationManifest` 区分）+ 发布域作用域（首期全局 `domain_code=NULL`）。
- **产出**：R01/R02/R03 v1.1、ADR 增补（ADR-003/004/007/008）。
- **现有功能影响**：无。

### P1 —— 发布骨架（纯新增，开关关闭，规模 M）

- **新增表（加法）**：`semantic_release`（`id`、`domain_code` 可空 FK→`data_domain.code`、`version`、`status` DRAFT/VALIDATED/ACTIVE/ARCHIVED、`schema_version`、`manifest_json` JSONB、`manifest_hash`、`created_by`、`created_time`、`activated_time`、`note`）。
- **服务**：Compiler（读治理表 → Manifest）、JSON Schema 校验、规范化 JSON 的 SHA-256 确定性哈希、activate/rollback（指针翻转）、版本 diff。
- **接口**：`/api/v1/semantic/releases`（list/get/publish/activate/rollback/diff），`ENABLE_SEMANTIC_RELEASE=false` 门控。
- **验收**：当前本体生成的 golden Manifest 固定；同输入哈希稳定；发布/激活/回滚/降级回放通过；**不触碰任何消费方**；既有测试失败集合净新增 0。
- **回滚**：关开关；表保持惰性。
- **现有功能影响**：零（新代码路径未被任何现有调用方引用）。

### P2 —— NL2SQL 影子接入（双路径，规模 M）

- **注入点**：新增 `semantic_registry_service.loadClassesForSchema(domain?)`；`nl2sql_service` / `nl2sql_plan` 的 `buildSchemaText` 入参改为经该服务获取。开关关闭或无激活发布 ⇒ 直读治理表（现状行为）。
- **影子期**：同一请求并行计算「快照 schema 文本」与「直读 schema 文本」，比对并记录差异，**仍使用直读结果**；差异为 0 后才允许切换。
- **切换**：内部用户先行；请求/运行记录挂 `semantic_release_id`（可空列，加法）。
- **验收**：现有 NL2SQL 单测 + 生产采集问题样本的回放结果与切换前一致；SQL Guard 链原样保留；chat/multistep 失败集合净新增 0。
- **回滚**：关开关 ⇒ 立即回到直读。
- **注意**：`agent_tools_nl2sql.py`、`chat_recall.py` 等仍有直读 `OntologyClass` 的调用点，P2 只改主 NL2SQL 路径，其余在 P3 逐个处理——这正是「避免一次大改」的关键。

### P3 —— 其余消费面逐个接入（每个子项独立发布，各规模 M）

| 子项 | 内容 | 切换条件 |
|---|---|---|
| 3a RAG | 检索前增加域/实体/组织/有效期过滤；保留 `security_level` 现有语义；Milvus 字段方案先在 2.4.6 实测（动态字段优先） | 影子比对：过滤前后召回集差异可解释 |
| 3b Neo4j | 发布镜像打标（节点/关系带 `release_id` 或独立镜像标签集），重建/校验任务 | 校验：图谱与发布 Manifest 一致率 100% |
| 3c Agent | `AgentOrchestrationRun` 快照挂 `semantic_release_id`（可空列），运行期固定 | 同一 run 重放结果一致；`AgentAccessPolicy` 不变 |
| 3d 其余 NL2SQL 调用点 | `agent_tools_nl2sql`、`chat_recall` 等改经 Registry | 与 3c 同批验证 |

- 每个子项都要有「开关 + 回落」，不允许一次性全部切换。

### P4 —— 知识服务 Facade（跨域通用，规模 M）

- **接口**：`/api/v1/semantic/knowledge/query`，请求带 `domain`、问题、权限上下文；内部编排 图谱 / RAG / SQL / 指标 四路，统一引用与权限口径（一次查询内四路权限判定必须同源）。
- **采购试点**：如需冻结路径，加 `/api/v1/procurement/knowledge/query` 薄别名（只做 domain 固定转发）。
- **验收**：采购试点问题集端到端通过；权限过滤用例双向（有权限能查到 / 无权限查不到）；引用可回溯到发布版本。
- **扩展性证据**：同一接口用第二域参数直接跑通（见 P6）。

### P5 —— Workflow / Command / Approval（新子系统，开关关闭，规模 L）

- **新增表（全部加法）**：`workflow_definition(domain_code, capability_code, version, definition_json, status)`、`workflow_instance`、`workflow_step`、`business_command`、`approval_task`；异步沿用 outbox 模式（可复用 `ResearchEventOutbox` 的设计，不共用表）。
- **执行器**：复用现有 Worker 容器模式（新 profile/开关门控），PG 状态机 + 幂等键 + 补偿钩子。
- **外部写适配**：先接口 + 模拟器，ERP/SRM 真实适配后置；Agent 仍只读，写操作一律经 Command。
- **采购审批矩阵**：纯数据（`definition_json`），其他板块直接复用同一引擎。
- **验收**：状态机全路径（含重复提交、超时、取消、补偿）；安全评审（权限矩阵、幂等、审计）通过后默认关闭上线。
- **风险**：这是本计划唯一的 L 级事项，必须独立立项、独立开关、独立回滚。

### P6 —— 第二板块 dry-run 与接入 Playbook（规模 S）

- 选一个最小第二域（如财务或销售的一个小场景）：新增 `data_domain` 行 → 挂 1–2 个 BO → 定义少量本体/指标 → 编译发布 → 绑定只读 Agent → 跑知识问答。
- **目标：零代码改动完成接入**。若出现代码改动，说明前五阶段抽象不足，回补原则而不是加特例。
- 输出《新板块接入 Playbook》：① 建域 ② BO 与本体映射 ③ 指标两层定义 ④ 编译发布 ⑤ Agent/工具绑定 ⑥ 知识源与权限 ⑦ 灰度开关。

## 7. 与冻结报告的关键差异（修订建议）

| 冻结报告表述 | 代码事实 | 修订建议 |
|---|---|---|
| 本体版本化 / `ontology_release_id` | 版本管理已在 Phase 6 移除，`version/valid_*` 为兼容残留，正常一类一行 | 发布层自包含快照；不要复活版本列 |
| `SemanticManifest` | 已有 `RelationManifest`（关系批量执行载荷） | 改名 `SemanticReleaseManifest` |

| Manifest 中 `domain` 字段 | `data_domain` 已是域 SSOT | Manifest 的域信息从 `data_domain`/BO 派生并写入快照；发布表 `domain_code` 可空以兼容全局快照 |
| 指标 SSOT 待定 | `kpi_catalog` docstring 已定两层模型（技术/业务，`metric_id` 弱关联） | 正式入档，不再另立模型 |
| ADR-008 部署以现场为准 | centos overlay 需 Compose ≥2.24，基础文件用 `profiles`（v2 特性） | 增加 Compose v1 独立全量文件分支；ollama `latest` 锁到当前 digest |
| WBS 164 人日 vs 94–122 人周 | 无法从代码裁决 | 先用 S/M/L 排期，P0 后重估，不再对外引用矛盾口径 |

## 8. 「不影响现有功能」的保障机制（每阶段硬性要求）

1. **开关默认关** + 条件 import（照抄 `enableAgentOrchestration` 模式），关闭时与今天完全一致。
2. **只做加法 DDL**：不删表、不删列、不改非空、不改类型；每个阶段最多一个小迁移，手写，downgrade 实测。
3. **双路径 + 影子比对**：先并行计算、只记录差异，差异为零才切换；切换以消费方为单位，不整体切换。
4. **Registry 可回落**：无激活发布 / 开关关闭 / 快照损坏时自动回直读治理表。
5. **接口只增不改**：现有路由、请求/响应字段、前端页面零改动。
6. **判据沿用现状**：CI 失败集合对差净新增 0（不追求全绿）；定向测试 + 回归邻套件。
7. **部署零新增中间件**：只复用现有 compose 服务与 Worker，镜像版本不动。

## 9. 风险清单

| 风险 | 等级 | 缓解 |
|---|---|---|
