## 0. 总体判断

冻结报告的九个专题在代码里**全部有对应实现**，无「纸面能力」：本体、图谱、RAG、NL2SQL、Agent、模型路由、部署栈均为真实运行代码。改造类型分布：

| 类型 | 含义 | 本平台判断 |
|---|---|---|
| **A 直接复用** | 不需实质修改 | Agent 工具白名单机制、SQL Guard、只读编排 Worker、Neo4j 白名单、模型路由/计量、EntityMapping 生效期机制、supplier-360 等采购域已有服务 |
| **B 扩展** | 现有代码上扩展 | NL2SQL schema 注入点（接 Semantic Registry）、RAG 权限过滤（现只有 security_level）、AgentRun 快照（挂 release_id）、本体 CRUD 增加发布管理、部署 feature flag |
| **C 局部重构** | 需改结构 | 本体「版本」语义（见 §2 的 P0 发现：版本管理已被移除）、指标 SSOT（ontology_metric / kpi_catalog / feature_definition 三处并存） |
| **D 新增开发** | 净新增 | 语义编译器 + Manifest Schema + Release 状态机、Semantic Registry 运行时、source/property/key bindings（多源绑定）、Workflow/Command/Approval、采购知识服务 Facade |

**结论**：冻结报告「渐进式增量升级、不推倒重建」的判断与代码事实一致，可行。**最大风险不是技术栈，而是「发布版本化」与现本体设计的正面冲突**（§2/P0）以及 DDL 合并（§5）。

## 2. 专题 02 本体管理 —— **C（关键发现）+ D（Release/编译器）**

**P0 发现（冻结报告未提及，必须在 WP02/03 立项前裁决）**：
`OntologyClass` 的版本管理是**已移除的功能**（源码 docstring 原文：「版本管理（Phase 6，已移除）：updateClass 现为原地 UPDATE，主键 id 稳定，不再产生新版本行。version/validFrom/validTo 列保留兼容」）。现状：
- `version`/`valid_from`/`valid_to` 是**兼容残留**，正常情况下每个 `class_name` 只有一行；
- 删除 = 软删墓碑（`valid_to` = now），列表默认过滤；
- `UNIQUE(class_name, version)` 约束还在，但业务层已不产生多版本行。

⇒ 冻结报告要求「Agent run 固定 ontology_release_id、运行中发布新版本不改变既有任务语义」**不能建在现有 version 列上**——必须在**发布层**（新表 `procurement_ontology_release` + 快照/编译产物）实现，本体治理表保持单行原地更新。这一点直接影响 DDL 设计：**发布快照必须自包含**（编译产物落库），不能靠「回查治理表+version 列」重建历史语义。

| 项 | 实测 |
|---|---|
| 现有代码位置 | `models.py:236` OntologyClass / `:305` Property / `:951` Relation / `:903` Join / `:365` Metric / `:589` BusinessObject；`services/ontology_service.py`；`api/v1/ontology.py` |
| 现有功能 | 完整 CRUD；Property 有 `is_primary_key`/`is_foreign_key`/`ref_class_id`/`source_column`/`data_type`/约束元数据（allowed_values/min/max/regex）；Join 支持**多列**（`source_columns`/`target_columns` 数组）；Metric 字段丰富（formula/agg/metric_type/numerator_denominator_measure/grain_keys/filter/status/execution_source）；`kpi_metric_publish_gate` 已对指标发布做门禁 |
| 已有「Manifest」概念 | `api/v1/ontology.py:59,658-743` 的 **RelationManifest**：关系清单 CSV → 批量 syncGraph/inferJoins/applyManifest 的**执行载荷**，不是发布契约 ⇒ 命名撞车，冻结报告的 SemanticManifest 建议改叫 `SemanticReleaseManifest` 以免混淆 |
| 目标要求 | Release 状态机（创建/校验/编译/激活/回滚）、Source/Property/Key Bindings、Semantic Manifest JSON Schema、确定性 hash |
| 差距 | 发布/编译/Registry/JSON Schema **全部不存在**（D 类净新增）；「多源绑定」与现有单值 `source_table`/`source_column` 冲突（见专题 03） |
| 改造建议 | **C+D**：治理表不动（A）；发布层全部新增（D）；发布状态机建议复用 `kpi_metric_publish_gate` 的门禁模式 |
| 风险 | ① 发布快照自包含（见上）；② 现有 RelationManifest 与 SemanticManifest 命名/职责混淆；③ 本体消费方（NL2SQL/Neo4j/RAG/Agent）都要从「直读治理表」改「读发布版本」⇒ 这是一次**全消费面穿透性改造**，不是加一张表 |

| 项 | 实测 |
|---|---|
| 现有代码位置 | `models.py` EntityMapping；`services/entity_mapping*`、`api/v1/entity_mapping.py`、`id_mapping.py`；`services/enterprise_semantic_layer.py` |

## 10. 冻结报告四个待统一事项的核查结论

| 事项 | 核查结论 |
|---|---|
| **API 路径**（§2.1） | 与现有路径无冲突。现有 `api/v1/ontology.py` 可原地扩 `/releases` 等子路由；`/semantic/*`、`/procurement/*` 为全新前缀。注意 prefix 双叠加历史 bug 的约定 |

| **DDL 合并**（§2.3） | 现有表复用面比报告预期更充分：EntityMapping 已有生效期、Join 已支持多列、Outbox 模式有 research 先例。新增表应**只做报告列出的最小集**。迁移必须手写（autogenerate 仍有破坏性提议的历史教训） |
| **WBS 口径**（§5） | 164 人日 vs 94–122 人周的口径矛盾，代码评估无法裁决；但本评估的 A/B/C/D 分布可作为重估输入：A/B 占大头（主题 01/04/05/06/07/08/09），C 只有本体版本语义一处，D 集中在 发布编译器+Registry、多源绑定、Workflow/Command、知识服务 Facade 四块 |
