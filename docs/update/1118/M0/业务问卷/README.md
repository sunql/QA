## 1. 为什么现在发这 4 份问卷

V0.3（`智能采购平台详细设计方案_V0.3.docx`）§13 列了 7 项「开发前必须冻结的待确认项」，其中 5 项至今**零回复**。同时，本地已经出现两处**因为缺业务口径而做不下去**的实证：

| 实证 | 位置 | 后果 |
|---|---|---|
| 12 条 KPI 的治理口径与技术口径 **12/12 mismatch** | `kpi_catalog.grain_keys`（中文粒度）vs `ontology_metric.grain_keys`（物理粒度 `SUPPLIER_CODE`/`FACILITY_CODE`） | 指标口径**没有真正进 NL2SQL**，KPI 类问题无法验收 |
| 4 条 KPI 的技术层度量**完全为空** | `ontology_metric.numerator_measure IS NULL`（不良率/一次合格率/NCR 率/资质合规率） | 这 4 条**无论工程怎么写都算不出数**，必须业务给定义 |

> 这就是 M0.6 存在的唯一理由：**它同时是「24–38 人日的 KPI 口径轨道（M2′）」和「12–18 人日的询价/审批（M5）」的唯一前置。**
> 问卷不发回来，M2′ 和 M5 都不能验收。

## 3. 怎么答（尽量省你们的时间）

每份问卷都是**「确认或修正」式**，不是空白问卷：

- 凡是「我们的理解」已经写好的，**只需要写「对」或改掉那一行**；
- 每题末尾的 `▸ 回答：` 就是回填位；
- 拿不准的写「不确定，需 X 部门确认」也有效——**「不确定」本身就是有效答案**，工程侧据此走降级，不会卡住；
- 单题答不出的，**不要跳过整题**，跳过即视为「待确认」，工程侧会把它登记为已知限制。

**预计耗时**：A 约 60–90 分钟（12 条指标），B 约 45–60 分钟，C 约 60 分钟，D 约 30 分钟。

## 4. 时间与回收

- 建议回收窗口：**1 个自然周**（对齐 M0 的 8–12 人日窗口，M0 的其余工作可与回收并行）。
- 回收后请填 `E-回收登记.md`，每题标注：答复 / 待确认 / 未答。
- **回收率低于 3 份（4 份中）时，M5/M6 不启动**（见落地计划 §2 准则 C 修正版）。**M1/M2/M2′/M3/M4 照常推进**——它们只需要"部分答案 + 降级"，不必等齐。只有回收 **≤1 份** 才触发整体重排。

## 5. 隐私与安全

- 问卷不含账号密码；C 问卷里的只读账号请走内部渠道单独给，不要写在问卷正文。
- 涉及具体金额阈值、供应商名单的答复，请按你们的信息分级要求处理；本仓不落库、不进 manifest，只作为规则参数的**来源标注**。
- 完整填答后的问卷与回收登记会归档到 `docs/update/1118/M0/业务问卷/`，作为 M0 验收包的一部分（判据 4）。

## 6. 联系

技术问题随时找研发侧；口径问题找不到对应人时，**先答你们能答的**，剩下标注「需 X 确认」即可。
