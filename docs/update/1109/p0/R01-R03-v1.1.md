## R01 v1.1 —— 代码与技术架构评估（结论）

**总体结论**：冻结报告九个专题在代码中**全部有真实实现**（无纸面能力），「渐进式增量升级、不推倒重建」的路线与代码事实一致。**在现有全部基础设施版本不升级的前提下，能力要求可以满足。**

### 九专题结论

| # | 专题 | 类型 | 一句话结论 |
|---|---|---|---|
| 01 | 总体技术架构 | A/B | FastAPI + React 分层完整；新子系统用 feature flag + 条件注册即可插入 |
| 02 | 本体管理 | **C + D** | 治理 CRUD 完整；**版本管理已被 Phase 6 移除**，`version/valid_*` 是兼容残留 ⇒ 发布层必须自包含（裁决一） |
| 03 | 数据集成与映射 | B + D | `entity_mapping`（含生效期）是实例层 SSOT；本体侧只有单值 `source_table/source_column`，多源无处表达（裁决二） |
| 04 | 知识图谱 | A/B | 本体图 + 业务图均在用；业务图已回填约 145 万关系；APOC core 可用，**GDS 未安装** |
| 05 | RAG 知识引擎 | B | 检索与 `security_level` 过滤已实现；缺域/实体/有效期过滤；Milvus 无动态字段 |
| 06 | NL2SQL 与语义查询 | B | `buildSchemaText` 是干净注入点；SQL Guard 链完整，原样保留 |
| 07 | Agent 运行平台 | A + B + D | 工具白名单/ACL/只读 Worker 可用；run 快照可挂 release；**Workflow/Command/Approval 完全不存在** |
| 08 | 模型与规则服务 | A | 路由、计量、成本管理均为真实实现，不动 |
| 09 | 部署与运维 | A | 生产为 Docker 19.03.9 + Compose **v1** + 离线镜像，按现状沿用（裁决：不升级） |

### P0 实测带来的三点修正

1. **容量不是问题**：本体 99 类 / 6,888 属性 / 191 JOIN；发布编译、影子比对可全量做。
2. **Milvus 方案已定**：5 个拆分集合、`enable_dynamic_field=false` ⇒ 新集合 + 全量回填（< 7,100 行）。
3. **外部写接口缺失**：THBI Oracle 为只读库，仓库无 ERP/SRM 写接口 ⇒ P5 先模拟器。

## R02 v1.1 —— 复用与改造清单

### A 类（直接复用，不改）

| 能力 | 代码位置 | 说明 |
|---|---|---|
| Agent 工具白名单 / ACL | `AgentAccessPolicy`、工具绑定表 | 写侧改造后仍沿用 |
| SQL Guard | `sql_guard` 全链 | P2/P3 一律不碰 |
| 只读编排 Worker | `agent_orchestration*` | P5 新 Worker 照此模式，不共用表 |

| 采购域已有服务 | `supplier_360` / `supplier_risk` 等 | P4/P6 直接调用 |

### B 类（现有代码扩展）

| 能力 | 扩展点 | 阶段 |
|---|---|---|
| 语义注入 | `nl2sql_schema.buildSchemaText` 的 `classes` 来源改经 Registry | P2 |

| 部署开关 | 仿 `enableAgentOrchestration` 条件注册 | P1–P5 |

### C 类（局部重构）

| 对象 | 原因 | 处置 |
|---|---|---|
| 本体「版本」语义 | 版本管理已移除，`version/valid_*` 仅墓碑 | **不复活**，发布层另建自包含快照（裁决一） |
| 指标 SSOT（三处并存） | `ontology_metric`（技术）/ `kpi_catalog`（业务）/ `feature_definition`（特征） | 前两者确立两层模型（裁决三）；`feature_definition` 保持独立，不在 Manifest 中合并 |

### D 类（新增开发）

| 模块 | 范围 | 阶段 |
|---|---|---|
| 语义编译器 + JSON Schema + 哈希 | 治理表 → 自包含 Manifest | P1a |
| `semantic_release` 表 + Registry + API + 状态机 | 发布/激活/回滚/diff | P1b |
| 多源绑定（属性级 `sources[]`） | 只落发布快照，运行期不读 | P1（编译期） |
| Workflow / Command / Approval / Outbox | 独立子系统、独立开关 | P5 |
| 知识服务 Facade（跨域通用） | 四路编排 + 统一权限 | P4 |

## R03 v1.1 —— 工作量评估（人日口径）

**口径**：1 人日 = 1 名工程师 1 个工作日；不含业务方等待、外部联调排队与法定节假日；按**单线程**估算，多人并行不缩短阶段内顺序。

| 阶段 | 人日 | 主要内容 | 门禁 |
|---|---|---|---|
| P0 基线与裁决 | 3 | D1 环境、D2 数据、D3 四项裁决 | G1 |
| P1a 发布骨架 | 4 | 迁移、编译器、Schema、哈希 | — |
| P1b Registry + API | 4 | 只读服务、6 端点、状态机守卫 | G2 |
| P2 NL2SQL 影子接入 | 6 | 适配器、影子比对、切换、发布钉住 | G3 |
| P3a RAG 过滤 | 4 | 新集合 + 回填 + 过滤 | — |
| P3b Neo4j 镜像 | 4 | 打标、分批重建、对账 | — |
| P3c Agent 钉住 | 3 | run 快照 + 重放一致 | — |
| P3d 其余调用点 | 3 | `agent_tools_nl2sql` / `chat_recall` 等 | G4 |
| P4 知识 Facade | 6 | 四路编排、统一权限、采购别名 | G5 |
| P5 Workflow/Command | 20（含 3 天缓冲） | 表族、状态机、幂等、审批、补偿、安全评审 | G6 |
| P6 第二板块 dry-run | 5 | 零代码接入证据 + Playbook | G7 |
| **合计** | **62 人日** | ≈ 12.4 个工作周 | G1–G7 |

**说明与边界**：

1. **不采用**冻结报告 WBS 的「164 人日 / 94–122 人周」矛盾口径；以本文 62 人日为唯一对外口径，P0 结束即锁定。
2. P5 是唯一 L 级事项，20 人日中 3 天为显式缓冲；若实际外溢超过 1 天，按日级排程 §15 **削范围不削验收**。
3. 未计入：文档源接入（当前文档数为 0，另立需求）、真实 ERP/SRM 适配（等外部接口）、前端页面改造（本计划不改现有页面）。
4. 按角色拆分（比例）：后端 ≈ 44、数据/SQL ≈ 8、测试 ≈ 6、安全评审 ≈ 4；前端 0（纯新增接口，无页面改动）。
