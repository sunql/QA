## 2. 归因方法

每条 KPI 取四组事实（全部只读、可复跑）：

| 事实 | 来源 |
|---|---|
| 治理层现状 | `kpi_catalog`：`business_definition` / `formula` / `numerator` / `denominator` / `grain` / `data_source` / 结构化 `numerator_columns` 等 |
| 技术层现状 | `ontology_metric`：`execution_source` / `formula` / `measures` / `grain_keys` / `time_column` / `time_grain`；`ontology_metric_source` 源类 |
| 本体覆盖 | 技术引用列（sqlglot 解析 formula/measure/filter/grain/time）− 源类 `ontology_property.source_column` |
| 对账结论 | `reconcileMetric(governanceSpecOf, techniqueOf, resolution)`（与 chat 运行时同源） |

分类规则（按「下一步谁动手」+「差异能否机械消除」）：

- **仅列名不同**：语义等价，加 alias 即闭合；
- **技术层需改**：治理定义明确，实现偏离（SQL/measure/绑定/时间参数化）；
- **真口径分歧**：双方都有依据，必须业务拍板；
- **治理层需改**：治理侧定义/字段本身缺或错，技术无从实现。

## 3. 12 条逐条归因

| # | KPI | 治理层现状 | 技术层现状 | 差异归因 | 缺什么 | 分类 |
|---|---|---|---|---|---|---|
| 1 | **KPI_SUPPLIER_OTD** | 分子=准时收货的**订单行**；分母=「PROMISED_DATE 位于统计周期内的有效采购订单行」；粒度 供应商+工厂+月 | `COUNT(CASE WHEN R.RECEIPT_DATE<=O.PROMISED_RECEIPT_DATE THEN 1 END)/COUNT(O.PROMISED_RECEIPT_DATE)`，`ORDER_LINE INNER JOIN GOODS_RECEIPT_LINE`；无时间窗、`time_column=NULL` | **INNER JOIN 把未收货订单从分母剔除**（分母变成"已收货行"）⇒ OTD 偏高；多次收货扇出放大计数；计数单位是收货行不是订单行 | `LEFT JOIN` + `COUNT(DISTINCT 订单行)` + 时间窗 + `time_column` | 技术层需改 |
| 2 | **KPI_SUPPLIER_OVERDUE_RATIO** | 分子=逾期订单行；分母同上 | 同上的 INNER JOIN 结构 | **未收货的逾期单（最典型逾期）被剔除** ⇒ 逾期率系统性偏低；同样扇出与计数单位问题 | 同上 | 技术层需改 |
| 3 | **KPI_PAYMENT_ON_TIME** | `PAYMENT_DATE<=DUE_DATE` 笔数 / 「已到约定账期的付款笔数」；源 `DWD_PAYMENT` | `VALUE_DATE<=DUE_DATE` / `COUNT(DUE_DATE)`；源 `DWD_SUPPLIER_PAYMENT`；`time_column=NULL` | 列名差异（`PAYMENT_DATE→VALUE_DATE`、表名不同）；**分母缺「已到期」时点过滤**（`COUNT(DUE_DATE)` 含未到期） | 分母加 `DUE_DATE <= 统计截止`；`time_column` | 技术层需改 |
| 4 | **KPI_INVOICE_MATCH_RATE** | **三单**（订单+收货+发票）匹配金额 / 总发票金额；`time_column=INVOICE_DATE` ✅ | 发票头 ⨝ 发票行 ⨝ 订单行，条件只含 PO 号/行号/数量/单价 —— **没有 join 收货单** | 实现是**两单匹配**，定义是三单 ⇒ 匹配率偏高 | 补收货单匹配条件（数量/金额对账）；若业务实际以两单为准 ⇒ 改治理定义 | 技术层需改 |
| 5 | **KPI_PURCHASE_CYCLE_TIME** | `AVG(收货日-请购创建日)`；粒度 供应商+工厂+月 | `AVG(TRUNC(R.RECEIPT_DATE)-TRUNC(L.CREATION_DATE))`，请购行 ⨝ 关联表 ⨝ 收货行 | 定义与实现一致（`TRUNC` 到日符合单位「天」；未收货不计入也符合"入库周期"语义）；**无 `time_column`** ⇒ 无法按「月」切片 | `time_column`（建议 `RECEIPT_DATE` 或请购创建日，需业务定） | 技术层需改 |
| 6 | **KPI_SUPPLIER_DELAY_DAYS** | `AVG(实际-承诺) WHERE 延误>0`；单位 天 | `AVG(TRUNC(R.RECEIPT_DATE)-TRUNC(O.PROMISED_RECEIPT_DATE)) WHERE R.RECEIPT_DATE>O.PROMISED_RECEIPT_DATE` | **过滤用原值、差值用 TRUNC**：同日不同时刻的边界不一致（可能"未逾期"却差 0 天）；`time_column=NULL` | 过滤与差值统一到 `TRUNC`；`time_column` | 技术层需改 |

## 5. `property_alias` 回填：范围、作用与约束

**范围**：12 条 KPI 实际引用的 (类, 物理列) 共 **45** 个，`property_alias` 全部为空
（全库 4182 条属性中只有 8 条有 alias，且全在 ASSET 域）。映射文件回填其中 **32** 个，
13 个（子表里的 join 键副本）**刻意留空**——它们与主表同值，回填只会制造
resolver 歧义。映射见 [`property-alias-mapping.json`](property-alias-mapping.json)。

**工具**：`backend/scripts/backfill_property_alias.py`（默认 dry-run）+ 纯函数层
`app/services/kpi_property_alias_backfill.py`。dry-run 做六道闸：

1. 目标类/列必须存在（写错即拒绝并列出全部）；同名类多条有效记录 ⇒ 报歧义（按 `class_id` 定位，不猜）；
2. **不覆盖**已有人工 alias（`ACTION_KEEP`，只报告）；
3. **同 KPI 作用域内一个 alias 不得指向两个物理列**——有效 alias = 库内存量 ∪ 本批回填；
   只有「本批回填撞上存量」才算会拦写库（存量冲突只报告，不是本批造成的）；
4. **模拟对账**：回填前后各算一遍有源类的 KPI（当前 9 条），verdict / resolved / unknown / missing
   必须完全一致；**参与集合必须齐全**（为空或漏条 ⇒ 拒绝，空集不能当通过）；
5. **覆盖率**：probe 抽出的每个 (源类, 物理列) 必须被 `entries ∪ excluded` 覆盖
   （「45 = 32 + 13」由脚本机械校验，不再靠文档手抄）；
6. **写正式库前备份**（`--apply` 且库名 = `qa_metadata` 时强制 `pg_dump ontology_property`）。

实测（[`evidence/property-alias-dryrun.txt`](evidence/property-alias-dryrun.txt)）：
`fill=32 keep=0 冲突=0（存量 0）`，`9 条参与模拟，解析/对账变化 0 条`。

**为什么本批不 `--apply`**：`semantic_release.manifest_json.classes[].properties[].propertyAlias`
是 `ENABLE_SEMANTIC_RELEASE=ON` 侧的来源。回填 live alias 而不重发布，会让
**OFF（直读）≠ ON（快照）**，A5 的答案级评估会红。⇒ `--apply` 与 **A9「采购域首次发布」同批**执行，
中间不留"半回填"状态。

**D-3 约束**：本批只产出**候选**映射与 dry-run 证据；候选在 A9 发布前**不得被生产读路径消费**。
