## 〇、需求

给图谱加**发布维度**：每个已发布版本在图谱里有一份**不可变**的快照，
使得「按发布版本读图」可行，且回放结果与当初发布时一致。

**验收标准（用户视角）**

1. 镜像存在时，**主图一个字节都不变**（现有浏览/遍历/语义关系功能零影响）；
2. 同一发布**重复物化**，结果**完全一致**（幂等）；
3. 镜像内容与该发布的 manifest **逐条对得上**（实体 100%，关系逐条解释）；
4. 读侧可以「按发布读图」，且**一键回退**到主图。

## 二、方案对比（≥ 2 个候选，含取舍）

| 维度 | **A 独立镜像库** | **B 主节点加发布属性/标签** | **C 独立镜像节点（本批采纳）** |
|---|---|---|---|
| 做法 | 把整个图复制到另一个 Neo4j database | 给现有节点加 `release_id` 属性 / `Release_x` 标签 | 新建 `:ReleaseClass` 等 label，节点身份 = (label, unified_id, release_id) |
| 发布间隔离 | 完美 | ❌ **无**：同一节点被所有发布共享，属性原地覆盖（C-2）⇒ A 版发布时的类 X 的属性**已被 B 版覆盖** | ✅ 完美：每个发布一份独立节点 |
| 回退到旧发布 | 指针切库 | ❌ 标签只增不减、属性已被覆盖 ⇒ **回不去** | ✅ 指针切换（读镜像 or 读主图） |
| 主图影响 | 零（但方案不可行） | ❌ 主图节点被污染；现有 `MATCH (c:Class)` 会命中多份 ⇒ 全量改造消费方 | ✅ 零：`MATCH (c:Class)` **不命中** `ReleaseClass`（独立 label）⇒ 现有消费方无需改（C-8） |
| 边怎么带发布维度 | 天然 | ❌ 边无键无属性 ⇒ 只能 delete-then-create（C-3） | ✅ **端点继承**：边连的是镜像节点 ⇒ 边天然属于该发布；**不需要给边加属性、不需要删边重建** |
| 可行性 | ❌ **Community 不支持多 database**（C-1） | 可行但语义错误 | ✅ 可行 |
| 存储成本 | 整库复制 | 最低 | 副本（本体图体量小；业务图不在范围内，见第四节） |

**裁决：C（独立镜像节点）。**

三条决定性理由：
1. **不可变**（与仓内「不可变数据」原则一致）：镜像是发布的快照，不随本体变化而变；
2. **边靠端点继承作用域**：这一条把「边无键无属性」这个死结整个绕开了；
3. **主图零影响**：现有 4 个生产消费方一行都不用改。

## 三、数据形态（裁决的具体化）

### 3.1 节点

| 实体 | 镜像 label | 节点身份（MERGE 键） | 属性来源 |
|---|---|---|---|
| 类 | `ReleaseClass` | (`unified_id`, `release_id`) | manifest `classes[]`（className/classAlias/description/sourceTable）+ `release_id` / `release_version` / `mirror_of` |
| 属性 | `ReleaseProperty` | 同上 | manifest `classes[].properties[]`（propertyName/propertyAlias/dataType/sourceColumn/isPrimaryKey/isForeignKey） |
| 指标 | `ReleaseMetric` | 同上 | manifest `metrics[]`（metricName/metricAlias/formula/aggFunction/status） |
| KPI | `ReleaseKpiCatalog` | 同上 | manifest `kpis[]`（kpiCode/kpiName/status/owner/unit） |

- `unified_id` 与主图节点**相同**（便于对照与回退）；
- `release_id` = `semantic_release.id`（int），`release_version` = 发布版本号（可读）；
- `mirror_of` = 主图 `unified_id`（显式冗余，便于「镜像 → 主图」回查）。

### 3.2 边

| 关系 | 方向 | 来源 |
|---|---|---|
| `HAS_PROPERTY` | 类 → 属性 | manifest `classes[].properties[]` |
| `REFERENCES` | 属性 → 被引用类 | manifest `classes[].properties[].refClassName` |
| `SUBCLASS_OF` | 类 → 父类 | manifest `classes[].parentClassName` |
| `JOIN` | 源类 → 目标类 | manifest `joins[]`（joinKey / sourceClassName / targetClassName） |
| `DERIVED_FROM` | 指标 → 类 | manifest `metrics[].targetClassName` |
| `MEASURED_BY` | KPI → 指标 | manifest `kpis[].metricName` |

- 边**不带属性、不带键**（与主图同款）：发布作用域由**端点**承载 ⇒ 无需删边重建；
- 边类型走**白名单**（6 种），与主图的写入函数分开（防止 CQL 注入）；
- **`REFERENCES` 为什么在内**（评审补的）：manifest 的 `properties[].refClassName`
  **自带**引用关系，主图也物化了 `(:Property)-[:REFERENCES]->(:Class)`
  （`neo4j_client.linkPropertyReferences`）。早期版本把它漏了 ⇒ 镜像 ≠ 主图本体
  子图 ⇒ D25 切读侧会**静默**少一截引用/外键导航路径（不报错，只是少结果）。
  悬空引用（目标类已进墓碑）在**编译器**里就编成 null ⇒ 镜像里既没有边，
  也没有「未解析」噪音。

### 3.3 名称 → unified_id 的解析

manifest 用名字（C-5），图谱用 `unified_id`。解析在 **PG 侧**做（一次性批量）：

```
ontology_class.class_name ─┐
ontology_property.property_name (+ 所属类) ├─→ id ─→ id_mapping.unified_id
ontology_metric.name ──────┤            （business_object ∈ {CLASS,PROPERTY,METRIC,KPI}）
kpi_catalog.kpi_code ───────┘
```

- 解析不到 ⇒ 该实体**不进镜像**，计入 **未解析清单**（类型/名字/原因），逐条报告（D24）；
- **级联**：类的属性若类未解析 ⇒ 属性一并记为未解析（无父节点的属性节点是孤儿，没有意义）；
- 解析依赖 PG **活数据**：发布后实体改名 ⇒ 物化时解析失败 ⇒ 这正是需要暴露的信号，不是 bug。

**三态解析（实测踩出来的坑，不是设计洁癖）**

只把「解析不到」合成一种原因是不够的——运维拿到清单要能**照着做**：

| 状态 | 判定 | 原因文案 | 运维动作 |
|---|---|---|---|
| 已解析 | 名字 → 唯一 `unified_id` | — | 无 |
| **歧义** | 同名 → **多个**不同 `unified_id` | 同名多行，实体歧义 | 本体数据重复 ⇒ 治理去重 |
| **未登记** | 实体存在，但 `id_mapping` **缺行**（LEFT JOIN 出来是 NULL） | 该实体未登记统一 ID（id_mapping 缺行） | 跑 ID 映射回填 |
| 不存在 | 本体里根本没有这个名字 | 本体中不存在该实体 | 补本体或修 manifest |

> 头一次跑真实数据时，「未登记」被并进了「不存在」，报告说"本体中不存在该实体"，
> 而那些类**明明在本体里**——只是没登记 `id_mapping`。按这个指引去补本体就是**查错方向**。
> ⇒ 三态必须分开，文案必须能直接指向运维动作。实现见 `EntityResolution.unmapped`。

## 四、边界声明（本批**不做**的事，写明理由）

| 不做的事 | 理由 |
|---|---|
| 镜像**业务图**（`BusinessEntity` ~51 万节点 / ~145 万边） | 业务图是**业务数据**图（订单/物料实例），不是语义本体；体量大一个数量级。启用需另做批次与耗时预算（D23 附录）。**D22 只做本体图 4 类节点** |
| 镜像**语义关系边**（`ontology_relation` 驱动的 relType 边） | manifest **无 relations 分区**（C-4）⇒ 该类边**无法从快照自包含重建** ⇒ 镜像若收录它就不是「这一版发布的图」，而是「物化那一刻的活数据图」⇒ 与发布语义冲突。**声明不在镜像范围**，对账口径同步写明。（注意：`REFERENCES` 不在此列——它由 manifest 的 `refClassName` 承载，**能**自包含重建 ⇒ 在镜像范围内） |
| 在 `activate()` 里**同步**写图 | 激活是 PG 内的事务；跨系统写在事务里 ⇒ 长事务 + 部分失败 ⇒ 发布状态与图谱状态不一致。**物化改为独立 Job**（D23），幂等可重跑 |
| 读侧切换（消费方改读镜像） | 读侧切换是 D25；D22–D24 只保证「镜像存在、可对账、可回放」 |
| 让 Milvus 的 `release_id` 变非零 | **图谱镜像与向量无关**。RAG 的 release 维度过滤需要**向量侧发布物化**（另一件事）。登记为 R-6，不在本批冒充已解决 |

## 五、批次方案（D23 的输入，编号 D22-B）

| 批次 | 内容 | 规模 | 事务/超时 |
|---|---|---|---|
| B1 | `ReleaseClass` 节点 | 本体类数量级（小） | 单批，单事务 |
| B2 | `ReleaseProperty` 节点 | 属性数量级（中） | 单批 + `UNWIND` 参数化 |
| B3 | `ReleaseMetric` / `ReleaseKpiCatalog` 节点 | 极小 | 单批 |
| B4 | 6 种边（按 relType 分组） | 与节点同量级 | 每种 relType 一批 |
| B5 | prune（清理本次计划外的残留镜像节点**与边**） | 与节点同量级 | 单批；**必须显式 opt-in** |

- **幂等**：节点 MERGE 键 = (unified_id, release_id)；边 MERGE 键 = (两端节点 + relType)
  ⇒ 重复执行不产生重复行；
- **断点续跑**：每批记录「批次号 / 条数 / 耗时 / 失败原因」，失败可从该批继续；
- **dry-run**：只解析 + 只出计划，**不写任何图**；
- **写守卫**：镜像写函数只接受 `Release*` label 与白名单 relType（防 CQL 注入 / 防误写主图）。

## 六、风险与守卫

| 风险 | 守卫 |
|---|---|
| 误写主图（Neo4j 无备份，C-7） | 镜像写函数**只认 `Release*` label + 白名单 relType**；主图 label（`Class`/`Property`/…）传入即 `ValueError` |
| CQL 注入（label / relType 来自数据） | label 走**固定映射表**（不拼字符串）；relType 走**白名单** |
| **写错目标实例**（生产图库无备份 ⇒ 误写不可逆） | **库层写目标闸门** `app/infrastructure/neo4j_write_target_guard.py`：默认只准写**测试实例**（7688），其它目标（含生产 7687、换端口/换主机）一律 `ValueError`；**每个镜像写函数**（节点/边/prune）都调用它 ⇒ D23 的物化 Job 自动继承（只靠脚本侧守卫 ⇒ Job 绕过脚本就失守） |
| 物化不完整却被当成已发布 | 物化 Job 记录「物化完成」状态与实体/边计数；D24 的对账脚本独立复核 |
| 名字解析失败被静默忽略 | 未解析清单**必须非空可见**（报告 + 退出码） |
| 端点缺失导致静默少写 | 镜像边端点用 **MATCH**（不凭空造节点）；命中边数 < 请求数 ⇒ **抛错** |
| 镜像 ≠ 主图本体子图（**REFERENCES 缺口，评审 HIGH**） | manifest 的 `classes[].properties[].refClassName` 承载「属性 → 类」引用，主图会物化成 `(:Property)-[:REFERENCES]->(:Class)`；镜像漏了它 ⇒ D25 读侧切换会**静默丢引用/外键导航路径** ⇒ 已补进 relType 白名单（现 **6** 种）与计划器 |

> ⚠️ 闸门**位置**的选择：写在脚本层（CLI 参数）不够 —— 库函数被别的调用方（D23 Job）直接调用时，
> 脚本层守卫不存在。故闸门下沉到 `app/infrastructure/`，**库函数自己调**，
> 脚本只做「参数 → `allowProdWrite`」的显式传递。
> 判定用**端口**而非黑名单 URI：`bolt://neo4j`（无端口）按默认端口 **7687** 判 ⇒ 生产目标被拒。

## 七、TDD 与实现要点

- **纯逻辑**（不连 Neo4j / PG，单测覆盖）：
  `buildMirrorPlan(manifest, resolution)` —— manifest + 名字解析结果 ⇒
  ``{节点, 边, 未解析}``；纯函数，无 IO；
  - 评审整改：原 `buildMirrorPlan` 单函数 **251 行** ⇒ 拆成 `_planClasses` /
    `_planProperty` / `_planReferenceEdge` / `_planSubclassEdges` / `_planJoinEdges` /
    `_planMetrics` / `_planKpis` + `_PlanContext` 累加器（每函数 < 50 行）；
- **解析**（连 PG）：**新模块 `app/services/semantic_graph_mirror_resolution.py`**
  的 `resolveManifestEntities(session, manifest)` ⇒ name → unified_id；
  - 为什么独立文件：解析要连 PG（IO），纯计划器不要 ⇒ 混在一起会把纯函数测试拖进 DB；
  - PG 的 IN 列表有 **65535 参数上限** ⇒ 名单按 `_QUERY_CHUNK_SIZE = 2_000` 分块查；
- **写入**（连 Neo4j）：**新模块 `app/infrastructure/neo4j_mirror_client.py`**，
  提供 `upsertReleaseMirrorNodes` / `upsertReleaseMirrorEdges` /
  `countReleaseMirrorNodes` / `countReleaseMirrorEdges` / `pruneReleaseMirror`；
  - **为什么不写进 `neo4j_client.py`**：那个文件已经 **1024 行**，超出仓内
    「文件 ≤ 800 行」的约定（`Harness/rules/工程结构.md`）。镜像写路径自成一体
    （独立 label 白名单 + relType 白名单 + `release_id` 守卫）⇒ 独立模块更合规矩；
    driver 仍复用 `neo4j_client.getDriver()`，**不重复连接逻辑**；
  - **写目标闸门**独立成 `app/infrastructure/neo4j_write_target_guard.py`
    （库层 ⇒ 所有调用方都生效，不只是脚本）；
- **契约与实现分离**：`app/domain/semantic_graph_mirror_spec.py` 放 label / 字段 /
  relType 白名单（service 与 infrastructure 共用，避免两份定义漂移，也避开 import 环）；
- **业务对象字面量 SSOT**：`app/domain/id_mapping.py` 新增
  `BUSINESS_OBJECT_CLASS/PROPERTY/METRIC/KPI` 与 `BUSINESS_OBJECTS`
  （原先字面量散落在 `ontology_service` 与 `kpi_vector_graph_sync` 两处，
  写错一个字面量会让解析静默落到「未登记统一 ID」⇒ 运维被误导）；
- **TDD**：先写用例（RED）→ 实现（GREEN）→ 重构。

### 7.2 真实数据验证（`scripts/semantic_graph_mirror_realdata.py`）

脚本默认**只读**；`--write` 才写图，且写目标闸门**默认只准测试实例**
（端口 7688）—— 其它目标（含生产 7687、任意别的端口/主机）一律要显式
`--allow-prod-write`。只挡 7687 是不够的：生产实例换个端口就绕过去了。实测（dev 库 5433 `qa_metadata` + **测试** Neo4j 7688）：


- **`REFERENCES` 3 条**（评审 HIGH 的补齐）：来自 manifest 的
  `classes[].properties[].refClassName`（属性 → 类的引用）⇒ 镜像现在与主图本体子图**同构**；
  悬空引用（指向 manifest 里没有的类）由编译器**归一为 `null`** ⇒ 不产生噪声边。
- **`--expect-delete`（破坏性操作的双保险）**：清理是**不可逆**操作（Neo4j 无备份）
  ⇒ `--cleanup` 必须同时给 `--expect-delete N`；脚本先数**实际将删多少**，
  与 N 不等 ⇒ **拒绝执行**（防「按预期数删一部分 / 删多了」）。

- **JOIN 只有 11 条而非 13 条**：manifest 里 13 条 join 有 **2 组是同一对类之间的不同 joinKey**
  （`13|PO_LINE_NO->19|PO_LINE_NO` 与 `13|PO_NO->19|PO_NO` 都在
  `DWD_GOODS_RECEIPT_DTL → DWD_PURCHASE_ORDER_DTL`；`6|PO_LINE_NO->…` 与 `6|PO_NO->…`
  都在 `DWD_ARRIVAL_ORDER_DTL → DWD_PURCHASE_ORDER_DTL`）。
  图谱边**不带属性**（C-3，边无键无属性）⇒ 同类对的多条 join 在图上是**同一条边**
  ⇒ 计划按 (relType, 源, 目标) 去重，13 → 11。
  **这不是漏写**：主图的 `linkClassJoin` 也是 `MERGE (a)-[:JOIN]->(b)` 不带列信息，
  镜像与主图**同粒度**。但列级 join 信息在图上丢失这一点必须登记（见第八节遗留项）。
- **端点解析**：镜像边的端点用 **MATCH**（不是 MERGE）⇒ 端点缺失**不会凭空造节点**；
  命中的边数少于请求数 ⇒ **抛错**，不静默少写（单测 `testUpsertReleaseMirrorEdgesDetectsMissingEndpoints` 钉住）。
- **主图零影响**：测试实例主图本来只有 2 个 `Class` / 3 个 `Property` / 0 个 `Metric` /
  0 个 `KpiCatalog`；镜像写完**四个 label 计数全部不变** ⇒ 独立 label 对现有消费方
  `MATCH (c:Class)` 不可见。
