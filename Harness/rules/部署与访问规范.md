# 部署与访问规范

> SSOT：前端发布后的访问地址适配（127.0.0.1 / localhost / 局域网 IP / 域名）。
> 2026-09-21 制定。背景：Windows 迁移部署中发现前端 bundle 烤死 `localhost:8000`，
> 换地址访问即全挂；本规范把「同源部署」定为强制架构决策。

## 一、强制：前端 API 走同源相对路径（CRITICAL）

**禁止把绝对 API 地址编译进前端 bundle。** Vite 的 `VITE_API_BASE_URL` 是
**编译期**注入，烤进 JS 后任何部署地址变化都会让浏览器连向错误的机器。

- `frontend/src/config.ts`：留空时回落到相对路径 `/api/v1`——**这是唯一认可的默认行为**
  （浏览器按「打开页面的那个地址」发请求，天然适配所有入口）。
- `docker/Dockerfile.frontend`：`ARG VITE_API_BASE_URL` 默认值**必须为空**；
  确有特殊部署要绝对地址时，显式 `--build-arg VITE_API_BASE_URL=...` 覆盖，
  并在变更记录里说明理由。
- `docker/docker-compose.yml`：frontend 服务**不得**设置运行时的
  `VITE_API_BASE_URL` 环境变量——静态构建产物读不到它，只会误导后来者。
- API 反向代理 SSOT：`docker/nginx.conf` 的 `location /api/` → `backend:8000`
  （含 `resolver 127.0.0.11` + 变量写法，防后端容器重建后 502）。修改代理路径
  必须同步 `config.ts` 的回落值。

## 二、禁止「动态探测 IP 注入配置」类方案

不得以启动脚本枚举本机 IP 再回写 nginx/CORS/前端配置：

- IP 会变（DHCP）、多网卡多 IP、内外网地址不可预知——枚举永远覆盖不全；
- 相对路径天然免疫上述全部问题，是 Web 部署标准做法；
- 唯一允许的「动态」动作：**打印**访问入口（见 §四），不写任何配置。

## 三、端口绑定与 CORS

- Docker `ports:` 默认绑 `0.0.0.0`（全网卡），即同时覆盖 127.0.0.1 /
  localhost / 局域网 IP——**这是默认且认可的行为**；仅安全加固场景才显式
  收紧绑定地址，收紧属变更，需记录。
- CORS 白名单（`backend/app/config.py` `CORS_ORIGINS`）只影响**绕过 nginx
  直连 8000** 的跨源请求；同源反代（§一）生效后前端链路不依赖它。
  为直连场景扩白名单时按 origin 精确列举，禁止 `*` + credentials 组合。

## 四、发布入口枚举（推荐）

发布/重启后应向操作者列出全部可用入口，避免「找不到对应地址」：

```bash
# scripts/show_access_urls.sh（WSL2 / macOS / Linux 通用）
echo "qa-system 访问入口："
for ip in 127.0.0.1 localhost $(hostname -I 2>/dev/null); do
  echo "  http://$ip:5173"
done
```

- `scripts/run_local.sh` 启动成功段应调用/内联该枚举。
- 正式部署验收：必须用**局域网 IP 入口**实际访问一次（不只验 localhost），
  重点确认登录 + 菜单 + 一次 API 调用成功。

## 五、新装库初始化 seed 清单（CRITICAL）

> 2026-10-23 制定。背景：CentOS 7 首装后「新建用户」500 ——
> `seed_menu_config.py` 从未包含 `item.profile`，新用户授默认菜单触发
> `permission_grant` FK 违反。SSOT 见
> `Harness/changes/fix-menu-seed-item-profile/summary.md`。

### 5.1 backend 启动自动 seed 的覆盖范围（不要高估）

容器 `CMD` 只做 `alembic upgrade head && uvicorn`；lifespan 里的启动 seed
**只覆盖** `agent_tool_bindings` / `agent_tool_configs` / `feature_rules`。
**以下全是手动脚本，alembic 不会建静态数据，漏跑即新装库缺数据：**

| 脚本 | 灌什么 | 新装是否必跑 |
|---|---|---|
| `python -m scripts.seed_menu_config` | `menu_config` 全部菜单 | **必跑**（缺 `item.profile` ⇒ 新建用户 500） |
| `python -m scripts.seed_rbac` | 角色/权限基线 | 必跑（按脚本内说明） |
| `python -m scripts.seed_system_config` | `system_config` 配置行 | 必跑（缺行 ⇒ 相关功能 500） |
| `python -m scripts.seed_permission_grant` | 各组织默认授权 | 必跑 |
| `python -m scripts.seed_user_passwords` | 初始账号密码 | 按部署模式 |

新增影响上表的启动 seed / 手动 seed 范围调整时，必须同步本表
（与 `Harness/changes/` 变更记录联动）。

### 5.2 「代码常量指向 DB 行」必须可由 seed 复现（强制）

凡业务代码引用**静态数据常量**（如 `rbac.py DEFAULT_NEW_USER_MENU_CODE = "item.profile"`）
指向某张表的行，该行**必须**：

1. 进对应 seed 脚本的清单；
2. 有集成测试数量断言兜底（seed 测试的总数断言 +1）；
3. 若是菜单项，同步 `test_seed_paths_aligned_with_frontend_routes` 的
   `frontend_routes` 集合与 i18n 键（`menu.item.*` 命名空间，zh/en 两侧）。

**代码常量 ↔ seed 条目 ↔ 测试断言，三处同改，漏一处 = 新装库必炸。**
评审触发词：代码里任何「按 code/编码查静态表」的引用，问一句
「新装库跑完 seed 一定有这行吗？」

### 5.3 seed 执行纪律

- **「seed 输出 N rows」只是清单总数，不是实写数**（条目多为
  `on_conflict_do_nothing`，冲突静默跳过）。数据是否落库以 SELECT 为准，
  禁止拿脚本 stdout 当成功证据。
- seed 幂等设计（upsert / DO NOTHING）⇒ 重复跑安全；但**反过来说**
  已有库跑 seed 不会修复「清单里缺的行」——先确认条目在清单里，再谈执行。
- dev 库的手工补数据会**掩盖 seed 缺口**；只有新装环境能暴露它。

### 5.4 首装冒烟必测项

新装/重建环境验收必须包含（缺一不可）：

1. `alembic current` == `alembic heads`（排除 schema 漂移）
2. `SELECT code FROM menu_config WHERE code='item.profile';` 有行
3. **admin 实际新建一个用户 → 201**（它穿透 menu_config → permission_grant
   FK 链，是 seed 完整性的端到端探针）
4. 按部署与访问规范 §四用局域网 IP 入口登录 + 菜单完整 + 一次业务 API 调用
