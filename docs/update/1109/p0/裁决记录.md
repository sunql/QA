## 裁决一：发布快照自包含（不建在 `version/valid_from/valid_to` 上）

**建议决定**：`semantic_release.manifest_json` 是**唯一运行期真相**，编译时把治理表完整快照写入；消费方只读快照，不回读治理表。`ontology_class.version/valid_from/valid_to` **不参与发布语义**，仅保留墓碑（`valid_to` 非空 = 已删）语义。

**依据（代码事实）**：

- `OntologyClass` docstring 明写：「版本管理（Phase 6，已移除）：updateClass 现为原地 UPDATE，主键 id 稳定，不再产生新版本行。version/validFrom/validTo 列保留兼容……本表正常情况下每 class_name 仅一行。」（`backend/app/domain/models.py:232-241`）
- 实测生产 `ontology_class` 99 行；若仍按「一版本一行」建模，发布与查询都会读到历史残留。

**影响面**：

- 新增表 `semantic_release` 必须自带 `manifest_json`（JSONB）+ `manifest_hash` + `schema_version`；
- Registry 的 `getActive()` **只读该表**，不得回查 `ontology_class/property/join/metric`；
- 墓碑语义保留：编译时过滤 `valid_to IS NOT NULL`（与 `listClasses` 现状一致）。

**备选与否决**：

- ❌ 复活 `version` 列做发布版本号 —— 会与「原地 UPDATE」冲突，且历史行已被折叠，无法复原；
- ❌ 只存「release → 类 id 列表」的引用式快照 —— 治理表一改，历史发布内容就漂移，回滚失效。

**钉住方式**：单测「编译 → 激活 → 修改治理表 → 重读发布」，断言快照内容不变；Registry 层禁止出现 `select(OntologyClass)` 的导入守卫。

**确认**：✅ 2026-11-09 项目负责人确认

## 裁决二：多源绑定与现有单源字段的 SSOT 关系

**建议决定**：**分三层，各管一段，不新增第三套模型**：

| 层 | 载体 | 语义 |
|---|---|---|
| 结构层（列级默认源） | `ontology_class.source_table`、`ontology_property.source_column` | **降级为默认/主源**。无显式绑定时用于 schema 文本与 LLM 提示 |
| 实例层（编码映射） | `entity_mapping`（`entity_type`、`enterprise_key/enterprise_code`、`source_system`、`source_key/source_code`、`match_rule`、`effective_date/expiry_date`） | SSOT。按生效日选取唯一 active 映射；同时生效的冲突映射**拒绝写入/拒绝查询** |
| 属性级多源（同一属性来自 ERP 与 SRM 两列） | 首期只落 `semantic_release.manifest_json` 的属性节点 `sources[]`，运行期不读 | 发布期裁决，避免污染治理表 |

**依据（代码事实）**：

- `ontology_class.source_table`（`models.py:253`）、`ontology_property.source_column`（`models.py:327`）均为 `String(100) nullable`，全库各只有一列 —— 天然承载不了「一个属性两个来源」；
- `entity_mapping` 已有 `effective_date`/`expiry_date`（`models.py:1563-1564`）与 `match_rule`，且生产已有 354,423 行在跑供应商名称解析 —— 说明实例层映射是**在用能力**，不是新设计；
- `ontology_metric_source`（`metric_id, class_id, role`）已解决**指标跨类**多源，与属性多源不是同一问题，不要混用。

**影响面**：

- P1 编译器：属性节点写 `sources[]`（默认源 + 显式多源），并在无优先级声明时报错；
- P2 影子比对：schema 文本渲染保持与现状逐字一致（多源不影响渲染，只影响解析优先级）；
- P4 知识服务：回答引用时可标注来源系统（来自 `sources[]` 或 `entity_mapping.source_system`）。

**备选与否决**：

- ❌ 现在新增 `ontology_property_source` 表 —— YAGNI；先由发布快照承载，等 P4 出现「运行期按源切换」的真实需求再加法建表（届时迁移成本一样低）；
- ❌ 把 `source_table/source_column` 直接改成多值 —— 破坏现有 schema 文本渲染与大量测试，违反「平滑不破坏」。

**钉住方式**：编译期守卫（多源无优先级 ⇒ 编译失败）；`entity_mapping` 冲突映射的拒绝用例（双向：单 active 通过 / 双 active 拒绝）。

**确认**：✅ 2026-11-09 项目负责人确认（业务/治理输入按末尾清单后补，不改变本裁决）

## 裁决三：指标两层模型正式入档

**建议决定**：**不新建模型**，正式确认现状即目标形态：

- `ontology_metric` = **技术口径**（`formula`、`agg_function`、`metric_type`、`numerator_measure`/`denominator_measure`、`grain_keys`、`target_class_id`），供 NL2SQL 生成 SQL；
- `kpi_catalog` = **业务治理口径**（`business_definition`、`numerator/denominator`、`grain`、`unit`、`owner`、`version`、`status`），供展示、可信度、对账；
- 二者经 `kpi_catalog.metric_id`（**可空 FK**）弱关联：**业务定义可以先行，技术实现后置**。

**依据（代码事实）**：

- `KpiCatalog` docstring 已明写上述分层与「业务定义先行，技术实现后置」（`models.py:456-467`）；
- 已配套治理字段：`numerator_columns`/`denominator_columns`/`grain_keys`（P1 结构化对账）、`semantic_keywords`（L1 匹配）、`match_threshold`；
- 实测 17 个 `ontology_metric`、16 个 `kpi_catalog` —— 体量小，两层对账可全量做。

**影响面**：

- Manifest 的 `metrics` 段 = 技术口径（必填）+ 可选 `kpi_code` 引用（弱关联，缺失不算错）；
- 发布校验规则：只有技术口径完整（formula/agg/类）的指标才允许激活；
- 治理报表**不进** Neo4j / Milvus（docstring 已定），保持现状。

**备选与否决**：

- ❌ 合并成一张表 —— 业务口径（中文分母说明）与技术口径（列集合）生命周期不同，合并会让「业务定义先行」无法表达；
- ❌ 再造第三套指标模型 —— 明确禁止。

**钉住方式**：Manifest Schema 中 `metrics.kpi_code` 可空；守卫用例「只有 kpi_catalog 无 ontology_metric」不得进激活发布；「只有 ontology_metric」允许但输出治理提示。

**确认**：✅ 2026-11-09 项目负责人确认（业务/治理输入按末尾清单后补，不改变本裁决）

## 裁决四：Manifest 命名 + 发布域作用域

**建议决定**：

1. 冻结报告中的 `SemanticManifest` **改名为 `SemanticReleaseManifest`**（Python 类与 JSON Schema `title` 同步）；
2. 首期发布作用域 = **全企业快照**：`semantic_release.domain_code = NULL`；
3. `domain_code` 非空留给未来「按域独立发布」，本期不实现激活语义，只保留列与校验（非空值必须存在于 `data_domain.code`）。

**依据（代码事实）**：

- 已有 `RelationManifest` 表示「CSV 批量执行载荷」（`backend/app/api/v1/ontology.py:59,740,743`），与新 Manifest 同名会在评审与自动补全中持续混淆；
- `data_domain` 已是域 SSOT，且有 `DataDomain` 表 + `business_object.primary_domain_id` + `business_object_domain` + `agent_definition.data_domains`（`models.py:632-680` 等），实测已有 3 个域、5 个 BO；
- 本体类本身可能被多个域共享（同一 `PurchaseOrder` 既属采购也属财务），按域切快照会立刻面对「同一类两份快照」的一致性问题。

**影响面**：

- P1 表结构：`domain_code` 可空 FK → `data_domain.code`（`ON DELETE RESTRICT`）；
- API：`/api/v1/semantic/releases` 的 `domain` 参数首期只做**过滤**（NULL = 全局），不做「按域发布」；
- 查询期按域过滤走 BO 映射（`business_object.primary_domain_id` / `business_object_domain`），不靠快照切分；
- 采购薄别名 `/api/v1/procurement/*` 只固定 domain 参数转发。

**备选与否决**：

- ❌ 首期就按域发布 —— 多域共享类要处理「同一类多份定义」，复杂度与收益不匹配；
- ❌ 用 `semantic_manifest` 命名 —— 与 `RelationManifest` 混淆，且未来可能还有别的 manifest 类型。

**钉住方式**：命名守卫（新代码禁止出现裸 `SemanticManifest`）；`domain_code` 外键用例（非法域拒绝、NULL 通过）；API 用例（`domain` 参数只过滤、不改激活语义）。

**确认**：✅ 2026-11-09 项目负责人确认
