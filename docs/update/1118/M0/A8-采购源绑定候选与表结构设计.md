## 2. 「34 个采购类」是怎么来的（先把计划前提钉住）

计划行只写「34 个采购类」，没给名单。实测有效类共 **59** 个，按层拆：

```text
DWD_*（有效）14 + ODS_*（有效）20 = 34      ← 与计划数字逐字吻合
另有  DIM_* 3 / bill_* 16 / AI&对账杂项 4 / 资产 2 / 平台自建 2（不在本节范围）
另有  DWD_* 墓碑 15（不计入有效类）
```

⇒ 工作定义：**34 = 有效 `DWD_*` + 有效 `ODS_*`**。`DIM_SUPPLIER` / `DIM_FACILITY` / `DIM_IMATERIAL`
虽是最核心的主数据，但按这个数**不在其中** —— 而 4 条 KPI 的粒度键用的正是 `SUPPLIER_CODE` / `FACILITY_CODE`。
**这是一处需要确认的口径**（不是 34 这个数字错，而是「34 是否就是采购域全集」），已登记 §5 待确认项 Q1。

### 2.1 解析方法（不连外部库）

`ontology_class.source_table` → 在 `schema_cache`（datasource 1 / 2 / 10 的缓存 JSON）里按表名匹配：

```text
命中 1 个 (datasource, schema)        ⇒ unique（conf=high）
命中同库多个 schema                    ⇒ schema-ambiguous（conf=medium）
命中多个库                              ⇒ datasource-ambiguous
零命中                                  ⇒ not-found
```

**为什么用缓存而不是直连**：THBI Oracle（192.168.205.70）/ SRM-TH-01（10.10.101.55）在开发机上不可达；
`schema_cache.updated_time` 为 2026-11-14 / 2026-11-16，是当前可用的最新事实。
**代价**：缓存可能滞后于真实库（新增表/改列不反映）⇒ 结论标 `candidate`，C 问卷核对时以真实库为准。

### 2.2 结果

```text
34 条候选：unique 28 / schema-ambiguous 6 / not-found 0
```

- **not-found = 0** ⇒ 34 个采购类的 `source_table` 全部能落到真实表上，没有「建了类但没有源」的情况；
- **schema-ambiguous = 6** ⇒ `ODS_BPARTNER` / `ODS_PORDER` / `ODS_PPRICFICH` / `ODS_PPRICLIST` /
  `ODS_YPRECEIPT` / `ODS_YPRECEIPTD` 在 `THBI` 与 `ZJTH` 两个 schema 下同名并存。
  实测 **THBI ⊇ ZJTH（ZJTH 独有列数恒为 0）**：5 张差 1 列（`ETL_LOAD_TS`），`ODS_BPARTNER` 差 2 列
  （`ETL_LOAD_TS` + `AUUID_0`）—— 见证据 §F。⇒ ZJTH 是镜像、THBI 是超集。
  **候选取 THBI**，但「哪个是权威层」必须由 C 确认（Q2）。

## 3. 三个必须决策的结构问题（本批最重要的发现）

### 3.1 7 个墓碑类仍被 8 条 KPI 引用 —— 而且不是「重命名」

2026-09-19 有一批采购类被软删除（`valid_to`），其中 **7 个仍在 `ontology_metric_source` 里**，
合计 **15 个「类 × 指标」引用对**，涉及 **8 条不同 KPI**（同一指标可同时引用 2 个墓碑类，故对数 > 指标数）：

| class_id | 类 | 墓碑日 | 关联指标数 |
|---|---|---:|---|
| 20 | `DWD_PURCHASE_ORDER_LINE` | 2026-09-19 | **6** |
| 14 | `DWD_GOODS_RECEIPT_LINE` | 2026-09-19 | 4 |
| 16 / 17 | `DWD_PURCHASE_INVOICE` / `_LINE` | 2026-09-19 | 各 1 |
| 22 / 25 | `DWD_PURCHASE_REQUISITION_LINE` / `DWD_REQUISITION_ORDER_LINK` | 2026-09-19 | 各 1 |
| 27 | `DWD_SUPPLIER_PAYMENT` | 2026-09-19 | 1 |

**「墓碑 = 被 `_DTL` 取代」这个解释不成立**：
`DWD_PURCHASE_ORDER_LINE`（29 列）与 `DWD_PURCHASE_ORDER_DTL`（35 列）**只共享 5 列**
（`PO_NO` / `PO_LINE_NO` / `ORDER_DATE` / `SUPPLIER_CODE` / `UPDATE_DATE`）——
一个是**订单行事实**，另一个是**订单行明细**，不能互相替代。

⇒ **A8 的处置建议（待决策 Q3）**：这 7 个类**必须先复活**（清 `valid_to`）才能谈绑定；
否则 M1-b 的「采购 manifest 覆盖 ≥8 个采购类 + 采购指标」根本连不上 KPI。
复活是**治理动作**（不是本批的写操作），须与 A9 首次发布同批。

> 同一事实在 A6 已暴露（`kpi_alignment_resolver.sourcePropertiesForMetric` 不按 `valid_to` 过滤），
> 本批把它从「模拟口径要对齐」升级为「**建表前必须解决**」。

### 3.2 一个源表挂两个类 —— 绑定键必须含 `class_id`

```text
DWD_SUPPLIER_PRICE_LIST（id=55）  ┐
                                  ├─ 同 source_table = DWD_SUPPLIER_PRICE_LIST
DWD_SUPPLIER_PRICE_LIST_DEL（29） ┘
```

⇒ 任何「按表名定位类」的绑定设计都会在这里错。
`procurement_source_binding` 的唯一键**必须**是 `(class_id, datasource_id, schema_name, source_table, binding_role)`，
而不是 `(datasource_id, source_table)`。

### 3.3 复合主键是常态，不是例外

`schema_cache` 里的真实主键：

| 表 | 主键列数 | 主键 |
|---|---:|---|
| `DWD_PURCHASE_QUOTATION_YEARLY_DTL` | 4 | `PRICE_LIST_CODE`+`PRICE_RECORD_NO`+`PRICE_LINE_NO`+`SEG_YEAR` |
| `DWD_REQUISITION_ORDER_LINK` | 4 | `REQUISITION_NO`+`REQUISITION_LINE_NO`+`PO_NO`+`PO_LINE_NO` |
| `DWD_PURCHASE_INVOICE_LINE` | 3 | `INVOICE_TYPE`+`INVOICE_NO`+`INVOICE_LINE_NO` |
| `DWD_PURCHASE_ORDER_DTL` | 3 | `PO_NO`+`PO_LINE_NO`+`PO_SEQ_NO` |
| `DWD_RECONCILIATION_BILL_DTL` | 3 | `BILL_NO`+`RECEIPT_NO`+`RECEIPT_LINE` |
| `DIM_SUPPLIER` / `ODS_PORDER` | **0** | 无主键（ODS/外部表常见） |

⇒ 这正是 **D2 决策「复合键走独立列、不进 JSON」** 的事实依据：
`key_ordinal` 必须是真列，才能做「同一绑定的键序号唯一」的库级约束；
而「无主键」的 ODS 表意味着回放/去重**必须**依赖业务键，不能依赖 `rowid`。

## 4. 两张表的列级设计（供 M1-1.1 实现）

> 设计三原则：① 同表双类靠 `class_id` 区分；② 有效期用**真列 + 部分唯一索引**（不用 JSON）；
> ③ 候选标记是**库级**的，不靠文档约定。

### 4.1 `procurement_source_binding`（类 → 源表）

| 列 | 类型 | 空 | 说明 |
|---|---|:-:|---|
| `id` | `BIGSERIAL` | | 主键 |
| `class_id` | `BIGINT` | ✗ | FK → `ontology_class(id)` `ON DELETE RESTRICT`（类被删则绑定不许静默失效） |
| `datasource_id` | `BIGINT` | ✗ | FK → `data_source(id)` `ON DELETE RESTRICT` |
| `schema_name` | `VARCHAR(100)` | ✗ | Oracle owner / PG schema / MySQL database |
| `source_table` | `VARCHAR(100)` | ✗ | 物理表名（可 ≠ `class_name`，如 `DWD_SUPPLIER_PRICE_LIST_DEL` → `DWD_SUPPLIER_PRICE_LIST`） |
| `binding_role` | `VARCHAR(20)` | ✗ | 复用既有 `MetricSourceRole`：`BASE` / `NUMERATOR` / `DENOMINATOR` / `FILTER` |
| `filter_expression` | `TEXT` | ✓ | 该源表的行级谓词（如 `STATUS <> 'X'`） |
| `filter_allowlist` | `TEXT[]` | ✓ | 允许在 `filter_expression` 里出现的标识符/函数名单（**独立列，不进 JSON**，D2） |
| `is_candidate` | `BOOLEAN` | ✗ | 默认 `TRUE`；`FALSE` 才允许进 manifest |
| `confirmed_by` | `VARCHAR(100)` | ✓ | 确认人（C 问卷核对后填） |
| `confirmed_time` | `TIMESTAMPTZ` | ✓ | 确认时间 |
| `valid_from` | `TIMESTAMPTZ` | ✗ | 默认 `now()` |
| `valid_to` | `TIMESTAMPTZ` | ✓ | `NULL` = 当前生效 |
| `created_by` / `created_time` / `updated_time` | | | 同仓内其它表 |

约束：

```sql
-- 同一类在同一数据源上，同一角色只允许一条「当前生效」绑定
CREATE UNIQUE INDEX uq_proc_src_binding_active
  ON procurement_source_binding
     (class_id, datasource_id, schema_name, source_table, binding_role)
  WHERE valid_to IS NULL;

CHECK (valid_to IS NULL OR valid_to > valid_from)
CHECK (NOT is_candidate OR confirmed_by IS NULL)   -- 候选不得有确认人（反之亦然）
CHECK (binding_role IN ('BASE','NUMERATOR','DENOMINATOR','FILTER'))
```

### 4.2 `procurement_property_binding`（属性 → 列 / 复合键位）

| 列 | 类型 | 空 | 说明 |
|---|---|:-:|---|
| `id` | `BIGSERIAL` | | 主键 |
| `source_binding_id` | `BIGINT` | ✗ | FK → `procurement_source_binding(id)` `ON DELETE CASCADE` |
| `property_id` | `BIGINT` | ✗ | FK → `ontology_property(id)` `ON DELETE RESTRICT` |
| `source_column` | `VARCHAR(100)` | ✗ | 物理列名（**允许 ≠ `ontology_property.source_column`**，否则这张表没有存在意义） |
| `key_ordinal` | `SMALLINT` | ✓ | 复合键序号（1..n）；`NULL` = 非键列 |
| `transform_expression` | `TEXT` | ✓ | 列级表达式（`TRUNC(x)` / `UPPER(x)` / 单位换算）；为空 = 直读 |
| `is_candidate` / `confirmed_by` / `confirmed_time` | | | 同 4.1 |
| `valid_from` / `valid_to` | | | 同 4.1 |

约束：

```sql
-- 一个绑定内，同一属性只允许一条生效映射
CREATE UNIQUE INDEX uq_proc_prop_binding_active
  ON procurement_property_binding (source_binding_id, property_id)
  WHERE valid_to IS NULL;
-- 一个绑定内，键序号不得重复
CREATE UNIQUE INDEX uq_proc_prop_binding_key_ordinal
  ON procurement_property_binding (source_binding_id, key_ordinal)
  WHERE key_ordinal IS NOT NULL AND valid_to IS NULL;
CHECK (key_ordinal IS NULL OR key_ordinal >= 1)
```

### 4.3 为什么不用 `ontology_property.source_column` 就够了

`source_column` 是**单源假设**（一个属性只能指一个源表的一列）。采购域实际有三处它表达不了：

1. **同属性多源**（ERP 与 SRM 都有供应商编码，取值优先序不同）；
2. **列级变换**（`TRUNC(RECEIPT_DATE)`、金额单位换算）；
3. **复合键位**（4 列主键需要「哪几列、按什么次序」构成唯一键）。

⇒ 属性级绑定表**必需**，与 `ontology_property.source_column` 并存（后者继续作为"主源直读"的快捷路径，不冲突）。

### 4.4 落库时机与迁移号

- **迁移号**：当前 head = `0153`；`0154` 已被 **A4-0**（审批面 `subject_id`）预留。
  ⇒ M1 两张表**顺延 `0155` / `0156`**，落库前须按当时 head 复核（本仓铁律：迁移号串行占号，不许插队）。
- **DDL 属 M1-1.1**，不在本批；本批只交付设计 + 候选数据。
- 建表后 `procurement_*` 表**不得**与 `semantic_release` / `workflow_*` 语义重复（D1 守卫用例已覆盖）。

## 8. 复现

```bash
# 34 条解析（只读；不连外部库）
docker exec qa-postgres psql -U qa_user -d qa_metadata -A -F ' | ' -c "
WITH t AS (SELECT s.datasource_id, upper(t->>'table_name') tbl, t->>'owner' owner
           FROM schema_cache s, LATERAL jsonb_array_elements(s.schema_data) t),
     m AS (SELECT c.id, c.class_name, upper(c.source_table) src,
                  (SELECT count(*) FROM ontology_property p WHERE p.class_id=c.id) props
           FROM ontology_class c WHERE c.valid_to IS NULL
            AND (c.class_name LIKE 'DWD\_%' OR c.class_name LIKE 'ODS\_%'))
SELECT m.class_name, m.props, m.src, string_agg(DISTINCT t.datasource_id||':'||t.owner, ', ')
FROM m LEFT JOIN t ON t.tbl=m.src GROUP BY m.id,m.class_name,m.props,m.src ORDER BY 1;"

# 完整证据（含列级缺口 / 墓碑引用 / 同表双类 / 未建模表）

```
