## 1. 本手册能确认什么、不能确认什么

**能确认**（本手册的两条验收路径都已实测通过）：

- 编排：提交 → 按定义顺序执行命令步骤 → 遇审批门暂停 → 审批通过后继续 → `COMPLETED`
- 审批：按矩阵生成任务、四眼拦截（提交人不得自批）、越权不可见、重复/超时拒绝
- 幂等：同一 `idempotencyKey` 重放返回同一实例，不落新行
- 取消：实例 `CANCELLED`、未执行步骤 `SKIPPED`、待办审批 `CANCELLED`、原因落库
- 审计：提交 / 审批发起 / 审批决策 / 取消 全部进 `audit_log`

**不能确认**（不是缺陷，是范围）：

- **真实业务写回**：执行器是 `SimulatedCommandHandler`，不发真实 ERP/SRM 请求。
  接真实适配器是独立批次。
- **前端交互**：P5 **后端批次**只交付 API。本分支另加了两个前端批次：
  **最小前端批次**（实例列表/详情、待办审批、提交表单，见
  `Harness/changes/2026-11-17-p5-workflow-ui/summary.md`，验收见本文 §7）与
  **定义管理批次**（新建/编辑/发布/停用定义 + 审批矩阵行，见
  `Harness/changes/2026-11-17-p5-workflow-definition-admin/summary.md`，验收见本文 §7.1）；
  更细的页面（业务对象页跳转提交）仍不在范围内。
- **生产行为**：生产尚未部署（alembic 仍 0143，P5 的 0149–0152 未上），
  部署步骤见 `Harness/changes/2026-11-16-p5-workflow-command/deploy-prod-1117.md`。

本地准备（compose 栈）：

```bash
# 1. 开开关：在 docker/.env 增加一行
echo 'ENABLE_WORKFLOW=true' >> docker/.env

# 2. 重建并启动后端（迁移随启动执行）
docker compose -f docker/docker-compose.yml build backend
docker compose -f docker/docker-compose.yml up -d backend

# 3. 起 worker（与后端同镜像，独立进程）
docker run -d --name qa-workflow-worker --network qa-system_default \
  --env-file docker/.env -e ENABLE_WORKFLOW=true \
  --restart unless-stopped qa-system-backend \
  python -m app.workers.workflow_worker
```

> 本地若 `AUTH_STUB_ENABLED` 未显式关闭，启动会打印一条
> "ENABLE_WORKFLOW=true 但鉴权仍为 stub" 的警告。这不影响验收：
> 审批决策要求 `isRealIdentity`（JWT 验签过），用 `/auth/login` 拿到的令牌满足；
> 生产环境必须显式关闭 stub。

提交人账号注意：`POST /api/v1/users` 建出的用户 `mustChangePassword=true`，
直接调业务接口会 403 `MUST_CHANGE_PASSWORD`。先由 admin 调
`PUT /api/v1/users/{id}/password`（`{"newPassword":"...","forceChangeOnNextLogin":false}`）清掉。

## 3. 一键冒烟（推荐）

```bash
ADMIN_PASSWORD='<本地 admin 密码>' \
SUBMITTER_USER=wf_submitter \
SUBMITTER_PASSWORD='<提交人密码>' \
./scripts/acceptance/p5_smoke.sh
```

脚本自检并执行四个场景，共 **29 项断言**，每项都同时核对 HTTP 结果与落库状态
（不只断言状态码）：

| 场景 | 断言要点 |
|---|---|
| 1/4 全链路 | 201 → `WAITING_APPROVAL` → 生成 1 条待办 → 非审批人 404 → 审批 200 → `COMPLETED` → 3 步 `SUCCEEDED` → 审计 3 条 |
| 2/4 幂等重放 | 同 key 返回 200、同一实例 id、库中该 key 仅 1 行 |
| 3/4 取消 | `CANCELLED` → 2 步 `SKIPPED` → 审批 `CANCELLED` → 原因落库 |
| 4/4 四眼 | 审批人自己提交、自己批 → 403 |

预期结尾：

```
通过 29 项，失败 0 项
验收通过
```

脚本安全边界：默认**拒绝**对非 `localhost` 地址运行（确需如此须显式
`ALLOW_NON_LOCAL=1`）；只做加法（写定义/实例/审批/审计），不删任何数据；
数据库密码从 `$PG_CONTAINER` 的容器环境读取，不落盘。

## 4. 手工验证（逐步）

前置：定义已发布。检查：

```sql
SELECT id, domain_code, capability_code, version, status FROM workflow_definition;
-- 期望有一条 procurement / po_write / v1 / PUBLISHED
```

定义体（`definition_json`）的关键三段：

- `steps`：`collect`(commandType `po.write`) → `gate`(requiresApproval) → `submit`(commandType `po.write`)
- `riskLevel`：`MEDIUM`（**服务端绑定，客户端不得自选**）
- `approvalMatrix`：`subjectType=workflow_instance` + `capabilityCode=po_write` + `riskLevel=MEDIUM` → `approverUser=admin`

### 4.1 提交

```bash
SUB=$(curl -s -X POST http://localhost:8000/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"wf_submitter","password":"<密码>"}' | jq -r .accessToken)

curl -s -X POST http://localhost:8000/api/v1/workflow/instances \
  -H "Authorization: Bearer $SUB" -H 'Content-Type: application/json' \
  -d '{"domainCode":"procurement","capabilityCode":"po_write","version":"v1",
       "idempotencyKey":"manual-001","request":{"poNo":"PO-MANUAL","amount":100}}' | jq
```

期望 `201`，`status=WAITING_APPROVAL`（第一步已执行，停在审批门）。

### 4.2 审批

```bash
ADM=$(curl -s -X POST http://localhost:8000/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"<密码>"}' | jq -r .accessToken)

curl -s -H "Authorization: Bearer $ADM" \
  http://localhost:8000/api/v1/workflow/instances/1/approvals | jq
# 取 PENDING 任务的 id

curl -s -X POST http://localhost:8000/api/v1/workflow/approvals/<taskId>/decision \
  -H "Authorization: Bearer $ADM" -H 'Content-Type: application/json' \
  -d '{"decision":"APPROVE","note":"同意"}' | jq
```

期望 `200`；稍候（worker 轮询）实例转 `COMPLETED`。轮询：

```bash
curl -s -H "Authorization: Bearer $ADM" \
  http://localhost:8000/api/v1/workflow/instances/1 | jq '.instance.status'
```

### 4.3 幂等重放

重复 4.1 的同一条请求（同 `idempotencyKey`）⇒ 期望 **`200`**、`.id` 与首次相同。

### 4.4 取消

```bash
curl -s -X POST http://localhost:8000/api/v1/workflow/instances/<id>/cancel \
  -H "Authorization: Bearer $SUB" -H 'Content-Type: application/json' \
  -d '{"reason":"手工验收取消"}' | jq
```

期望 `200`、`status=CANCELLED`；详情中未执行步骤 `SKIPPED`、待办审批 `CANCELLED`。

### 4.5 守卫（负向用例）

| 操作 | 期望 |
|---|---|
| 提交人调用 `/approvals/{taskId}/decision` | `404`（对象级不可见，与"不存在"同形） |
| 已决策任务再次决策 | `409` |
| 审批人自己提交的实例自己批 | `403`（四眼） |
| 请求体多传 `riskLevel` | `422`（`extra="forbid"`） |
| 开关关闭时访问任意 `/workflow/*` | `404`（路由未注册） |

## 6. 已知边界（验收结论需注明）

1. 执行器为模拟实现，**不产生真实单据**。
2. 前端有两个批次（本文 §7 / §7.1）：实例与审批页、定义管理页。审批矩阵在**定义编辑器内**
   编辑（矩阵行），没有独立的矩阵管理页。
3. 提交权当前仅要求登录：任何登录用户可提交任何已发布能力，**尚未收口到角色/域**——
   这是产品决策项，不是本批缺陷。
4. `workflow_outbox` 当前无独立消费者（worker 直接轮询实例）；接真实适配器时再定 outbox 语义。
5. 生产未部署；生产验收须按 `deploy-prod-1117.md` 走一遍，且审批人必须真实身份。

| 2 | 点「详情」 | 抽屉展示状态、幂等键、错误信息、步骤时间线（绿=成功/红=失败/紫=补偿）与审批记录表 |

| 6 | 点「通过」（填意见）或「驳回」（**意见必填**） | 决策成功后列表立即刷新，该任务不再出现在待办里 |

## 7.1 UI 验收（定义管理批次）

> 本批次随本分支交付：`/workflow/definitions`（列表 + 新建/编辑 + 审批矩阵行 + 发布/停用）。
> 菜单由 `seed_menu_config.py` 播种（`item.workflowDefinitions`），已挂载的库需重跑 seed。
> **定义体决定「谁批这件事」** ⇒ 写入口是安全边界：仅 admin 可写，写入必过运行时校验器，
> 校验权只在后端一处（前端不复制规则）。

| # | 操作 | 期望 |
|---|---|---|
| 1 | admin 登录 → 「业务配置 → 工作流定义」 | 列表显示域/能力/版本/状态；**admin 可见定义体与审批矩阵**（非 admin 无此菜单） |
| 2 | 点「新建定义」→ 填域代码/能力代码/版本/步骤编码/命令类型/勾「需要审批」/矩阵编码/审批角色/超时小时 → 确 定 | 列表新增一行，状态为**草稿**；「版本」与同域同能力下已有定义冲突时报错 |
| 3 | 步骤留空（或既无命令类型又无需要审批）/ 矩阵缺审批人 | **保存即报错**，后端 422；坏定义**写不进去**（失败关闭） |
| 4 | 草稿行点「发 布」 | 状态变**已发布**；同一域+能力已有发布版时点发布 ⇒ 报错（至多一个 PUBLISHED） |
| 5 | 已发布行点「停 用」 | 状态变**已停用**；发布过/停用过的行**不可编辑**（编辑仅草稿可用） |

| 7 | 用 §7 提交表单提交 §7.1 新建并发布的定义 | 实例进入 `WAITING_APPROVAL`，且生成 1 条待办审批（矩阵命中）⇒ 前台建的定义**可直接用于运行** |
