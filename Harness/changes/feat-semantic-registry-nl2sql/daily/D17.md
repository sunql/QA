## 2. 实测细节

### 2.1 判据 1：影子差异 0 ✅

```
OFF 回报发布 id = None（必须为 None）
ON  回报发布 id = 1（必须为 ACTIVE id）
两态 schema 文本行数：OFF=602 / ON=602
内容差异块数 = 0（必须 0）
整段文本行序差异 = 1064 行（D14 已知差异，不计失败）
```

排除了第三种可能（不是差在别处）：关键过滤口径摘要段**按限定名排序、截断也稳定**
（`nl2sql_schema.py:531-543`）⇒ 两态摘要段内容相同，不存在「截断切掉了不同条目」。
⇒ 两态唯一差异就是 **类内列序 + JOIN 条目序**。

### 2.2 判据 2：回放一致 ❌（确定性差异）

| 问题 | 对照（关 vs 关） | 对照（开 vs 开） | 实验（关 vs 开） |
|---|---|---|---|
| 各供应商的收货明细条数 | 逐字相同=True / 列集合相同=True | 逐字相同=True / 列集合相同=True | **逐字相同=False / 列集合相同=False** |
| 各供应商的到货明细数量合计 | 逐字相同=True / 列集合相同=True | 逐字相同=True / 列集合相同=True | **逐字相同=False / 列集合相同=False** |

差异不是"SELECT 列顺序 / 别名"这种无关紧要处，而是**过滤口径**：

**问题 ①**

```
OFF: SELECT s.BPSNUM_0 AS SUPPLIER_CODE, s.BPSNAM_0 AS SUPPLIER_NAME, COUNT(d.RCV_LINE_NO) AS RECEIPT_LINE_COUNT
       FROM DWD_GOODS_RECEIPT_DTL d JOIN DIM_SUPPLIER s ON d.SUPPLIER_CODE = s.BPSNUM_0
      WHERE d.INTER_COM_CODE = '1' AND d.INTER_SITE_CODE = '1'
        AND LENGTH(s.BPSNUM_0) > 2 AND s.BPSNUM_0 NOT IN ('T01', 'D01')
      GROUP BY s.BPSNUM_0, s.BPSNAM_0 ORDER BY RECEIPT_LINE_COUNT DESC NULLS LAST
ON : SELECT d.SUPPLIER_CODE, s.BPSNAM_0 AS SUPPLIER_NAME, COUNT(d.RCV_LINE_NO) AS RECEIPT_LINE_COUNT
       FROM DWD_GOODS_RECEIPT_DTL d JOIN DIM_SUPPLIER s ON d.SUPPLIER_CODE = s.BPSNUM_0
      WHERE d.INTER_COM_CODE = '1' AND d.INTER_SITE_CODE = '1'
      GROUP BY d.SUPPLIER_CODE, s.BPSNAM_0 ORDER BY RECEIPT_LINE_COUNT DESC NULLS LAST
```

ON 态丢了两条供方口径（长度过滤、排除测试供方），分组键也从 `s.BPSNUM_0` 换成 `d.SUPPLIER_CODE`。

**问题 ②**

```
OFF: SELECT a.SUPPLIER_CODE, s.BPSNAM_0 AS SUPPLIER_NAME, SUM(a.ARR_QTY) AS TOTAL_ARR_QTY
       FROM DWD_ARRIVAL_ORDER_DTL a
       JOIN DIM_SUPPLIER s ON a.SUPPLIER_CODE = s.BPSNUM_0
       JOIN DIM_IMATERIAL m ON a.ITEM_CODE = m.ITMREF_0
      WHERE a.DOC_STATUS_CODE = '3' AND s.ENAFLG_0 = 2
        AND LENGTH(s.BPSNUM_0) <> 2 AND s.BPSNUM_0 NOT IN ('T01', 'D01')
        AND m.TCLCOD_0 IN ('A02', 'A03', 'A04', 'A05')
      GROUP BY a.SUPPLIER_CODE
ON : SELECT a.SUPPLIER_CODE, s.BPSNUM_0, s.BPSNAM_0, SUM(a.ARR_QTY) AS TOTAL_ARR_QTY
       FROM DWD_ARRIVAL_ORDER_DTL a JOIN DIM_SUPPLIER s ON a.SUPPLIER_CODE = s.BPSNUM_0  -- 少了 DIM_IMATERIAL 的 JOIN
      WHERE s.BPSNUM_0 NOT IN ('T01', 'D01') AND LENGTH(s.BPSNUM_0) > 2
```

ON 态丢了「启用供应商」`ENAFLG_0 = 2` 与「生产型物料」`TCLCOD_0 IN (...)` 两个口径，
也丢了整个 `DIM_IMATERIAL` 的 JOIN（连带 `LENGTH(...) <> 2` 变成 `> 2`）。

⇒ **结果集不同 ⇒ 回答会不同**。这不是格式漂移。

## 4. 根因：为什么会变，以及为什么不能简单对齐

**两侧顺序为什么必然不同**

| 侧 | 顺序来自 | 是否契约 |
|---|---|---|
| 直读（开关关） | ORM 关系物理行序（`OntologyClass.properties` **无 ORDER BY**）；JOIN 按自增 id（插入序） | ❌ 跨环境/跨机器不稳定 |
| 快照（开关开） | 编译器**显式排序**：属性按 `propertyName`、JOIN 按 `joinKey`（`semantic_compiler.py:217` / `:287`），为的是 manifest 字节确定性 | ✅ 已发布即固定 |

⇒ 内容相等、顺序必然不同 ⇒ prompt 不同 ⇒ 模型对行序敏感 ⇒ 计划与 SQL 都变。

**为什么不能"把快照侧改成直读顺序"（这个方向是错的）**

`test_semantic_schema_adapter.py::Test顺序确定性` 钉死了相反的原则：
快照列序必须由 **manifest 自己**决定，否则同一版发布在不同机器 / 不同时间会渲染出不同文本
⇒ **D16 的「钉住 ⇒ 重放读同一版 ⇒ 同一口径」直接塌掉**。而直读侧顺序本身又不是契约
（见上表）。所以「快照向直读对齐」是把稳定的一侧去迁就不稳定的一侧，方向反了。

**唯一结构性解法**（本次**不做**，见 §5）：让 **两侧都按同一规范顺序**渲染
（属性按限定名、JOIN 按 joinKey）⇒ ON/OFF 逐字节相同，G3 结构性通过，
并顺带修掉「直读顺序跨机器不稳定」这个既有隐患。代价是**会一次性改变今天（开关关）的 prompt 与回答**。
