## 三、试点数据集设计（真实数据 · 隔离库）

目标库：`qa_metadata_test_pilot`（5434，与集成夹具用的库**分开**，避免 `data_domain.code` /
`organizations.code` / `uq_business_object_header_class` 撞车；**绝不碰生产**）。

| 形状 | 内容 | 作用 |
|---|---|---|
| 组织 | `PROCUREMENT_ORG`（采购部）/ `QUALITY_ORG`（质量部）/ `OUTSIDE_ORG`（其它部） | 域主组织绑定 + 「不拥有任何域」的组织 |
| 数据域 | `PROCUREMENT → PROCUREMENT_ORG`、`QUALITY → QUALITY_ORG`；`LOGISTICS` 保持 NULL | 可见性推导的唯一抓手；`LOGISTICS` 是 fail-closed 样本 |
| 本体类 | `Supplier` / `PurchaseOrder` / `Receipt` / `ItemMaster`（采购域）+ `IncomingInspection`（质量域） | 复用迁移 0040 的类，只补别名 / 属性 / 物理表 |
| 属性 | 13 条（含 `Supplier.delivery_days`、`Receipt.receipt_qty`、`ItemMaster.material_spec`、`IncomingInspection.pass_rate`） | 各路召回的命中面 |
| JOIN | `po_supplier`、`gr_po`（采购域内）+ `iqc_gr`（**跨域**，质量→采购） | 域内 JOIN 命中；跨域 JOIN 被切片排除 |
| 指标 / KPI | 3 指标（`supplier_delivery_days` / `po_amount` / `iqc_pass_rate`）+ 3 KPI（`KPI_DELIVERY` / `KPI_PO_AMOUNT` / `KPI_IQC`），**全 DRAFT** | 指标路与 KPI 命中；DRAFT ⇒ 不伪造治理状态 |
| 业务对象 | 5 条（BO → headerClass → 主域） | 域切片的**唯一**锚点（C-3） |
| 发布 | 走**真实写路径** `createDraft → markValidated → activate`，两域各一版 ACTIVE | manifest 由**真实编译器**从**真实治理表**编译；闸门真跑；审计真写 |

> ⚠️ **为什么必须走真实写路径**：快照若是手写塞进去的，验的就不是生产里那条路
> （编译器 / 发布闸门 / 哈希 / 审计全被绕开）⇒ 试点通过率没有意义。

**逐路状态 + 证据 ref 集合完全一致** ⇒ 「别名 = 同一逻辑」由**真实数据**证明，
而不是只靠 AST 守卫证明「没有分支」（C-9）。

## 七、开发过程中真实踩到并修掉的坑

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `psql` 报 `connection to server on socket "/tmp/.s.PGSQL.5432" failed` | `psql` 不认 `postgresql+asyncpg://` 这个 SQLAlchemy 方言前缀 ⇒ 把它当成本地 socket 连 | 查询前把前缀换成 `postgresql`：`${PILOT_URL/postgresql+asyncpg/postgresql}` |
| 2 | `column "id" does not exist`（`data_domain`） | `data_domain` 的**主键是 `code`**（varchar），不是自增 `id`；`semantic_release` 存的是 `version` | 按真实列名改查询（`WHERE code = …` / `WHERE version = …`） |
| 3 | `TypeError: 'created_by' is an invalid keyword argument for OntologyProperty` | `OntologyProperty` 只有 `TimestampMixin`（无 `created_by` 列），而 `OntologyClass` / `OntologyJoin` / `OntologyMetric` / `KpiCatalog` / `BusinessObject` 有 | 属性插入去掉该 kwarg；重跑 ⇒ 落库成功 |
| 4 | 度量写 `className` 被编译器拒（"不应自带 className"） | 度量里的类引用是 `class_id`（JSON 内嵌引用），编译器负责归一成 `className`（C-4） | 播种改写 `class_id` + `class_alias`；**先读编译器再写数据**，省掉一轮试错 |
| 5 | JOIN 源类写成不存在的 `GoodsReceipt` | 迁移 0040 的类名是 `Receipt`（`DWD_GOODS_RECEIPT` 只是物理表名） | 改成 `Receipt`；发布闸门随即通过 |
| 6 | 一度把 `agg_function` 与 `aggregation_order` 塞进同一个元组位 | 两个概念不同（聚合函数 AVG/SUM vs 比率聚合阶 NONE/WEIGHTED_RATIO） | `_METRICS` 结构重排，**两个字段各自独立** |
| 7 | 差点直写 `status=PUBLISHED` 让指标「看起来已发布」 | 那等于**伪造一个没走过治理闸门的状态**（C-6）⇒ 「已发布」就失去含义 | 指标 / KPI 一律 `DRAFT`；发布闸门只对 PUBLISHED 的 RATIO/DIFFERENCE 硬拒（C-5）⇒ DRAFT 天然不挡；知识服务读的是**语义发布快照**，与治理状态正交（C-7） |
| 8 | `scope` 支持先写了实现、后写测试 | 违反 TDD 顺序 | **RED 验证**：临时把 `scope=_scopeOf(raw)` 改回 `scope=None` ⇒ `test_parseQuestionSetReadsRequestScope` 与 `test_parseQuestionSetRejectsIllegalScope` 两条**真的红**（2 failed / 13 passed）⇒ 还原 ⇒ 15 passed |

## 八、约定沉淀（避免下一批再踩）

1. **试点数据要走真实写路径**：手写快照 ⇒ 试点通过率没有意义。
2. **先读编译器 / 闸门再写数据**：`class_id` vs `className`、`agg_function` vs `aggregation_order`、
   `PUBLISHED` vs `DRAFT` 三处，写错一次就是一轮试错。
3. **「无逻辑」要两种证据**：AST 守卫（没有分支）+ **运行时等价**（两边响应逐项一致）⇒ 只有后者能证「同一逻辑」。
4. **判定逻辑必须是纯函数**：判据藏在脚本里 ⇒ 脚本一改判据跟着变，且没人说得清「通过」怎么算的。
5. **空集 / 降级 / 拒绝必须分开判**：`EMPTY`（查了没命中）/ `DEGRADED`（能力不可用）/ `DENIED`（无权查）三者混为一谈 ⇒ 越权泄漏会伪装成「查不到」。
6. **成对问题证明域隔离**：同一问题在两个域各问一次、结果**必须不同** ⇒ 否则「跨域可用」可能只是「换个参数结果不变」。
7. **隔离库要与集成夹具的库分开**：撞 `data_domain.code` / `organizations.code` / BO 唯一键会让夹具互相污染。
