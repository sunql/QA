## 一、核心定位对比

| 设计蓝图 | QA System 实际定位 |
|---------|-----------------|
| **Enterprise LLM Wiki** = 业务对象 Wiki + 知识图谱 + Evidence 证据链 + Agent 检索层 | **对话式 NL2SQL + AI Agent 平台** |
| RAG 是 Wiki 的辅助检索能力 | NL2SQL 是核心能力，文档 RAG 是 Phase 5 待做的事 |
| 知识编译生产线（文档 → Claim → Evidence → Page） | 仅实现了 Page 的手动 CRUD，尚无自动编译管线 |

**Gap 本质**：设计中的「知识自动化」vs 实现中的「知识管理工具」。

## 三、尚未实现 ❌

### 高优先级（影响 LLM Wiki 核心价值）

| 缺失功能 | 设计蓝图章节 | 说明 |
|---------|-----------|------|
| **Knowledge Compiler 管线** | §16-18 | 文档 → 知识编译 → Page 的自动化流水线，当前只能手动 CRUD |
| **Evidence 自动绑定** | §13, §19 | 从源文档自动提取 Evidence 5 元组（来源/页码/小节/段落/原文）并绑定到 Claim |
| **冲突检测** | §19 | 多制度对同一规则定义矛盾时，不允许直接覆盖，生成 Conflict 记录等待裁决 |
| **Authority Level 自动判定** | §14, §40 | L5-L0 权威等级，未与来源文档绑定 |
| **Knowledge 版本管理（Page 级）** | §15 | 知识页面版本化（created/effective/expired/superseded），当前 WikiPage 有 `status` 但无版本链 |

### 中优先级（影响企业级落地）

| 缺失功能 | 设计蓝图章节 | 说明 |
|---------|-----------|------|
| **Knowledge ACL 权限** | §57-58 | 按 Organization/Role/Domain 的知识可见性控制，当前仅 owner-based ACL |
| **Knowledge 质量评分** | §20 | `Knowledge Score = 来源权威性 × 证据完整性 × 时效性 × 一致性 × 人工审核` |
| **Agent API 工具集** | §21-26 | `wiki_search / wiki_read / wiki_links / entity_search / relation_query / evidence_get` 尚未标准化暴露 |
| **SQL Agent** | §27 | 非 Wiki 查询（直接 SQL 能力），当前 NL2SQL 已覆盖但无独立 SQL Agent |
| **多租户 tenant_id** | §58 | 设计中明确要求，当前未实现 |
| **Redis 缓存本体** | 设计02 六 | 文档建议 Redis 缓存热门 Class/Metric 定义，当前跳过 |

### 低优先级（可后续迭代）

| 缺失功能 | 设计蓝图章节 |
|---------|-----------|
| **pBOM 多站点支持** | `multisite-pbom-*.md` 独立模块 |
| **SL Segment Routing 多模型路由** | 设计偏差：仅实现了加权随机 |
| **字段级血缘** | 当前仅 TABLE 级血缘 |
| **文档自动分块策略自定义** | 当前固定 512 tokens |

## 四、与设计蓝图的设计偏差

| 设计项 | 现状 | 偏差原因 |
|--------|------|----------|
| 多租户 tenant_id | 未实现 | MVP 阶段不需要，架构预留字段 |
| Redis 缓存本体 | 未实现 | 当前规模下性能可接受，优先级低 |
| SL(Segment Routing) 多模型路由 | 部分实现 | 只做了加权随机 + 成本阈值，未做 Segment Routing |
| 完整 Data Lineage | 部分实现（边） | 字段级血缘未实现，只有表级血缘 |
| APScheduler 调度 | 改为 croniter + 独立 worker | APScheduler 绑定进程生命周期，croniter 更轻量独立 |
