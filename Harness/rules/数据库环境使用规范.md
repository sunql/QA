# 数据库环境使用规范

## 强制要求（CRITICAL，不可违反）

本仓库存在**两个 PostgreSQL 库**，开发与测试必须按下列规则使用，禁止混用：

| 库名 | 用途 | 何时使用 |
|---|---|---|
| `qa_metadata` | **正式数据库**（prod 同源，含 35 万 entity_mapping 等真实业务数据） | **表结构修改 / 新增表 / 数据迁移类需求**：必须先用 prod `qa_metadata` 开发的全部流程 |
| `qa_metadata_test` | **单元 / 集成测试库**（手动建空库） | pytest 集成测试（`TEST_DATABASE_URL` 必须显式指向它，详见 `测试规范.md`） |

## 默认规则

1. **涉及「表结构修改」或「新增表」的开发需求**：必须直接使用 prod `qa_metadata` 进行开发。
2. **执行任何 alembic upgrade / 表 DDL / 数据 INSERT|UPDATE|DELETE 之前**：必须先**备份受影响的表**。
3. **备份表命名约定**：`<原表名>_<YYYYMMDD>`（日期戳用本地日历日，例如 `organizations_20260908`）。
4. 备份完毕后即可在 prod `qa_metadata` 上跑迁移 / 改数据，不再回退到 `qa_metadata_test`。

## 为什么（本仓库实踩的坑）

- **两库 schema 漂移**：`qa_metadata_test` 与 prod `qa_metadata` 表结构可能不一致（Alembic 迁移未同步、初始数据缺失、列默认值差异），在 test 库跑通的迁移上线 prod 直接炸。
- **丢失真实业务数据特征**：prod 有 35 万 entity_mapping 等规模数据，PG 行为（执行计划、约束并发、索引选择）在 test 库空数据上不可复现，迁移可行性论证不足。
- **回滚盲区**：用户改 prod 数据的决策路径与改 test 数据的决策路径完全不同，在 test 库做的 DDL 演习与 prod 真实效果可能差异巨大；备份 + 直接改 prod 路径让决策证据更强。
- **典型事故**：`feat-org-tree` (commit 0046) 涉及 `organizations` 表加 `sort_order` 列 + 复合索引，直接 prod 跑 alembic upgrade + 一次 POST/PUT 冒烟覆盖全路径，避免了 test 库跑通的索引在 prod 命中行为差异。

## 备份操作流程（标准动作）

每次涉及 prod `qa_metadata` 的表结构 / 数据变更前：

```bash
# 1. 确认 prod 库连接（不要连错库）
docker exec qa-postgres psql -U qa_user -d qa_metadata -c "\dt" | grep -E "<待改表名>"

# 2. 备份表（DDL 含结构 + 数据）
docker exec qa-postgres pg_dump -U qa_user -d qa_metadata -t <table> > /tmp/<table>_<YYYYMMDD>.sql
# 或者纯数据备份（带结构备份给「我重置用」）：
docker exec qa-postgres pg_dump -U qa_user -d qa_metadata --table=<table> --no-owner > /tmp/<table>_<YYYYMMDD>.sql

# 3. 在 prod 上做迁移 / DDL
docker exec qa-backend bash -lc 'cd /app && alembic upgrade head'   # 或对应 SQL
# 或
docker exec qa-postgres psql -U qa_user -d qa_metadata -c "ALTER TABLE ..."

# 4. 冒烟：跑对应 API + 验证
curl -s -H "X-User-Id: admin" http://localhost:8000/api/v1/<endpoint> | jq .

# 5. 若 prod 改 DDL 且回归需要，把 schema 同步到 qa_metadata_test
TEST_DATABASE_URL=postgresql+asyncpg://qa_user:qa_pg_dev_2026@localhost:5434/qa_metadata_test \
  .venv/bin/alembic upgrade head
```

## Alembic 迁移编写约束（2026-09-13 起）

1. **revision id 必须 ≤ 32 字符**。`alembic_version.version_num` 是
   `character varying(32)`。超长时写版本号会抛
   `StringDataRightTruncationError: value too long for type character varying(32)`，
   而且**发生在 `upgrade()` 的 DDL 执行之后、版本号落库之前** —— 库会被留在
   「对象已建、版本没动」的半截状态，重跑时 `IF NOT EXISTS` 又让它看似正常。
   实测：`0062_document_catalog_content_hash_unique`（41 字符）踩中，
   改为 `0062_doc_catalog_hash_unique`（28 字符）。**新迁移先数长度。**
2. **`downgrade()` 必须对称反转 `upgrade()`**。不要为了「只撤其中某一项」把
   downgrade 改成不对称：库会停在一个**没有任何 revision 描述**的状态
   （`alembic_version` 回到上一版而对象仍在），而「版本号相同 ≠ 结构相同」
   正是本仓库 `0060_schema_reconcile` 收敛过的漂移事故。
   **需要「能单独撤掉某个对象」时，把它拆成独立迁移** —— 独立迁移的 downgrade
   天然只撤自己那一项，且版本号如实反映结构。
   实例：唯一索引 `uq_document_catalog_content_hash` 为支持
   「只撤索引、保留 `wiki_page.content_hash` 与 `wiki_import_task.skipped_pages`」
   而从 `0061_wiki_dedup` 拆成 `0062_doc_catalog_hash_unique`。
3. **迁移与代码必须同批上线**。本仓库出现过危险中间态：prod 的
   `alembic_version` 已推进（唯一索引已生效），而容器仍跑旧代码 —— 旧代码对该
   唯一索引无任何处理，重复上传抛未捕获的 `IntegrityError` → 500，且此时对象存储
   与向量库的副作用已经写下。**DDL 与依赖它的代码不得分开部署。**
4. **幂等**：`ADD COLUMN IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`，
   与 0053+ 同模式 —— prod 是从 dump 恢复出来的，重复执行必须是 no-op。
5. **迁移的降级行为要有测试钉住**（尤其「降级后哪些对象还在」），
   见 `backend/app/tests/integration/test_document_catalog_content_hash_unique_migration.py`。

## 例外

- 纯算法 /纯计算 /前端组件单测：不触 DB，无需走 prod / test 任一库。
- 用户明确说「这次走 test 库」时：以用户指令为准，并在 commit / PR 描述里说明。

## 反模式（review 时拦截）

- ❌ 涉及表结构变更却在 `qa_metadata_test` 跑 alembic / DDL 后声称「验证通过」
- ❌ 在 prod `qa_metadata` 上执行 DDL / 数据迁移却没先 `pg_dump` 备份
- ❌ 把「在 test 库跑通了」当作 prod 上线的充要条件
- ❌ 备份表名没用日期后缀，导致多次备份互相覆盖、无法区分
- ❌ 「prod 怕炸所以我在 test 库先试一下」——按本规范，这种 reasoning 是禁止的，prod 该用就用，先备份
- ❌ 迁移 revision id 超过 32 字符（写版本号时才炸，且 DDL 已执行 —— 半截状态）
- ❌ 把 `downgrade()` 写成不对称（只撤一部分），让库停在无 revision 描述的状态
- ❌ 迁移已上线而依赖它的代码没同批上线（或反之）
- ❌ 新增/修改迁移后不跑降级语义测试，靠「源码里写了这行」当作验证
- ❌ 手工 DDL（`psql -c "ALTER ..."` / `op.create_table` 在容器外）跑过表结构后**不立刻 stamp**，让 `alembic_version` 落后于事实 → 下次启动撞 `DuplicateColumnError` / `DuplicateTableError` → backend crash loop（详见下文「迁移元数据漂移治理」）

## 迁移元数据漂移治理（CRITICAL，2026-10-14 起）

### 问题

`alembic_version.version_num`（单行 VARCHAR(32)）与库内实际 schema 不同步。最常见两类：

1. **DDL 已跑、版本号落后**（典型场景：分支切换 / 合版撞号 / 之前手工 psql 跑过迁移的 DDL 但没 stamp / `docker cp` 覆盖代码但库未回退）。症状：下次 `alembic upgrade head` 在 `op.add_column` / `op.create_table` 撞 `asyncpg.exceptions.DuplicateColumnError` / `DuplicateTableError` → backend crash loop。
2. **版本号被伪造、DDL 没跑**（典型场景：有人 `UPDATE alembic_version SET version_num = 'XXXX'` 试图跳过迁移；或裸 `pytest` 跑集成测试时 conftest 改了 `alembic_version` 但没真改库）。症状：`alembic current` 看着正常，但 ORM 启动 / API 命中时报 `UndefinedTableError` / `UndefinedColumnError`。

### 强制纪律（不可违反）

1. **任何手工 DDL（`psql -c "ALTER ..."`、`docker exec ... pg_dump / pg_restore`、`docker cp` 覆盖代码后又跑了 schema 变更等）跑过表结构后，必须立刻 `alembic stamp <revision>` 让元数据追上事实**。这是「承认事实」，不是「伪造版本号」（见下文判定）。
2. **严禁在 DDL 没实际生效的情况下改 `alembic_version`**。`UPDATE alembic_version SET version_num = 'XXXX'` 只改声明不追事实 → 整片假 error，下一次启动 / ORM 初始化全炸。
3. **stamp 之前必须逐条对账**：库内 schema 必须与目标 revision（含其整条 lineage）的 DDL 描述**逐对象匹配**。不允许「大致差不多」就 stamp。
4. **stamp 命令必须显式覆盖 `DATABASE_URL`**（即便走 docker compose env_file 注入），留痕便于审计追溯。这与「宿主机裸 `alembic upgrade head` 会打 prod」是同一条 SSOT 端口契约的不同应用（见下文 §环境区分）。

### 识别症状（启动撞名 = 漂移信号）

启动日志（`docker logs qa-backend`）若命中以下任一异常 → **第一动作不是改迁移文件 / 改 Dockerfile**，是按本节流程做对账：

```
asyncpg.exceptions.DuplicateColumnError: column "X" of relation "Y" already exists
asyncpg.exceptions.DuplicateTableError: relation "X" already exists
sqlalchemy.exc.ProgrammingError: ... already exists
```

崩溃入口常落在 `env.py:80 asyncio.run(_run_async_migrations())` 或 `env.py:58 await connection.run_sync(_do_run_migrations)`，但**触发点必然是某条 `NNXX_*.py` 里的 `op.add_column` / `op.create_table`**。在 traceback 里抓最后一个 `<some_revision>.py` 行号，就是漂移点。

### 修复流程（标准动作）

按顺序执行，**每步验证后再下一步**：

```bash
# 1. 停 backend（crash loop 状态下 stamp 也会被反复重试干扰）
docker compose -f docker/docker-compose.yml stop backend

# 2. 摸清 alembic 元数据现状
docker exec qa-postgres psql -U qa_user -d qa_metadata -c "SELECT version_num FROM alembic_version;"
docker compose run --rm \
  -e DATABASE_URL='postgresql+asyncpg://qa_user:qa_pg_dev_2026@postgres:5432/qa_metadata' \
  backend alembic heads
# 期望：单条 head revision（多 head = 撞号，按 [变更记录强制规范] 处理）

# 3. 逐条对账 line head 整条 lineage 的 DDL 与库内 schema
#    对每条 revision 的 upgrade()，grep 出 op.add_column / op.create_table / op.create_index
#    等所有 op.* 调用，再用 \d <table> / pg_indexes 在库内一一确认存在
#    —— 这一步是 stamp 的「事实证据」，不可省
grep -E "op\.(create_table|add_column|alter_column|create_index)" \
  backend/alembic/versions/<revision>.py

docker exec qa-postgres psql -U qa_user -d qa_metadata -c "\d <table>"
docker exec qa-postgres psql -U qa_user -d qa_metadata -c \
  "SELECT indexname FROM pg_indexes WHERE tablename='<table>' ORDER BY indexname;"

# 4. 若 lineage 全部对齐 → stamp head（承认事实）
docker compose run --rm \
  -e DATABASE_URL='postgresql+asyncpg://qa_user:qa_pg_dev_2026@postgres:5432/qa_metadata' \
  backend alembic stamp head

# 5. 验证元数据追上 head
docker compose run --rm \
  -e DATABASE_URL='postgresql+asyncpg://qa_user:qa_pg_dev_2026@postgres:5432/qa_metadata' \
  backend alembic current
# 期望：<head_revision> (head)

# 6. 重启 + 验证
docker compose -f docker/docker-compose.yml up -d backend
sleep 8
docker ps --format 'table {{.Names}}\t{{.Status}}' | grep backend
docker logs qa-backend --tail=20 | grep -E "Application startup|Uvicorn running"
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8000/openapi.json
# 期望：Up + 启动成功 + 200
```

### stamp vs UPDATE alembic_version（判定红线）

| 场景 | 元数据相对事实 | 推荐动作 | 严禁动作 |
|---|---|---|---|
| DDL 已跑、版本号落后（库内对象齐全、`\d` / `pg_indexes` 对得上迁移描述） | **落后** | **`alembic stamp head`** | `UPDATE alembic_version` 直改声明（虽然效果一样但绕过 alembic 审计日志） |
| DDL 没跑、想跳过迁移 | **超前**（声明领先事实） | **补跑 DDL**（`alembic upgrade head` / 手工 SQL 后再 stamp） | `UPDATE alembic_version` 让声明追上（典型「伪造版本号」，下一次 ORM 启动必炸） |
| 部分 DDL 已跑、版本号落后（库内只齐 lineage 的前半段） | **部分落后** | **补齐缺失 DDL 再 stamp head**（补齐方式：`alembic upgrade <revision>` / 手工 SQL） | stamp 到 head（库 schema 缺对象，ORM 启动炸） |
| 不确定 / 拿不准 | n/a | **先按本节流程对账**，对账结果再决定 | 任何形式的 stamp / UPDATE |

### 环境区分（防「宿主机裸跑打到 prod」）

stamp / upgrade 命令在哪一层跑、用哪个 `DATABASE_URL`，跟 §「备份操作流程」里宿主机 vs 容器内 vs 远程 prod 的区分**完全一致**，本节不再重复。SSOT 端口契约见 `Harness/wiki/operations-runbook.md`。

### 反模式（review 时拦截）

- ❌ 看到 `DuplicateColumnError` / `DuplicateTableError` 就去改迁移文件加 `IF NOT EXISTS` —— 这是治标，下一次切分支 / 合版还会撞
- ❌ 看到迁移撞名就 `UPDATE alembic_version SET version_num = '<当前 head>'` —— 跳过对账 = 制造下一次 `UndefinedTableError`
- ❌ 在宿主机（不通过 docker compose）裸跑 `alembic stamp` / `alembic upgrade` 但 `DATABASE_URL` 没显式覆盖 —— 命中 `app/config.py:databaseUrl` 默认值（`localhost:5432/qa_metadata`），把命令打到宿主 PG 而不是容器内 qa-postgres / 远程 prod
- ❌ 撞名后让 `restart: unless-stopped` 一直 crash loop —— 25s 间隔每次都拉一次迁移，掩盖真错误日志（建议先 `docker compose stop backend` 再修）

## 数据库密码失败策略（CRITICAL，强制执行）

**触发场景**：开发或测试访问数据库（prod `qa_metadata` / `qa_metadata_test` / 业务库 Oracle 等任一）时，**任一次连接返回密码错误**（典型信号：`password authentication failed for user`、`ORA-01017`、`Access denied for user`、SQLAlchemy 报 `OperationalError` 含 "password" 等）。

**强制规则（不可违反）**：

1. **最多重试 5 次**（含首次失败）。第 6 次连接尝试必须中止，**不再尝试**。
2. **重试上限到达后立即停止**：把已发生的错误（含 stderr / 完整 traceback / 尝试次数）整理给用户，**询问如何处理**（更新密码？换 user？联系 DBA？回滚到旧配置？）。**不得**继续盲试。
3. **不得在循环里加 backoff / sleep 后继续重试**：策略的本意就是「失败次数封顶」，sleep 只会拉长事故链。
4. **不得绕过这条规则尝试「最后一次验证」**：5 次就是 5 次。

**适用范围**：

- 任何手工命令（`psql`、`pg_dump`、`docker exec`、Oracle 客户端等）。
- 任何 pytest / uv run / alembic / 后端启动时的 DB 连接失败。
- 本地开发连接（5433/5434/7687/7688 等任一端口）。
- 容器内连接（`docker exec qa-backend` / `docker exec qa-postgres`）。

**为什么（本仓库实踩的坑）**：

- 某些数据库 / 认证代理在连续密码错误后会**锁定账号 / 触发风控**（典型阈值 5~10 次）。无封顶重试可能把生产账号打挂，恢复流程比修一次密码长得多。
- 「再试一次说不定就行」是反模式 —— 密码错误是**确定**信号，不是网络抖动。重试不会改变凭证的有效性，只会放大事故。
- 5 次足够区分「手抖输错」（≤ 2 次就能纠正）和「配置 / 凭据根本不匹配」（5 次都不可能通）。

**标准动作**：

```bash
# 第 1~5 次：每次都明确失败，**记录**到当前 shell 历史 / 日志
docker exec qa-postgres psql -U qa_user -d qa_metadata -c "SELECT 1"  # 失败 → 报错
# ... 至此已 ≥ 1 次
# 累计到第 5 次仍失败 → STOP，下面是给用户的报告模板

cat <<'EOF'
[DB 密码失败 - 已达 5 次上限]
库: <qa_metadata | qa_metadata_test | Oracle ds_id=X>
命令: <原命令>
最近一次错误: <复制 stderr 末行>
当前尝试次数: 5 / 5
按 Harness 规则停止尝试，等待用户指令。

可能的处理选项：
  1. 用户提供新密码（更新 .env / docker-compose.yml / ~/.pgpass）
  2. 切换到别的 user（qa_user → postgres / 业务库其他账号）
  3. 跳到这台 DB 的运维文档走凭据恢复流程
  4. 取消本任务
EOF
```

**反模式（review 时拦截）**：

- ❌ 密码报错后继续无封顶重试（任何 `while True` / `for i in {1..20}` / shell `!!` 重复执行）
