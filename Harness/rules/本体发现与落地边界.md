# 本体发现与「落地」边界（WP-ONT-AI / G5）

> 2026-11-22 ｜ 适用：发现域（discovery_*）、语义发布、本体管理
> 结论：**发现域只产出候选与意见，不写本体**；落地由人工在「本体管理」完成。

## 一、红线（不可破）

1. **发现域不写本体表**：只写 `discovery_*`；本体类/属性/指标/关系的写入口只有
   `ontology_service`（本体管理页），四眼与审计在这一侧。
2. **候选不是结论**：`discovery_candidate.status=ACCEPTED` 只代表「业务同意」，
   不等于已进入本体；发布只走既有 `semanticReleaseService`。
3. **判定可追溯**：候选/问题的判定与关联都落 `decided_by/time/decision_note`
   + `linked_entity_type/code`，历史在 `audit_log`。

## 二、已落地的「轻量关联」（0169）

| 能力 | 说明 |
|---|---|
| 关联本体对象 | 候选/问题可挂到 `ONTOLOGY_CLASS` / `ONTOLOGY_PROPERTY` / `ONTOLOGY_METRIC`（自然键：类名 / 类名.属性名 / 指标名） |
| 解决前必须关联 | finding 置 `RESOLVED` 前必须有 `linked_entity_code`（防「空口关闭」） |
| 对照与深链 | 评审页「关联本体」弹窗按 `targetCode` 匹配已有类，提示「已存在去更新」或「暂无去新建」，并一键打开本体管理页 |
| 证据可复核 | 候选证据带 `channel=PROFILE` / `ref` / `summary`（实测数字） |

## 三、待优化：**全自动落地**（采纳即写本体）

> 用户 2026-11-22 决策：**暂不做**，登记为待优化事项，后期择机。

**为什么不现在做**：要在采纳动作里写本体表 ⇒ 等于在发现域开第二写口，
直接撞上述红线；且缺少审批、幂等、回滚与灰度四件套。

**开做的前置条件（缺一不可）**：

1. 写入口放在**本体管理/治理侧**（`applyProposal` 一类的具名函数），发现域只发请求；
2. **四眼 + 审批**：至少提案级审批（复核 P5 `approval_task` 或 `discovery_review` 强四眼）；
3. **幂等**：同一候选重复采纳不产生重复类/属性（自然键 + 冲突处理明确）；
4. **可回滚**：落地动作必须有对应的撤销（软删除/版本），并与发布回滚口径一致；
5. **灰度开关**：默认关闭；按域/按源开启；
6. **审计**：落地动作逐条落 `audit_log`，并可反查「这条类来自哪个候选/哪次运行」；
7. **测试**：契约守卫（禁直写本体表）+ 变异反证 + 真实 PG 集成用例。

**验收口径（将来）**：误写/重复写入 = 0；回滚演练通过；每条落地可追溯到候选与证据。
